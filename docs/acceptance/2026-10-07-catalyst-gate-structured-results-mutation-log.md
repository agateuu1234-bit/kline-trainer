# Catalyst 闸门改读结构化结果 · 变异记录

> 这份文件回答一个问题：**新加的那些测试，到底有没有判别力？**
>
> 「测试全绿」本身什么也不证明 —— 一条永远绿的测试和一条真能抓错的测试，
> 输出长得一模一样。唯一的区分办法是**故意把代码改坏**，看那条测试会不会变红。
> 改坏叫「变异」。下面每一行都是一次「改坏 → 看谁红了 → 改回来」。
>
> 每次变异都先做两件事，否则结论会完全反过来：
> ① 断言要替换的那段文字在文件里**只出现一次**（否则改错地方）；
> ② 替换后**读回文件确认真改上了**（改没上而测试打印「通过」，会让人以为测试没判别力）。
> 最后再跑一次**没有变异**的版本，必须回到 53 通过 0 失败且与变异前逐字一致 ——
> 这叫反向对照，证明上面那些红是变异造成的，不是环境噪声。

日期：2026-10-07 · 分支 `fix/catalyst-gate-structured-results` · 基线 **53 通过 0 失败**

## 二、两处归因订正（下次别再踩）

**1. 「红」不等于「红在该红的那条判据上」。**
写测试那一步，M5b/M6/M7 三档确实红了，我差点据此往下走。实际红的原因是：
喂数据的小脚本里写 `cat <文件路径>` 没加引号，而本仓目录名含空格
（`Prj_Kline trainer`）⇒ 系统把路径当成两个文件、取数失败 ⇒ 闸门按「取数失败就不放行」
退出。也就是说那三条红**与要测的东西无关**。
改法：路径加引号（`printf %q`）；并给测试台加一行「退出码不符时把闸门的原话打出来」——
没有这一行，看不见红在哪条判据上。

**2. 变异的方向必须和用例的方向对上。**
我原以为「G8 退回读文本」（变异 C）能杀掉 M7。实测杀不掉，而且本该如此：
M7 测的是「转义落在不参与匹配的行上，不算违规」，而变异 C 并不引入「有转义就违规」
这个行为。M7 真正的对位变异是 F。用错方向会得出「这档没判别力」的**假结论**。

## 三、真机真包实证（不靠构造样本）

本机真跑了一次 Catalyst 构建（带 `-resultBundlePath` 产出结果包），拿**真结果包**跑闸门：

| 动作 | 实得 |
|---|---|
| 构建结果 | `TEST SUCCEEDED`；文本汇总行 `Test run with 1935 tests in 227 suites passed` |
| 结果包 | 18 MB；取数脚本退出码 0，吐出 1 309 518 字节 JSON |
| 结果包里的测试节点 | **2054 个，全部 `Passed`** |
| 活基线 80 条 | 在「Passed 名字集合」里**逐条命中，0 条找不到** |
| 闸门（真包 + 真日志 + 活基线） | **GATE PASS** |
| 正向对照：从真包数据里删掉 1 条 | **GATE FAIL 并点名**那条测试 |

⭐ 顺带实证了 spec §4.1 的理由③：文本汇总行说 **1935**（只数一种测试框架），
结果包里是 **2054**（两种框架混在一起）—— 两个数本就不同口径，这正是 G7 不迁移的原因之一。

## 四、端到端：同一份真日志 + 同一个真包，改前假红、改后放行

把真日志里某条 baseline 测试的 ✔ 行做成转义态（`§` → `\302\247`，只改这一行，
形态照真实日志里已经出现过的样子），其余一切不变：

| 闸门版本 | 退出码 | 结论 |
|---|---|---|
| 本片**之前**（grep 日志文本） | **1** | **假红** —— 真包明明记录着这条测试 `Passed` |
| 本片**之后**（读结构化结果） | **0**（GATE PASS） | 假红已治 |

⚠️ 改前那次的失败文字是新版措辞（变异只换了判据那一行、没换提示语），
不影响结论：**输入完全相同，退出码 1 对 0**。

## 五、验收脚本自身的两个缺陷（实测打断它才暴露）

A3 那条验收动作会把闸门临时改成「什么都放行」。我原本把它写成一行长命令，
后来落成脚本 `catalyst-gate-judgment-check.sh`。**真去打断它**才发现两件事：

**1. 原本写成一行长命令时，中断会把闸门留在「恒接受」状态。**
2026-10-08 真发生过：一个验证进程被我杀在「已施加变异、还没还原」的中间，
`catalyst-gate.sh` 就此停留在 `if false && …` —— 也就是那条判据什么都放行。
是 `git status` 显示该文件被修改才发现的。这就是落成脚本（带「无论怎么退出都还原」）的理由。

**2. 第一版脚本装了还原保险，但被打断后仍然打印「✅ 有判别力」。**
原因：`trap` 里只做还原、没有退出，而 bash 在被打断的命令之后会**继续往下跑**。
于是用户按了 Ctrl-C，却看到成功结论；更糟的是变异那次根本没有产出末行，
判断语句拿空值去比对、匹配不上「0 失败」，于是**被当成通过** —— 标准的假绿。
顺带还打出一条指向已删除备份文件的「⛔ 还原失败！请手动执行…」，骇人且是假的。

**怎么测出来的**：第一次实验我直接给脚本进程发中断信号，结果它跑完了全程、退出码 0 ——
**那次什么也没证明**（bash 正阻塞在子进程上，要等子进程结束才处理信号）。
真实用户按 Ctrl-C 是发给**整个前台进程组**。改成整组发信号后才真打中。

**修完的实测**：打断在最危险的窗口 → 打出「先还原闸门，再退出（本次不产出任何结论）」
→ 退出码 **130** → 闸门与提交状态逐字一致 → **没有**任何成功结论。
未被打断的正常路径仍然报「✅ 有判别力」、退出码 0。

> 教训：「我装了保险」和「保险真的兜得住」是两件事，中间隔着一次真打断。
> 而且**测保险的方式本身也会测错** —— 第一次实验的做法根本没触发它要测的那条路径。
