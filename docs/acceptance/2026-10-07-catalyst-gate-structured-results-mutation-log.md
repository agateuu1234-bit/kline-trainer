# Catalyst 闸门改读结构化结果 · 变异记录

> 这份文件回答一个问题：**新加的那些测试，到底有没有判别力？**
>
> 「测试全绿」本身什么也不证明 —— 一条永远绿的测试和一条真能抓错的测试，
> 输出长得一模一样。唯一的区分办法是**故意把代码改坏**，看那条测试会不会变红。
> 改坏叫「变异」。下面每一行都是一次「改坏 → 看谁红了 → 改回来」。
>
> 每次变异都先做两件事，否则结论会完全反过来：
> ① 断言要替换的那段文字在文件里**只出现一次**（否则改错地方）；
> ② 替换后**读回文件确认真改上了**（改没上而测试打印「通过」，会让人以为测试没判别力）。
> 最后再跑一次**没有变异**的版本，必须回到 58 通过 0 失败且与变异前逐字一致 ——
> 这叫反向对照，证明上面那些红是变异造成的，不是环境噪声。

## 二、两处归因订正（下次别再踩）

**1. 「红」不等于「红在该红的那条判据上」。**
写测试那一步，M5b/M6/M7 三档确实红了，我差点据此往下走。实际红的原因是：
喂数据的小脚本里写 `cat <文件路径>` 没加引号，而本仓目录名含空格
（`Prj_Kline trainer`）⇒ 系统把路径当成两个文件、取数失败 ⇒ 闸门按「取数失败就不放行」
退出。也就是说那三条红**与要测的东西无关**。
改法：路径加引号（`printf %q`）；并给测试台加一行「退出码不符时把闸门的原话打出来」——
没有这一行，看不见红在哪条判据上。

**2. 变异的方向必须和用例的方向对上。**
我原以为「G8 退回读文本」（变异 C）能杀掉 M7。实测杀不掉，而且本该如此：
M7 测的是「转义落在不参与匹配的行上，不算违规」，而变异 C 并不引入「有转义就违规」
这个行为。M7 真正的对位变异是 F。用错方向会得出「这档没判别力」的**假结论**。

## 三、真机真包实证（不靠构造样本）

本机真跑了一次 Catalyst 构建（带 `-resultBundlePath` 产出结果包），拿**真结果包**跑闸门：

| 动作 | 实得 |
|---|---|
| 构建结果 | `TEST SUCCEEDED`；文本汇总行 `Test run with 1935 tests in 227 suites passed` |
| 结果包 | 18 MB；取数脚本退出码 0，吐出 1 309 518 字节 JSON |
| 结果包里的测试节点 | **2054 个，全部 `Passed`** |
| 活基线 80 条 | 在「Passed 名字集合」里**逐条命中，0 条找不到** |
| 闸门（真包 + 真日志 + 活基线） | **GATE PASS** |
| 正向对照：从真包数据里删掉 1 条 | **GATE FAIL 并点名**那条测试 |

⭐ 顺带实证了 spec §4.1 的理由③：文本汇总行说 **1935**（只数一种测试框架），
结果包里是 **2054**（两种框架混在一起）—— 两个数本就不同口径，这正是 G7 不迁移的原因之一。

## 五、验收脚本自身的两个缺陷（实测打断它才暴露）

A3 那条验收动作会把闸门临时改成「什么都放行」。我原本把它写成一行长命令，
后来落成脚本 `catalyst-gate-judgment-check.sh`。**真去打断它**才发现两件事：

**1. 原本写成一行长命令时，中断会把闸门留在「恒接受」状态。**
2026-10-08 真发生过：一个验证进程被我杀在「已施加变异、还没还原」的中间，
`catalyst-gate.sh` 就此停留在 `if false && …` —— 也就是那条判据什么都放行。
是 `git status` 显示该文件被修改才发现的。这就是落成脚本（带「无论怎么退出都还原」）的理由。

**2. 第一版脚本装了还原保险，但被打断后仍然打印「✅ 有判别力」。**
原因：`trap` 里只做还原、没有退出，而 bash 在被打断的命令之后会**继续往下跑**。
于是用户按了 Ctrl-C，却看到成功结论；更糟的是变异那次根本没有产出末行，
判断语句拿空值去比对、匹配不上「0 失败」，于是**被当成通过** —— 标准的假绿。
顺带还打出一条指向已删除备份文件的「⛔ 还原失败！请手动执行…」，骇人且是假的。

**怎么测出来的**：第一次实验我直接给脚本进程发中断信号，结果它跑完了全程、退出码 0 ——
**那次什么也没证明**（bash 正阻塞在子进程上，要等子进程结束才处理信号）。
真实用户按 Ctrl-C 是发给**整个前台进程组**。改成整组发信号后才真打中。

**修完的实测**：打断在最危险的窗口 → 打出「先还原闸门，再退出（本次不产出任何结论）」
→ 退出码 **130** → 闸门与提交状态逐字一致 → **没有**任何成功结论。
未被打断的正常路径仍然报「✅ 有判别力」、退出码 0。

> 教训：「我装了保险」和「保险真的兜得住」是两件事，中间隔着一次真打断。
> 而且**测保险的方式本身也会测错** —— 第一次实验的做法根本没触发它要测的那条路径。

## 六、内部评审的三条 Important（2026-10-12，已全部修完并实测）

codex 整支评审之前先派了一个独立评审员（它自己跑了变异复核，没照抄本文）。
结论：**0 条 Critical，3 条 Important** —— 三条都在「验证工具」上，不在生产闸门逻辑里。
我把三条逐条独立复现过（⛔ 不凭它的自述），确认都成立。

**#3 元测试的正则漏扫（最该修：它正好打在本片自称的「完整性保证」上）**
原来用 `[a-z0-9.-]+\.log` 匹配样本文件名 ⇒ 带下划线或大写的样本名**一个都扫不到**。
我自己验了：`some_new_fixture_with_underscores.log`、`NewFixture.log` 都漏。
⚠️ 修法**不是**放宽字符类 —— 放宽后它会匹配到元测试自己那行正则、反而误报。
改成「行首是 `expect` + 取第 3 个字段」，不做字符类假设，并先把反斜杠续行接起来。
另加一条：扫到 0 个就判红（今天至少 2 个，扫出 0 只可能是取数坏了）。
四个性质逐个实测：仍只扫到那 2 个真样本且不自匹配 / 下划线+大写+**跨物理行**三种都扫到 /
零匹配会判红 / 测试台全绿。

**#1 备份丢失会让闸门永久停在「什么都放行」**
原来拿「备份文件还在不在」当幂等判据 —— 它分不清「已经安全还原过」与「备份被外力删了」，
后者直接 return 0，闸门留在被改坏状态而不说一句话。修了三层：
① 备份建不出来或与闸门不逐字相同 ⇒ **拒绝变异**（实测退出码 2、闸门零改动）；
② 改用 `MUTATED`/`RESTORED` 标志判定；
③ **备份真丢了就按反向替换还原** —— 变异是确定性字符串替换，不需要备份也能改回去，
   且只在「恰好 1 处变异体」时动手，并自证改回成功。
实测（钉死 TMPDIR 后删掉备份再整进程组发 SIGINT）：退出码 **130**、打出
「备份文件不见了…已按反向替换把闸门改回原样（已自证）」、闸门与提交状态逐字一致、
锁不残留、**不产出任何成功结论**。

**#2 并发两份会互相毁掉备份**（第二份可能把第一份留下的变异体当原文备份）
加目录锁（`mkdir` 原子互斥；⛔ 不用 `flock`，macOS 没有）。实测第二份退出码 2、闸门零改动。
验收清单里原先把并发只说成「会变慢」—— 轻描淡写，已改成「可能把闸门留在被改坏的状态」。

两条 Minor 也处理了：`kill -9` 兜不住这件事写进头注释并给出事后自查命令；
关于 `2>&1`，实测后发现**我和评审员说的是不同的两处，两层保护都真实存在** ——
取数脚本的 stderr 由 `json.load` 的严格性拦下（GATE FAIL「结构化结果解析失败」），
python 自己 exit 0 时的 stderr 由整行相等（`-x`）挡住（GATE PASS）。两层都写进注释。

### 修这一轮又暴露我自己两个新缺陷

**(a) 锁泄漏。** 脚本中途那句 `trap - EXIT INT TERM HUP` 把 EXIT 处理器清掉了，
于是我刚加的锁在**正常跑完**后残留，下一次运行会被自己上一次的锁挡住（退出码 2）。
是实验输出里「锁残留:」那一行显示出来的。改成只撤信号处理器、保留 EXIT
（`restore` 现在幂等，留着不会重复还原）。

**(b) `$VAR` 紧跟汉字，第三次犯。** `$BACKUP）` —— bash 把全角括号的字节吃进变量名，
`set -u` 下运行到那行直接崩。本片里我已经用正则全文扫过一遍修掉过，
**然后在修完别处之后新写的那几行里又犯了一次**。
⇒ 不再靠记性：测试台加了一条结构性守卫，扫 `.github/scripts/*.sh`，凡 `$VAR` 紧跟
非 ASCII 字符就判红并点名文件和行号。判别力已实测（故意塞一处 →
`FAIL … catalyst-result-tests.sh:29`，还原后回到全绿）。

⭐ 一个意外收获：**(b) 那次崩溃反而验证了 #1 的兜底是有效的** —— 崩的那行正是
「反向替换成功」的提示语，说明备份被删后闸门确实被改回去了。我用三个独立判据
核过当时闸门的真实状态（变异体 0 处 / 原判据 1 处 / 与提交状态 0 行差异），
⛔ 没有只看 `git diff` 一个判据。
