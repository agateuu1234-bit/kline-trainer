## 为什么要做这件事

一项自动检查显示「通过」，**本身说明不了任何事**。

举个极端例子：一项检查如果写成「只要程序还在运行就算通过」，那不管代码被改成什么样，
它永远显示通过——这种检查等于没有。

所以每写完一条新规矩，光看「现在是绿的」不够，必须反过来问一句：

> **如果我故意把这条规矩改坏，有没有任何一项检查会报警？**

没有人报警，就说明这条规矩**写在代码里但没人盯着**，哪天被误删、被改坏，整套检查
照样全绿。这份文档记的就是逐条「故意改坏、看报警」的全过程。

⛔ 本文件**不写「共 N 组」这类总数**——本仓栽过「写死的总数在下一次补记时变错」的坑。
条数请自己数：

```
grep -c '^## M' docs/acceptance/2026-10-02-qmt-r1-committed-bytes-refund-mutation-log.md
```

## 纪律（本仓踩过坑，逐条写死）

1. **改之前记下文件指纹**（`shasum -a 256`），**改完逐字还原再比一次**，必须相同。
   ——证明「确实还原了」，不是「我以为还原了」。
2. **每次跑之前清掉 `__pycache__`**（Python 的编译缓存目录），并带环境变量
   `PYTHONDONTWRITEBYTECODE=1`。——不清的话，Python 可能用的是**改动之前**缓存下来的
   旧代码，于是「改坏了却没人报警」这个结论是假的。
3. **比红绿只比「失败条数 + 失败项的名字」**，绝不比 pytest 那行汇总。
   ——那行带运行耗时（`2.65s` vs `2.64s`），两次必然不同，拿它比会把**真发现判成误报**。
   ⚠️ 这不是假设：本片第一次做变异验证时，我的核验脚本就是比整行汇总，给出了
   「变异被杀掉」的**错误结论**，而正确结论是「变异存活」——也就是那条规矩当时真的没人盯着。
   **错的方向是危险的那一边**（会让人把真问题当误报丢掉）。
4. **变异方向必须与检查项的方向对上**：
   - 断言「**该拦住**」的项，只有把规矩**放宽**才杀得死；
   - 断言「**该放行**」的项，只有把规矩**收紧**才杀得死。
   ⚠️ 方向用反会得出「这项检查没判别力」的**假结论**。本片我也先错过一次（见 M4 一节）。
5. **把邻居全部 deselect（排除），单独再跑一次目标项**。
   ——「一堆检查里有东西红了」不等于「红的是它」。
6. **每条命令都打印 `branch` 与 `HEAD`**。——防「跑到了别的分支、测的是另一份代码却全绿」。

## M4 · 「恢复时一条新记录都不许夹带」的那个分岔（本片最重要的一发）

这一发暴露的是**规范与实现差了一格**，而差的那一格能被绕过。

**背景**：规范原文约束的是「不得包含任何新增的**键**（条数）」。第一版实现写成了
「新增的**字节数之和**大于 0 才拦」。两者在一种情况下分岔：**夹带的记录字节数恰好是 0**。

**改哪里**（把实现退回第一版）：

```
if added_keys:      →      if added_in_recovery:
```

**实测输出**：

```
基线         失败 3 / 通过 1635
变异后        失败 4 / 通过 1634
  变异**新增**的红: ['tests/test_qmt_manifest.py::test_r1_u19_recovery_rejects_added_records_even_with_zero_bytes']
  变异**消失**的红: （无）
   U15  ⚪ 仍绿     U16  ⚪ 仍绿
  ⇒ ✅ 变异被杀：U19 精确变红，U15/U16 两边都没红 —— 订正到位且没改过头
还原后 sha256: 06a4bf9fabc3d830d83909e309c92a15614d62fde1931fe2fa84e753017a2044 ——与改前逐字相同
```

**为什么 U15/U16 必须仍绿**：它们夹带的记录字节数**不为 0**，两种写法都拦得住它们。
若它们也变红，说明订正**改过头**了——把本来合法的情形也拦了。

**发现这个分岔的过程**（先用探针把问题跑出来，而不是读代码推断）：

```
新增两条 bytes=1234567（U15 的情形）     ✅ 拦住：…「只许移除」…（本次新增了合计 2469134 字节）
新增两条 bytes=0（spec 与实现分岔处）      ⛔ **放行** —— 新增了 2 条键却没被拦
```

⚠️ 探针用的账本**先过了真正的读侧校验函数**（`validate_manifest`），
证明它是一份**合法**账本，不是畸形输入——否则这个发现证明不了什么。

**改成按条数判之后的额外收益**（终审时实测）：夹带的记录如果字节数字段**缺失 / 是空值 /
是文字 / 是负数 / 是 0 / 是布尔值**，按字节求和的写法会算不出来而放过，
**按条数判一律拦住**——六种畸形值**全部拦住**。因为按条数判根本不看那个字段长什么样。

## M7 · 「断言落盘」与「断言返回值」的差别（这一发证明了一条断言是空的）

**背景**：有一项检查写着「落盘后的总账必须等于退还后的数」，但它查的是
`commit_stock()` 的**返回值**。而 `commit_stock` 的最后一行就是 `return payload`——
返回的正是测试自己递进去的那个内存对象。所以对总账这个字段而言，那条断言是
**拿自己刚写进去的值跟它自己比**，恒成立。

**改哪里**：构造一个「守卫照常放行，但写到磁盘上的字节是错的」状态
（只污染要写盘的那份副本，不动内存对象，且只在崩溃恢复提交时污染）。

⚠️ **第一次尝试失败并已撤销**：最初的改法是对每次写盘无条件 +1，结果连基线数据
一起污染、守卫自己先报错，于是**分辨不出两种写法的差别**。换成只在恢复提交时污染
写盘副本，才构造出目标状态。**失败的尝试一并记在这里**，因为它说明了为什么最终那个
改法必须长成那样。

**实测输出（A/B 对照）**：

```
read_manifest 风格（改后）→ FAIL（expected=9806956, on_disk=9807955）  ✅ 抓住了
当前 result[...] 风格（改前）→ 仍判通过（expected=26, result=26，而磁盘实为 1025）⛔ 漏掉
```

**结论**：改后抓得住、改前抓不住 ⇒ 这次修的是**一个真盲区**，不是换了个说法。

> ⚠️ 这一发还暴露了一条更一般的教训：**常规那个变异（把退款分支整个摘掉）两种写法都杀得死**
> ——守卫一拒绝，内存和磁盘两条路都走不通。所以**那个变异根本分辨不出这两种写法的差别**。
> ⇒ **「故意改坏能让检查变红」不等于「这条断言问对了问题」**，还要问一句：
> **那个「改坏」有没有对准这条断言本身？**

## M8 · 三项检查「声称在测 A，实际被 B 挡住」

**发现方式**：把某条规矩停用，看声称盯着它的那项检查会不会红。

- **U5**：声称盯「总账不许调小」。停用那条规矩后 **U5 全绿**。
  实际拦住它的是**排在前面**的另一条规矩（「已提交的文件记录不得回滚」）。
  已订正它的说明文字，并补上「该报哪种错」的匹配串。
- **U6 / U7**：同类扫查时发现的——它们声称盯的规矩**本身没写错**，但都缺「该报哪种错」
  的说明。逐项跑出真实报错文本核实后补上。

**机械扫查（不是肉眼数）**：本片 23 项检查里，**14 项**断言「该拦住」，
现在 **14 项全部**写明了该报哪种错，**0 项**遗漏；其余 **9 项**是断言「该放行」的，不涉及。

⚠️ **这三个数本文上一版写错成 13 / 13 / 10**（总数 23 对、拆分错）。
是 codex 对抗性评审第 2 轮指出的（它报「实际为 14 项拒绝、9 项放行」），
控制者用 AST 机械扫描复核，与它一致 ⇒ 已订正。
⭐ 教训：**补了几条用例之后，派生出来的拆分数要重新量，不能在原数上加减**。
本文开头之所以不写「共 N 组」，正是同一个道理 —— 写死的派生数在下一次补记时就会变错。

> 2026-10-04 补记 · **这个错是两轮前埋下的，追一下链条**（每个数都是在对应 commit 上
> 用同一段 AST 脚本当场量的，不是推算）：
>
> | 提交 | 真实拆分 | 本文当时写的 |
> |---|---|---|
> | `22dbde99`（19 条） | 11 拦截 / **8** 放行 | 11 / 8 ✅ |
> | `690ce405`（20 条，+U20 拦截档） | **12** / 8 | 20 / **11 / 9** ⛔ |
> | 当前（23 条，+U21/U23 拦截 +U22 放行） | **14 / 9** | 13 / 10 ⛔ |
>
> **根因**：加 U20 那一轮，总数从 19 改成了 20，但**拆分没有重新量** —— 拦截数没动
> （仍写 11，实为 12），放行数凭空从 8 变成 9。下一轮又在这个错基数上加「2 拦截 +1 放行」，
> 于是错继续传下来，直到 codex 第 2 轮把它指出来。
>
> ⭐ **这正是本文开头不写「共 N 组」的理由的另一半**：不只是总数会变错，**派生出来的
> 拆分数更会变错**，而且错得更隐蔽 —— 总数对的时候，拆分错没人会去查。
> 凡是派生数，要么现场量，要么别写。
>
> 两条新的拦截档都带了匹配串，且都用 `git grep` 确认该串在 `qmt_manifest.py` 的
> 报错文案里唯一。

## M10 · 放宽方向：把那两条规矩改回原来的嵌套

**2026-10-04 补记** —— codex 对抗性评审第 1 轮（判决 `needs-attention`）的唯一一条
finding：「恢复时不许夹带新记录」与「必须恰好退还多少字节」这两条规矩，被**打包塞进
同一个开关**（`if ob is not None:`，意思是「只有上一份账本带着总账数字时才检查」）。
而旧账本**允许没有总账数字**（故意留的兼容性，见 spec §8 的 R-B2）。

**先复现，再动手**（两份账本都先过了真正的 `validate_manifest`，证明是合法账本）：

```
对照组：上一份**带** committed_bytes → ✅拦住（报「只许移除」，并列出新增的两个键）
实验组：上一份**缺** committed_bytes → ⛔放行 —— 夹带 2 条新记录、共 2469134 字节
```

**修法**：把那一层塌掉、去掉开关 —— 「不许夹带」改为无条件执行（它只看键的差集，
压根用不到总账数字）；「必须恰好退还」确实要基准，缺基准就直接拒（新规矩，spec 里
编号 R5）。新补三项检查：U21（绕法本身）、U23（R5 自己）、U22（邻居没被误伤）。

**改哪里（放宽方向，用来打两条「该拦住」的检查）**：

```
if scoped_removed:                     →  if scoped_removed and ob is not None:
```

这一改**精确等价于修复前的行为**：缺总账数字时两条规矩一条都不执行。

**实测输出**：

```
单独跑（邻居 deselect 掉）：2 failed, 1 passed, 401 deselected
  FAILED ...test_r1_u21_recovery_on_a_ledger_without_committed_bytes_cannot_smuggle_new_files
  FAILED ...test_r1_u23_recovery_on_a_ledger_without_committed_bytes_is_refused
整个 test_qmt_manifest.py：2 failed, 402 passed   ← 失败项名字集合与上面逐字相同，无旁人连带
U22（断言该放行的那条）在这一改下**仍然全绿** ✅ 方向对得上：放宽只杀得死反向用例
```

## M11 · 收紧方向：把新规矩从「只拦恢复提交」改成「一律拦」

**为什么要这一发**：U22 是**正向**用例（断言「旧账本缺总账数字时，普通提交照旧放行」）。
正向用例**只有收紧方向的变异杀得死**。拿 M10 那个放宽变异去打它，它会纹丝不动，
于是会得出「U22 没判别力」的**假结论**——本片的前几轮已经栽过一次这个方向错。

**改哪里**：把 R5 那段判据（文案原样不动）从 `if scoped_removed:` 里提到函数顶层，
于是它对**所有**提交生效，而不只是恢复提交。

**实测输出**：

```
单独跑：2 failed, 1 passed, 401 deselected
  FAILED ...test_r1_u22_a_ledger_without_committed_bytes_still_passes_a_normal_commit   ← 要的就是这条
  FAILED ...test_r1_u21_...cannot_smuggle_new_files
U23 仍绿（它的匹配串正是 R5 的文案，提到顶层后照样命中）
```

⚠️ **U21 一并变红，原因要讲清楚**：R5 被提到顶层后**排在「不许夹带」前面**，于是
U21 收到的报错是 R5 的文案、不是它要匹配的「只许移除」。这是这个变异的**副作用**，
不是 U21 的问题——本发要的证据是 **U22 变红**，它变红了。
