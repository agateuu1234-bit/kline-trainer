# 验收清单 · Catalyst 闸门改读结构化结果（治偶发假红）

> **给非程序员的背景**（三句话）
>
> 我们有一道「闸门」：每次改代码要合并进主线之前，它会自动检查一批测试是否真的跑过并通过。
> 它原来的做法是**读构建时打印的那一大段文字**，从里面找「某某测试 通过」这行字。
> 问题：构建时有两个程序同时往同一个输出口写字，偶尔会把一个中文字符**劈成两半**，
> 文字就对不上了 —— 明明通过的测试被判成「没跑」，于是莫名其妙地变红，重跑一次又好了。
> 本次改动：改成读构建工具**自己生成的结果档案**（一个结构化的数据包，不是打印出来的文字），
> 测试跑没跑、过没过都在里面明确记着，不再受「劈字」影响。

### A2 · 闸门确实已经改成读结构化结果了（而且没留下旧做法）

**动作**
```
cd "/Users/maziming/Coding/Prj_Kline trainer/.dev/worktree/catalyst-gate-structured" && printf '新做法在不在: %s\n旧做法还剩几处: %s\n' "$(grep -cF 'grep -qxF -- "$uikit_test" <<<"$RESULT_PASSED_NAMES"' .github/scripts/catalyst-gate.sh)" "$(grep -cF 'match_str=' .github/scripts/catalyst-gate.sh)"
```

**预期**：两行，分别是 `新做法在不在: 1` 和 `旧做法还剩几处: 0`

**通过 / 不通过**：□ 通过　□ 不通过

> 为什么要查两样、而不是只查「旧做法剩 0 处」：
> 一个「数出 0 个问题」的检查，可能是真的没问题，也可能是**它压根没在看对的地方**
> —— 两种情况输出一模一样。所以同时查一个**应该数出 1** 的东西（新做法在不在）：
> 万一文件改名、判据被整段删掉，这一行会变成 0，当场暴露。
> （已实测双向：把旧做法塞回去一行，第二个数立刻变 1；把新判据改掉，第一个数立刻变 0。）
>
> ⚠️ 命令里的 `-F` 不能去掉：苹果系统自带的 `grep` 会把模式里的 `$` 当成特殊符号，
> 不加 `-F` 就什么都匹配不到、两个数都是 0 —— 看上去像「旧做法已清干净」，其实是检查失效了。
> 这个坑我写这份清单时真踩了一次。
>
> ⚠️ 别用「日志里那串文字出现几次」来查：代码注释里**刻意保留**了一段描述这个缺陷的文字
> （`catalyst-gate.sh:142`），那是给后来人看的说明，不是判据。查它会得到 1，让人误判。
>
> 另外，统计总用例数那条判据仍然读文字，那是**刻意**保留的（见下面第三节）。

### A3 · 测试档位真的能抓错（不是永远绿的摆设）

**动作**
```
cd "/Users/maziming/Coding/Prj_Kline trainer/.dev/worktree/catalyst-gate-structured" && bash .github/scripts/catalyst-gate-judgment-check.sh
```

**预期**：最后一行是 `✅ 有判别力：停掉 G8 判据后测试台变红，还原后回到『结果：58 通过，0 失败』`
（前面会依次打出三行数字：基线全绿 → 停掉判据后**有失败** → 还原后又全绿）

**通过 / 不通过**：□ 通过　□ 不通过

> 这条在回答一个容易被忽略的问题：**那些测试真的在看这道闸门吗？**
> 一套永远绿的测试和一套真能抓错的测试，平时输出一模一样，但前者比没有测试更糟
> —— 它给人虚假的安心。唯一的分辨办法是把闸门**故意弄坏**，看测试会不会变红。
>
> 脚本会自己把闸门改回原样，**而且中途按 Ctrl-C 也会还原**（它装了「无论怎么退出都还原」
> 的保险，并在还原后逐字比对备份，不吻合会报错并告诉你手动还原的命令）。
> 这个保险不是多余的：我写这份清单时，原本把这段操作写成一行长命令，
> 结果一个验证进程被中断在「已经弄坏、还没改回」的中间，闸门被留在了「什么都放行」的
> 状态。落成脚本就是为了这个。
>
> 脚本跑三遍测试台，大约需要几分钟，期间请不要在同一个目录开第二个终端跑测试台
> （两份同时跑会**互相毁掉备份、可能把闸门留在被改坏的状态** —— 脚本已加锁，第二份会直接拒绝运行）。

## 三、这次刻意**没有**做的事（不是遗漏）

1. **总用例数那条判据（G7）继续读文字，没有一起改。**
   三条理由：① 它的文字里不含测试名，劈字伤不到它；② 改它会连带废掉一批既有的检查
   —— 这一条已用变异 G 实测：改了之后 15 项检查变红，其中 10 项是本次改动之前就有的；③ 文字说 1935、
   结果档案说 2054，两个数本就不同口径，不改就不必处理这个差。
   并且加了一档测试钉住它「仍读文字」，谁改它就会立刻红。

2. **不把「日志里出现劈字」本身当违规。**
   劈字是两个程序抢同一个输出口造成的，日志给人看时偶尔还会出现，这不是错误。
   专门有一档测试（M7）钉住这一点，防止有人「治过头」反而造出新的假红。

3. **回滚演练没做**（沿用上一条治理线的决定）。
