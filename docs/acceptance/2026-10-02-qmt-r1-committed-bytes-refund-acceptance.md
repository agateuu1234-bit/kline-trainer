## 这一片做了什么（一句话）

抓取 K 线数据的程序有一个「已经用掉多少字节」的总账。程序崩溃后重启，它会把没抓完的
那只股票的半成品清掉——但**清掉的那部分字节，之前没有从总账里减回去**。于是同一只股票
每崩一次，总账就凭空多记一份。这一片让它**必须恰好减回去**。

## 为什么这件事值得单独开一个改动

总账那个数字，是用来判断「是不是已经用满了用户设定的流量上限」的。

它只多不少地往上涨，后果不是「数字不太准」，而是：

1. 同一只股票反复崩溃重试 → 总账被反复抬高 → 某一刻程序认为**流量用满了**，于是停下来；
2. 而「流量用满」在这套系统里是一种**正常的、干净的结束方式**——上游的检查会直接放行；
3. 结果：**一次基础设施故障（反复崩溃），被记录成了一次正常收工。** 没有任何人、任何
   检查会告诉你「其实是出故障了」。

实测的数字：同一只股票占 2469134 字节，崩两次之后，总账的下限从 12276090 被抬到
17214358——而磁盘上实际写下去的字节数一直没变。

## 怎么修的（两条规矩）

- **规矩一（恰好退还）**：崩溃恢复时，总账必须**正好**减去「被清掉的那些记录所占的字节」。
  多减一个字节也不行（那等于白送流量额度），少减一个字节也不行（那就是原来的毛病）。
- **规矩二（只许减，不许加）**：崩溃恢复这一次提交里，**一条新记录都不许夹带进来**。
  要加新东西，请另起一次提交，好让它的字节被正常记账。

## 过程中发现、并且已经修掉的问题（挑四个说，都不是「写错字」那类）

### 一、规范和实现的理解差了一格，而差的那一格能被绕过

「恢复时一条新记录都不许夹带」这条规矩，第一版实现写成了「夹带进来的记录**总字节数**
大于 0 才算违规」。

两者在一种情况下分岔：**夹带的记录字节数恰好是 0**。实测确认——一份**完全合法**的账本，
恢复时夹带两条字节数为 0 的记录，第一版实现**放行了**。

已改成「只要**条数**不为 0 就拦」。改成按条数判之后还顺带解决了另一类情形：夹带的记录
如果字节数字段**缺失、是空值、是文字、是负数**，按字节求和的写法会算不出来而放过，
按条数判则一律拦住。终审时专门拿这六种畸形值试过，**六种全被拦住**。

### 二、三项检查「看起来在测 A，实际被 B 挡住了」

有三项检查声称自己在盯某一条规矩，但实测发现：真正把它们拦住的是**另一条排在前面的
规矩**。也就是说，它们声称要盯的那条规矩**其实没有任何人在盯**，哪天被改坏也不会有人
发现。已逐项修正，并补上「该报哪一种错」的说明（就是 A3 查的那件事）。

### 三、一条规矩的边界没人盯着

「总账不许调小」这条规矩，原先有一项检查在盯——但它是把总账**一口气调小 166 万字节**。
我把规矩故意放宽 **1 个字节**之后，那项检查**照样通过**。

意思是：如果有人把这条规矩写成「少 1 个字节也行」（编程里很常见的「差一错误」），
整套检查全绿，没人会发现。已补上专门盯这个边界的 U20。

### 四、一条规矩被挂在一个跟它无关的开关后面

「恢复时一条新记录都不许夹带」这条规矩（上面第一条说的就是它），实现时被和另一条
规矩**打包塞进了同一个开关**里：只有当上一份账本**带着总账数字**时，这两条才会被检查。

而旧账本**允许没有总账数字**（这是故意留的兼容性，否则所有已经拉了几百只股的半成品
目录会全部作废）。于是：上一份账本没有总账数字时，这两条规矩**一条都不执行**。

实测（两份账本都先过了真正的格式校验，证明是**合法**账本、不是乱填的）：

```
上一份**带**总账数字 → ✅拦住（并列出夹带了哪两条）
上一份**缺**总账数字 → ⛔放行 —— 夹带了 2 条新记录、共 2469134 字节，没有任何人拦
```

夹带进来的这 2469134 字节**完全不计账**——而「一条新记录都不许夹带」这条规矩，
本来就是为了堵这种不计账。换句话说：**同一个漏洞换了个入口又回来了。**

修法不是在旁边再加一条检查，而是**把那个开关去掉**：「不许夹带」这条规矩压根用不到
总账数字（它只看记录条数），改成无条件执行；真正需要总账数字的那条（「必须恰好退还
多少字节」）则改成「没有总账数字就拒绝做恢复」——没有基准，就没法核对退得对不对。

**正常提交不受影响**：旧账本缺总账数字时，普通的提交**照旧放行**，兼容性一个字节
都没动。专门补了一项检查（U22）盯着这件事，防止「收紧一条规矩时把旁边的正常路径
一起堵死」。
