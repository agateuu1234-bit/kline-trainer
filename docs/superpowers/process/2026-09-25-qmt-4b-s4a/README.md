## 为什么值得留

这一片交付 1345 行产品代码，却跑了 **12 次对抗性评审**（5 次真判决 / 6 条 finding）、
**5 轮修复**、**1 次补做的独立任务评审**。最贵的教训不在代码里，在过程里：

- **同一个缺陷家族被报了三次，每次漏法都不一样**——
  清理路径 → 关源描述符 → 目录遍历辅助函数。三次都是「收尾动作抛的异常顶替在途原异常」，
  后果都是「必须停机」被降级成「跳过这只股」。
- **第四次是自己人挖出来的**：补做的独立评审发现同一条判据写成 `isinstance(...)`
  表达式的两处**完全没有守卫**——上一轮任务书要求「按**字面量**枚举 `except Exception`」，
  于是三处语法相同的被钉住、另两处漏掉。
  ⇒ **按语法枚举 ≠ 按判据枚举。**
- **控制者的任务书两次数错数**（大 spec 覆盖语句说 2 句实际 5 句；关闭点说 9/17 实际 6/14），
  两次都是靠「要求实施者自己重新枚举并报数」兜住的。
- **验收清单写完必须真跑**：C2 那条原本两个参数互相抵消，根本打不出它让读者去数的东西。
- **一次 approve 是拿错基准算出来的**（评审前 main 前进了一步而分支没接上），已作废重跑。

## 没有归档的东西

**10 份评审 diff 包**（`review-<base>..<head>.diff`，合计约 600KB）没有收进来：
它们是机器生成的 `git diff` 输出，只要分支 ref 还在就能原样重建：

```
git diff --stat <base>..<head>
git diff -U10 <base>..<head>
```

⚠️ **前提是 `origin/qmt-4b-s4a` 这个分支 ref 还没被删。** 该分支已 squash 合并，
删掉它之后那 41 个中间提交就不可达了，这些 diff 也就重建不出来。
真要长期保留中间历史，需要另外打 tag。
