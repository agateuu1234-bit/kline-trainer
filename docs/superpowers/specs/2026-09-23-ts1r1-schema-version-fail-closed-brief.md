# TS1-R1 立项简报：把 `schema_version` 改成 fail-closed（下一片）

**状态**：⛔ **本文不是 spec，是立项依据**。真正开工前仍要走
`superpowers:brainstorming` → `superpowers:writing-plans` → `codex:adversarial-review`。

**一句话**：去掉 PostgreSQL `training_sets.schema_version` 的 `DEFAULT 1`，
让**漏给该字段的写入直接失败**，而不是静默拿到第 1 代。

---

## 为什么现在立项（十轮证据）

`schema_version` 漏填会**静默**把第 2 代产物标成第 1 代 —— 不报错、不告警，只是数据错了。
本片（PR：INSERT 守卫）用**文本扫描**去堵这件事，经历了：

| | 数 |
|---|---|
| 对抗性评审轮次 | **10** |
| 被攻破次数 | **10**（每轮一次，无一轮空手）|
| 其中**真假绿**（守卫报绿、语句确实缺字段） | **3** |
| 其中由**我自己的上一轮修复**引入的 | **2** |
| 最终穷举的文本形态 | 69 个 + 5 个正向对照 |
| 仍然挡不住的**已知边界** | **4 类**（见下）|

**攻破的角度逐轮不重样**：注释冒充列名 → 大小写/换行/限定名 → 关键字间夹注释 →
`+` 拼接 → 转义序列 → 限定符点号周围 → 注释里的右括号 → 嵌套块注释 → 行注释里的 `/*`。

### ⛔ 结论：这是**路线的天花板**，不是判据不够细

文本守卫在用**扫描**模拟一个 **SQL 词法分析器**，而宿主语言（Python / shell / YAML /
Markdown）的引号、注释、字符串拼接，与 SQL 自己的引号、注释**互相嵌套** ——
组合是**开放**的，补丁永远慢一步。

## 文本守卫**挡不住**的四类（已实测确认）

| # | 形态 | 为什么挡不住 |
|---|---|---|
| 1 | 表名来自 f-string 变量 | 源码文本里**没有**这个表名 |
| 2 | 表名来自 `.format()` | 同上 |
| 3 | 表名来自常量相加 | 同上 |
| 4 | 语句被 `/* */` 整段注掉、且缺字段 | 抹平后发现层看不见（取消注释即成雷）|

⚠️ 这四类**全部**会被 TS1-R1 挡住 —— 因为它管的是**写入那一刻**，与 SQL 怎么拼出来无关。

## 已知代价（立项时就要摆上桌，不要到实施时才发现）

1. **属 DDL 变更** ⇒ 需要一份**受治理的 migration**；
2. **会让 P6b 形状闸门的 `schema.sql` md5 锚失配** ⇒ 必须**重新生成整份闸门文件**；
3. 落地前必须先确认**所有写入方都已显式给值** —— 本片已把仓内 10 处补齐（`checked=12`，
   0 处缺字段），⇒ **本片是 TS1-R1 的前置**，次序不能反：
   先补齐、再 fail-closed，否则改完当场炸。

## 建议的验收判据（写 spec 时细化）

- 造一条**漏给字段**的 `INSERT`，期望 **PostgreSQL 直接报错**（不是拿到默认值）；
- 造一条**表名来自变量**的漏填写入（文本守卫的已知边界 1–3），期望**同样被 DB 拒**
  —— 这条才是 TS1-R1 相对文本守卫的**增量价值**证明；
- 现有 12 处 `INSERT` 全部仍能正常写入（正向对照，防止改成恒拒）。
