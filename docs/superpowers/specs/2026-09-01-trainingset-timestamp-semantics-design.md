## 1. 问题（全部实测，非推演）

### 1.1 仓库里有两套 `datetime` 标注约定，从未对过账

| 周期 | `datetime` 标的是 | 证据 |
|---|---|---|
| `3m` / `15m` / `60m` | **收盘时刻** | 实测 60m = `10:30 / 11:30 / 14:00 / 15:00`；15m 首根 `09:45`；3m 首根 `09:33`（A 股 9:30 开盘）。重采样器函数签名即 `_bucket_label_minute(close_min, minutes)` —— **有意为之** |
| `daily` | 该交易日 `00:00` | `2026-04-30 00:00` |
| `weekly` | 该周**首个交易日** `00:00` | `2026-04-27` / `2026-02-24`（春节后首个交易日，非周一） |
| `monthly` | 该月**首个交易日** `00:00` | `2026-04-01 / 03-02 / 02-02` |

而 `assign_global_indices`（`backend/generate_training_sets.py:273-296`）的注释写着「覆盖区间 **`[开盘, 下一根开盘)`**」，对**所有**周期一律 `upper = 下一根 datetime − 1`。

⭐ **切分本身没错**：实测每天 `3m` 80 根 / `15m` 16 根 / `60m` 4 根，与 A 股 4 小时交易严丝合缝，午休已处理。**缺的只是这两套约定的对账。**

⭐ **日线及以上标 `00:00` 不是缺陷**：`00:00` 到当日首根 3m（`09:33`）之间无数据，故按「下一根开始 − 1」反算与「上一交易日 15:00 收盘」**逐点一致**。

### 1.2 后果一：日内周期的「形成时刻」晚一整个周期

实测 `000001.SZ_1756656000`，2026-04-20 四根 60m：

| 标 | 库里编号指向 3m 收于 | 它其实形成于 | 差 |
|---|---|---|---|
| 10:30 | 11:27 | **10:30** | 19 根 |
| 11:30 | 13:57 | **11:30** | 19 根 |
| 14:00 | 14:57 | **14:00** | 19 根 |
| 15:00 | **次日 10:27** | **15:00** | 19 根 |

逐根新旧对照（同一产物）：

| 周期 | 旧值 − 新值 分布 | 说明 |
|---|---|---|
| `15m` | **4**（2573 根）· 3（1 根）· 0（120 根） | 一根 15m 含 **5** 根 3m ⇒ 常规位移 **4** |
| `60m` | **19**（643 根）· 8（1 根）· 0（142 根） | 一根 60m 含 20 根 3m |
| `3m` | 全 0 | 两式同解 |

⚠️ **位移不是常量**：0 的那些是轴前 K 线（新旧都 clamp 到 0），`3`／`8` 落在轴边界，末根可能不动。**迁移与测试一律不得依赖位移常量，必须逐根重算。**

### 1.3 后果二：开盘侧用「下一根」当边界，而周线序列**允许有洞**

`select_period_window`（`:100-104`）**故意删掉**跨训练起点 / 跨 `after_end` 的那根周线（既有测试 `test_generate_training_sets.py:118-129` 起点设**周三**、明写 `assert "0629" not in got`）。被删那一周的 3m 数据**在轴上是存在的** ⇒ 洞之前那根周线会被判成「在洞里的某个时刻才完成」。

**实测**：三个真实产物里，「按下一根」与「按真实日历周期」不同的根数 ——

| 周期 | 000001.SZ_1756656000 | 600519.SH_1762099200 | 000001.SZ_1762099200 |
|---|---|---|---|
| `daily` | 0 | 0 | 0 |
| **`weekly`** | 0 | **1** | **1** |
| `monthly` | 0 | 0 | 0 |

⇒ **三个包里两个已经带着这个错误**（这 3 个包起点恰好都是周一，未触发「删跨界周」；错的是别处的周历边界）。

### 1.4 为什么藏到今天

仓库里**没有任何一条测试把「生成器真实产物」喂给「App 读取器」**。两侧各自的测试都绿，缝在中间无人负责。

## 2. 契约变更

### 2.1 每周期 `datetime` 语义（**本次新立**）

> `klines.datetime` 的语义**按周期区分**，任何依赖它的计算**必须**显式区分：
> - **`3m` / `15m` / `60m`**：该 K 线的**收盘（结束）时刻**；覆盖区间 `(上一根 datetime, 本根 datetime]`。
> - **`daily` / `weekly` / `monthly`**：该 K 线所属周期的**开始侧标识**；覆盖区间 = **该日历周期本身**。

### 2.2 `end_global_index` 的定义

> 含义 = 「这根 K 线在全局 3 分钟轴上**于第几刻形成（完成）**」。逐根精确等于：
>
> ```
> 收盘标注（3m / 15m / 60m）：  upper = 本根 datetime
> 开盘侧标注（daily/weekly/monthly）：
>     upper = period_end(本根 datetime, 周期)      ← 本根所属【日历周期】的结束时刻
>             daily   → 该交易日 23:59:59
>             weekly  → 该 ISO 周的周日 23:59:59
>             monthly → 该自然月最后一刻
>             （一律 Asia/Shanghai）
>
> derived = clamp( bisect_right(m3_datetimes, upper) − 1 , 0 , n3 − 1 )
> end_global_index == derived
> ```
>
> ⛔ **开盘侧不得用「下一根 − 1」**：该序列**允许有洞**（§1.3）。
>
> `.m3` 自身另有不变量（`global_index == end_global_index == 数组下标`，从 0 起严格递增无缺口），**本片不改**。

### 2.3 产物代际标识

> 迁移前后的产物**互不可读**（同一张表、同一组列，但 `end_global_index` 取值语义变了）⇒ 属**两代**，`PRAGMA user_version` **`1` → `2`**。
>
> 依据是冻结 schema 文件自己写的：`training_set_schema_v1.sql:3` ——「schema 变更时 bump `user_version`，旧 version reader 直接拒收」。
>
> ⚠️ **判断依据是「新旧产物能否互读」，不是「列有没有变」。**

## 3. 改动清单（本片）

### 3.1 抽出 `period_end(datetime, period)` 纯函数

放在生成器侧，**供本片的索引计算与迁移脚本共用**。切片二的读取端校验将 import 或按同一定义实现 —— ⚠️ **两侧各写一份正是本次整个缺陷的成因**，切片二必须复用而非重写。

- 时区**必须**用 **tz 数据库**的 `Asia/Shanghai`，⛔ 不得写成固定 `+08:00`。
  ⚠️ **当前数据下两者结果完全相同**（中国 1986–1991 有夏令时，实测 `1991-04-30 23:59:59 Asia/Shanghai` 的偏移是 **+09:00**；而 monthly 序列虽回溯到 1991-01-05，那些 bar 全在 3m 轴起点之前 ⇒ 两种实现都 clamp 到 0）⇒ **没有任何测试能抓住这个差异**。⛔ 因此这条**只写进规矩、不设机械守卫** —— 按 §7 自检的总则，一条恒绿的守卫不该存在（Opus 评审 R13-M2）。
- ⭐ **`period_end(weekly)` 必须复用仓内已有的 `_week_end_date`**（`generate_training_sets.py:96-98`，`d + timedelta(days=(6 - d.weekday()))`）。
  ⛔ **但它现在是 `select_period_window` 函数体内的【嵌套闭包】（`:96`），作用域不可达 ⇒ 直接写「复用」是兑现不了的**（Kimi 评审 K1-③）：实施者照字面执行会发现无从复用，要么自己补一次未授权的提取重构、要么另抄一份公式 —— **正好复活本条自己警告的「两份实现漂移」**。
  ⇒ **本片必须先把 `_week_end_date` 提取到模块级**（纯搬移，不改行为），再由 `period_end(weekly)` 与 `select_period_window` 共用；这一步已列进 §3.3 改动清单。
  ⚠️ **仓内此刻已经有第三份**（Opus 评审 R13-M2）：本节盯的是「生成器侧 vs App 侧」两份，可 `_week_end_date` 与 `period_end(weekly)` 算的是**同一件事**（该周周日），而前者决定**哪一根 weekly 进窗口**（`:100-104`）、后者决定**索引怎么算**。两者若日后分叉，得到的正是「**窗口按 A 切、索引按 B 算**」—— 与 §1.4 描述的「两侧各自的测试都绿、缝在中间无人负责」是同一个形状。
  · **实测两者现在完全一致**：真实产物 153 根 weekly（含 **11 根首日非周一**，如春节后 `2025-02-05 Wed`、国庆后 `2025-10-09 Thu`；含 **2 根跨年周** `2024-12-30` / `2025-12-29`）零分歧。
  · ⛔ **不要用 `isocalendar()` 的周数反推周日**：`date(2024,12,30).isocalendar()` 的 ISO **年是 2025**（实测），任何以 `(iso_year, iso_week)` 为键的写法都会在那 2 个跨年周出错。§2.2 写「ISO 周」只是给语义命名，**实现一律用 `6 - weekday()`**。
- 周期→标注约定用**显式常量表**（`_CLOSE_LABELLED = {"3m","15m","60m"}`），**不得**用「周期名里有没有 `m`」之类的字符串把戏。

### 3.2 `assign_global_indices()` 按语义分流

`:288-292` 改为 §2.2 的两分支。其余（`bisect_right` / `clamp` / `global_index` 仅 `3m` 赋值）**一律不动**。

     P11/P15 的模板各只有**一张**期望表，而 P11b 的三步（旧闸 → UPDATE → 新复核）**要求两套**
     ⇒ 照字面执行会得到一个只有一套期望的脚本。承重判据仍**逐条保留**（`\set ON_ERROR_STOP on`
     / `BEGIN` / `LOCK TABLE` / 双向 `EXCEPT ALL` / 按主键取 id / `COMMIT`）
   ⭐ **模板 = 现有两份 SQL 逐字**，⛔ **只替换 `p11_expected` / `p15_expected` 的
      那 3 行 `VALUES`**，其余**一个字符都不动**（Opus 评审 R12-M1）
      —— 必须原样保留的承重判据：`\set ON_ERROR_STOP on`、`BEGIN` / `LOCK TABLE …
      ACCESS EXCLUSIVE`、全部 `DO $$ … RAISE EXCEPTION`（含 P11 的**空表前置**与
      `n_bad_state` 检查）、**双向 `EXCEPT ALL`**、P15 的**按主键取 id**（⛔ 不用 CRC32
      当身份）、`COMMIT`
      ⚠️ **`\set ON_ERROR_STOP on` 最要命**：psql **默认遇错继续执行** ⇒ 模板化时漏掉它，
      `RAISE EXCEPTION` 抛出后后面的 `COMMIT;` **照样执行**、脚本**退出码仍为 0**
      ⇒ 空表前置与七元组比对全部形同虚设，而它看起来是成功的（本仓「假绿家族」典型）
   ⛔ 指纹与七元组一律由清单生成，不得人工填写
   · ⭐ **结构断言**：生成后与模板 diff，断言**差异只落在那 3 行 `VALUES` 上**
   · 仓库副本与将要部署的副本【逐字节一致】（生成后 diff 断言）

R4 部署（文件侧）
   · NAS 上的旧 training-sets 目录【改名归档】（⛔ 不是删除），新目录就位
   · ⭐ **落盘**：新目录本身与其父目录逐一 `fsync`；旧目录改名后同样 `fsync` 父目录
     ⛔ **rename 的原子性不等于目录项已持久**（Opus 评审 R12-C3）
   · 按 runbook P7 的既有判据【重算 CRC32】并与 R2 的清单比对
   · 同步更新 P7 的来源目录（handoff）与 $DIR/sql/ 下的**三份**部署副本 SQL（P11 / P15 / **P11b**）

R5 写库：⛔ **不是 P10 → P11**（Kimi 评审 K2-high 打回），而是**新的 P11b：按旧七元组
   身份闸，只 UPDATE 那 3 行的 `content_hash` 与 `schema_version` 两列**
   ⚠️ **为什么不能用 P10**：P10 **只删 `SMOKE-A`/`SMOKE-B` 烟测行**，并且**表里存在任何
      非烟测行就 `RAISE EXCEPTION`、一行不动**（`…-p10-cleanup-smoke-rows.sql:39-53`）。
      runbook 自己的实测注记白纸黑字写着「**只有 3 行真数据 → 拒绝，3 行一行不少**」。
      而生产库里正是那 3 行真数据 ⇒ **P10 必然拒绝、P11 的空表前置永远不满足**。
      全仓也不存在任何「清空含真数据的表」的既有路径（`DELETE FROM training_sets` 只在
      P10 的烟测行限定删除处出现一次）。⇒ 上一版「走 P10 → P11 这条既有路径」不可执行。
   ⭐ **而且根本不需要删表**：R2 ⓑ 已把起点钉成与旧三个**完全相同** ⇒ 文件名
      `<code>_<start>.zip` 不变 ⇒ `file_path` 不变；`stock_code` / `stock_name` /
      `start_datetime` / `end_datetime` 也都不变。**真正变的只有 `content_hash` 与
      `schema_version` 两列**，且行 `id` 与生命周期状态原样保留。
   · P11b 由 R3 一并生成 —— ⛔ **模板照 P15 的形状、期望表两张**
     （`p11b_old_expected` / `p11b_new_expected`）；⛔ **不适用**「逐字复用、只换期望值」
     那条 —— 它只对 P11 / P15 成立（理由见 R3：那两份模板各只有**一张**期望表，
     而 P11b 的三步要求**两套**）：
     ```
     \set ON_ERROR_STOP on
     BEGIN;  LOCK TABLE training_sets IN ACCESS EXCLUSIVE MODE;
     身份闸：按【旧的】完整七元组与表内容双向 EXCEPT ALL；不符 → 一行不动、整体回滚
     UPDATE：按身份闸精确匹配出的那 3 个 id，只改 content_hash + schema_version
             ⛔ 不动 status / lease 三列（生命周期归 P15 管）
     复核：再按【新的】完整七元组双向 EXCEPT ALL；不符 → 回滚
     COMMIT;
     ```
   · ⭐ **整步在一个事务里** ⇒ **真正的**事务失败 = 整体回滚、库一行未动
     ⛔ **但 P11b 不幂等，恢复前必须先分诊** —— 见下「**P11b 没打印成功**」那条的三态判读；
        ⛔ **不得无条件重跑**（成功一次后表里已是新七元组，再跑身份闸必然失配，
        而错误信息看起来像「数据被人动过」）
   · P11 / P15 仍要按 R3 重新生成（它们是**干净重部署**与**生命周期复位**的权威脚本），
     只是**本次重建不执行 P11**

R6 收口闸（全绿才算成功；⛔ 未全绿不得启回 api、更不得开对外入口）—— 本片称【收口闸清单】
   ① 3 个包的 CRC32 == R2 清单的【新值】
   ② 每个包内 PRAGMA user_version == 2，且成员名为 <code>_<start>.db
   ③ training_sets 恰好 3 行、完整七元组与 R2 清单的【新值】【双向 EXCEPT ALL】相等
   ④ 全仓 grep 旧指纹（白名单外）命中 0
   ⑤ 部署副本与仓库副本的 **P11 / P15 / P11b 三份**逐字节一致

R7 ⛔ 切片一到此结束：api 保持停止、scheduler 与生成器 CLI 保持停止、对外入口不开
```

⭐ **崩溃与恢复处方**（每一种都有已定义的出路；⛔ 此处不写条数 —— 它漂过一次了）：

⭐ **本块是【出事时照着做】的权威处方**；§7「**崩溃恢复演练**」是它的**验收演练**，按名引用本块、⛔ 不复述内容。⛔ **短名里不放数字** —— 数字会漂、名字不会（这句是消重时被删掉的，R18-M3 打回后还回本处；删掉它之后当场就造出了一个含数字的锚点名，已改名去掉数字）。

· P11b 没打印成功  → ⛔ **先分诊，再处置**（Opus 评审 R15-C2）：P11b **不幂等** ——
                       身份闸按【旧】七元组，成功一次后表里已是【新】七元组，再跑必然失配。
                       而「事务失败」与「已提交但没看到结果」（ssh 断线 / 终端被杀 / 掉电）

                       ⭐ 比上一版（P10 已提交 / P11 失败 ⇒ 表为空）**严格更安全**：
                       不存在「表被清空、App 拿不到东西」这个中间态

                       ⇒ 不需要备份四态、不需要阶段清单
· R5 提交【之后掉电】 → ⭐ **演练方法**：用「**R4 时故意不 fsync 新目录及其父目录，
                       再在 P11b `COMMIT` 之后立刻断电 / 强制重启**」这一等价手段模拟。
                       ⛔ **只 kill 进程不等价** —— 它不触发本形态唯一关注的「目录项未落盘」。
                       （⚠️ 这句是消重时从 §7 删掉的**独占内容**，R18-C1 打回后补回本块）
                       PG 默认 synchronous_commit=on，WAL 必落盘；而 NAS 上两次目录
                       rename 的**目录项未必落盘** ⇒ 可能出现「库是新指纹、文件还是旧目录
                       或半截状态」。恢复 = 重启后先重跑 R6 收口闸①②③；任一不符 ⇒ 回到
                       R4 重新就位文件（R2 的字节确定性保证包可重得）
                       ⛔ **回到 R4 之后不得顺势跑 R5**（Opus 评审 R17-C2）——
                          本形态的前提就是**库侧已经是新的**。先按上面
                          「P11b 没打印成功」那条的三态判读确认库侧状态：
                            · 判为【新】⇒ 文件就位后**直接进 R6 收口闸**，⛔ 不重跑 P11b
                            · 判为【旧】⇒ 才走 R5
                       ⛔ 收口闸未全绿不得启回 api

**静默期的正确做法**（codex S1-R1-F1 打回后订正）：

⚠️ **原文写「先 P16 关入口」是不成立的**，两个理由：

2. 就算关成功了，**关 tailscale 入口挡不住两类流量** —— 已被接受的在途请求，以及 **NAS 本机直连 `127.0.0.1:8010`** 的访问。

⚠️ **只停 `api` 还不够**（codex S1-R2-F1）：本仓还有**独立于 API 的写入方** —— `backend/app/scheduler_main.py`（`build_generate_batch`）与生成器 CLI，**都能在 API 不在的情况下产出 zip 并往 `training_sets` 插行**。

```

           持住 = 任何生成路径都进不来，且这是【可证明】的互斥而非口头约束）
        ⛔ 全程【只取一次、只放一次】，⛔ 中途不得重复取

             ⓒ本机 curl 连不上  ⓓ锁已持有

⛔ **切片一结束时 `api` 必须保持停止**（codex S1-R2-F4）：此刻库存已是第 2 代，而 App 仍拒 `.db` 与 `user_version = 2`。启回 api ⇒ 若持久化的 tailscale serve 配置没被成功清掉，**不兼容的客户端会立刻恢复访问、预占库存、然后在确认前失败**，把库存烧成 `reserved`。

⛔ **`scheduler` 与生成器 CLI 同样要停到切片二之后**（codex S1-R5-F3）：

- `backend/app/scheduler.py:5` 写明其职责是「`unsent<=40` 就调 `generate_batch` **补到 100**」⇒ 一启动就会**批量补货**；

⇒ 启回 scheduler = 往库里塞进**几十行 schema-v2 但下载必 404** 的记录，**且它们全在收口闸校验的 3 行之外**。

⚠️ 这条与「`file_path` 宿主/容器语义未统一」这个既有残留是同一个根（PR-2 已明写、本次不修）。**在那个残留解决之前，任何自动补货都必须保持关闭**，并把「scheduler 与 CLI 仍处于停止」写进本片的最终验收。

⭐ 这比「修好 `expose.sh` 再重建」更强：停容器**同时**掐断 tailnet 与本机两条路径，且**不依赖任何待修缺陷**。`expose.sh` 的锁缺陷仍是独立残留（§6.4），但**不再是本片的前置阻塞**。

1. 用**生产顶层装配函数** `assemble_from_windows(...)` 从一组合成 bar 数据产出一个**小训练组**，提交进仓库作为**跨端共用 fixture**；

2. 该 fixture 的形态必须**同时覆盖本片三类特征**：① 至少一个非 m3 周期有 ≥2 根落在 `end_global_index = 0`（轴前历史）；② 含跨**午休**与跨**日**的日内边界；③ 含一处**被删的跨界周**（起点设为周中）。
3. 断言：**压缩包清单**（恰好 1 个成员、后缀 ∈ {`.sqlite`,`.db`}、无 sidecar）+ **逐周期索引向量**与**独立人工推算**的期望值逐根相等。
   ⭐ **fixture 用【压缩交易日】即可**（Opus 评审 R13-M1）：例如每个交易日只放 6 根 `3m`（上午 2 根 + 午休缺口 + 上午末 2 根 + 下午 2 根），照样覆盖「跨午休」与「跨日」两条边界。
   依据：`assemble_from_windows`（`:375-411`）**不校验每日根数** —— `per_day_intraday_complete` 只在 `build_training_windows:200` 里被调。⇒ 手写期望值控制在**几十个**量级。
   ⛔ **若按生产形态做**（≥2 个交易日 ⇒ `3m` ≥160 根），期望值会到 **~210 个字面量** —— 那时「期望值必须手写」在实践上必然退化成「跑一遍抄回来」，B18 要防的东西就从门里溜进来了。
   ⚪ **行序不需要显式 `ORDER BY`**：`build_training_set_sqlite:350-351` 按 `PERIODS` 固定次序插入、`klines.id` 是 `AUTOINCREMENT` ⇒ 无 `ORDER BY` 的 `SELECT` 返回 rowid 序 = 插入序，两次构建必然一致（按 rowid 序比对即可）。
   ⚠️ **期望值必须手写**，不得由「跑一遍生成器」得出 —— 否则生产者与校验者可以**一起用错公式而全绿**，那正是缺陷藏住的机制。

4. ⭐ **CI 每次都要把「当前生成器的输出」与「已提交的 fixture」对齐**（codex S1-R4-F1）：

   ```
   每次 CI：重新调 assemble_from_windows(...) 产出一份 → 与仓库里那份 fixture 比对
            比【逻辑内容】：压缩包成员清单 + user_version + 每张表的全部行
            ⛔ 不比 zip 原始字节（zipfile 嵌 mtime，跨机跨时不可复现，比字节必然假红）
   ```

   ⚠️ **缺了这条，§1.4 那道缝会原样复活**：生成器日后改了序列化 / DDL / 版本，**生产者侧的测试对着新鲜输出照样绿**，而 App 侧对着**陈旧的已提交 fixture** 也照样绿 —— 两边都绿，缺陷照旧静默。

**移交切片二**：必须用**这一个 fixture**（不是自己另造一份）跑通真实的解压 → 打开 → 读取链路。⇒ 三方（当前生成器输出 / 已提交 fixture / App 读取链路）钉在同一件产物上，任何一方漂移都会红。

**正向对照（必配，防「全是拒了」的套件掩盖恒抛守卫）**：健康输入必须被放行 —— ① `daily`/`monthly`/`3m` 逐根不变；② **重建出的** 3 个包内容自洽（`user_version = 2`、索引逐根等于 §2.2 反算值）；③ **R2 连跑两次得到逐字节相同的一批包**（⛔ 不是「幂等空操作」—— 那是已废方案的概念）；④ 上述 fixture 通过全部断言。

⚠️ **B1 与 B3 必须互不掩盖**：另配一次 **B1+B3 组合变异**，确认组合下仍有测试红并记录是哪一条。
