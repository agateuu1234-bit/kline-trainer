## 1. 问题（全部实测，非推演）

### 1.1 仓库里有两套 `datetime` 标注约定，从未对过账

| 周期 | `datetime` 标的是 | 证据 |
|---|---|---|
| `3m` / `15m` / `60m` | **收盘时刻** | 实测 60m = `10:30 / 11:30 / 14:00 / 15:00`；15m 首根 `09:45`；3m 首根 `09:33`（A 股 9:30 开盘）。重采样器函数签名即 `_bucket_label_minute(close_min, minutes)` —— **有意为之** |
| `daily` | 该交易日 `00:00` | `2026-04-30 00:00` |
| `weekly` | 该周**首个交易日** `00:00` | `2026-04-27` / `2026-02-24`（春节后首个交易日，非周一） |
| `monthly` | 该月**首个交易日** `00:00` | `2026-04-01 / 03-02 / 02-02` |

而 `assign_global_indices`（`backend/generate_training_sets.py:273-296`）的注释写着「覆盖区间 **`[开盘, 下一根开盘)`**」，对**所有**周期一律 `upper = 下一根 datetime − 1`。

⭐ **切分本身没错**：实测每天 `3m` 80 根 / `15m` 16 根 / `60m` 4 根，与 A 股 4 小时交易严丝合缝，午休已处理。**缺的只是这两套约定的对账。**

⭐ **日线及以上标 `00:00` 不是缺陷**：`00:00` 到当日首根 3m（`09:33`）之间无数据，故按「下一根开始 − 1」反算与「上一交易日 15:00 收盘」**逐点一致**。

### 1.2 后果一：日内周期的「形成时刻」晚一整个周期

实测 `000001.SZ_1756656000`，2026-04-20 四根 60m：

| 标 | 库里编号指向 3m 收于 | 它其实形成于 | 差 |
|---|---|---|---|
| 10:30 | 11:27 | **10:30** | 19 根 |
| 11:30 | 13:57 | **11:30** | 19 根 |
| 14:00 | 14:57 | **14:00** | 19 根 |
| 15:00 | **次日 10:27** | **15:00** | 19 根 |

逐根新旧对照（同一产物）：

| 周期 | 旧值 − 新值 分布 | 说明 |
|---|---|---|
| `15m` | **4**（2573 根）· 3（1 根）· 0（120 根） | 一根 15m 含 **5** 根 3m ⇒ 常规位移 **4** |
| `60m` | **19**（643 根）· 8（1 根）· 0（142 根） | 一根 60m 含 20 根 3m |
| `3m` | 全 0 | 两式同解 |

⚠️ **位移不是常量**：0 的那些是轴前 K 线（新旧都 clamp 到 0），`3`／`8` 落在轴边界，末根可能不动。**迁移与测试一律不得依赖位移常量，必须逐根重算。**

### 1.3 后果二：开盘侧用「下一根」当边界，而周线序列**允许有洞**

`select_period_window`（`:100-104`）**故意删掉**跨训练起点 / 跨 `after_end` 的那根周线（既有测试 `test_generate_training_sets.py:118-129` 起点设**周三**、明写 `assert "0629" not in got`）。被删那一周的 3m 数据**在轴上是存在的** ⇒ 洞之前那根周线会被判成「在洞里的某个时刻才完成」。

**实测**：三个真实产物里，「按下一根」与「按真实日历周期」不同的根数 ——

| 周期 | 000001.SZ_1756656000 | 600519.SH_1762099200 | 000001.SZ_1762099200 |
|---|---|---|---|
| `daily` | 0 | 0 | 0 |
| **`weekly`** | 0 | **1** | **1** |
| `monthly` | 0 | 0 | 0 |

⇒ **三个包里两个已经带着这个错误**（这 3 个包起点恰好都是周一，未触发「删跨界周」；错的是别处的周历边界）。

### 1.4 为什么藏到今天

仓库里**没有任何一条测试把「生成器真实产物」喂给「App 读取器」**。两侧各自的测试都绿，缝在中间无人负责。

## 2. 契约变更

### 2.1 每周期 `datetime` 语义（**本次新立**）

> `klines.datetime` 的语义**按周期区分**，任何依赖它的计算**必须**显式区分：
> - **`3m` / `15m` / `60m`**：该 K 线的**收盘（结束）时刻**；覆盖区间 `(上一根 datetime, 本根 datetime]`。
> - **`daily` / `weekly` / `monthly`**：该 K 线所属周期的**开始侧标识**；覆盖区间 = **该日历周期本身**。

### 2.2 `end_global_index` 的定义

> 含义 = 「这根 K 线在全局 3 分钟轴上**于第几刻形成（完成）**」。逐根精确等于：
>
> ```
> 收盘标注（3m / 15m / 60m）：  upper = 本根 datetime
> 开盘侧标注（daily/weekly/monthly）：
>     upper = period_end(本根 datetime, 周期)      ← 本根所属【日历周期】的结束时刻
>             daily   → 该交易日 23:59:59
>             weekly  → 该 ISO 周的周日 23:59:59
>             monthly → 该自然月最后一刻
>             （一律 Asia/Shanghai）
>
> derived = clamp( bisect_right(m3_datetimes, upper) − 1 , 0 , n3 − 1 )
> end_global_index == derived
> ```
>
> ⛔ **开盘侧不得用「下一根 − 1」**：该序列**允许有洞**（§1.3）。
>
> `.m3` 自身另有不变量（`global_index == end_global_index == 数组下标`，从 0 起严格递增无缺口），**本片不改**。

### 2.3 产物代际标识

> 迁移前后的产物**互不可读**（同一张表、同一组列，但 `end_global_index` 取值语义变了）⇒ 属**两代**，`PRAGMA user_version` **`1` → `2`**。
>
> 依据是冻结 schema 文件自己写的：`training_set_schema_v1.sql:3` ——「schema 变更时 bump `user_version`，旧 version reader 直接拒收」。
>
> ⚠️ **判断依据是「新旧产物能否互读」，不是「列有没有变」。**

| Mac 本地 `~/qmt_trial_out/` | 3 个 zip（若仍在；`:135` 把它写成了判据） |

**执行协议 —— 全量备份 + 校验 + 失败重做（⚠️ 刻意**不**做「断点续做」）**：

```
0 静默：见下「静默期」——【所有写入方】停掉并持锁
1 备份：9 个目标全部备份（6 个 zip → .bak；PG 3 行 → pg_dump 到文件）
        备份完成后校验备份可用（zip 可解、dump 里有 3 行）
2 执行：暂存目录产出新包 → 逐个自校验 → 替换 6 个文件 → PG 3 行单事务更新
3 校验：9 个目标逐一比对期望新指纹 + schema_version；全对才算成功
4 失败/中断：【全量还原】6 个文件 + PG 三行（从 dump 恢复），然后【从头重做】
```

⚠️ **为什么不写「准备/提交/恢复三段状态机」**（上一版是那么写的，codex S1-R2-F2 打回其不完备 —— 缺 staged 文件与目录的 fsync 次序、缺「9 个都新了但最终标记没写」这一支、缺 PG 的反向回滚）：

**补齐那套状态机是错的方向。** 这是一次**一次性人工操作**，作用于 **6 个文件 + 3 行**，且**全程没有任何并发写入方**（见静默期）。在这种前提下，「**全量还原 + 从头重做**」在任何中断点都是安全且完备的 —— 它不需要知道自己中断在哪一步，因此：

- 不需要 staged 文件 / 备份 / 父目录的 fsync 次序（重做会覆盖一切）；
- 不存在「所有目标已新、最终标记未写」这种要靠标记消歧的状态（**校验步骤本身就是标记**）；
- 不需要为 PG 写反向事务（`pg_dump` 还原即可）。

⇒ **用「可完整还原 + 可重复执行」换掉「可断点续做」**，状态空间从「每目标 × 各阶段」塌缩成「成功 / 未成功」两态。⛔ 实施时**不得**为了「省时间」加断点续做 —— 那会把上面这些前提全部重新引入。

**必配故障注入**：在第 2 步的**每个替换点之后**各中断一次（含 PG 事务提交前/后），断言：还原后 9 个目标**全部回到旧代**，且重做一次后**全部到达新代**。

**其它硬要求**：

| 要求 | 做法 | 不做会怎样 |
|---|---|---|
| **静默期（改法见下）** | **停掉 `api` 容器**，而不是只关 tailscale 入口 | 并发下载读到「旧元数据 + 新字节」，撞完整性校验；已被接受的请求与 **NAS 本机直连**的流量，关 serve 根本挡不住 |
| 确定性压缩 | 固定 `ZipInfo.date_time` 与压缩参数，使同一输入恒产出同一字节 | `zipfile` 默认嵌 mtime ⇒ **重跑一次 CRC 就变** ⇒ 迁移不幂等 |
| 回滚副本 | 原包留 `.bak`，**直到切片二真机验收通过**才删 | 原始数据只此一份，出错无退路 |

**静默期的正确做法**（codex S1-R1-F1 打回后订正）：

⚠️ **原文写「先 P16 关入口」是不成立的**，两个理由：
1. 本仓已实测三次：`expose.sh` 的看门狗**继承了 flock**，窗口期内 `close` 恒 `LOCK_TIMEOUT`、**关不掉**（母 spec 已记录，我却同时把它列为「范围外」又依赖它）；
2. 就算关成功了，**关 tailscale 入口挡不住两类流量** —— 已被接受的在途请求，以及 **NAS 本机直连 `127.0.0.1:8010`** 的访问。

**改为**：

⚠️ **只停 `api` 还不够**（codex S1-R2-F1）：本仓还有**独立于 API 的写入方** —— `backend/app/scheduler_main.py`（`build_generate_batch`）与生成器 CLI，**都能在 API 不在的情况下产出 zip 并往 `training_sets` 插行**。它们若在迁移中途跑起来，9 目标清单当场过期，还会产出**旧代契约**的新包。

```
迁移前：① docker compose stop api
        ② 停掉 / 确认没有 scheduler 与生成器 CLI 在跑
        ③ 【整个迁移期间持有 B2_GENERATION_LOCK_KEY】（生成器自己就用这把锁，
           持住 = 任何生成路径都进不来，且这是【可证明】的互斥而非口头约束）
        验证 ⓐ`docker compose ps` 无 api  ⓑ宿主机 8010 无监听
             ⓒ本机 curl 连不上  ⓓ锁已持有  ⓔ`training_sets` 恰好 3 行且 id 与清单一致
迁移后：9 目标收敛校验通过 → 释放锁
        ⛔ 【不启回 api】—— 见下
```

⛔ **切片一结束时 `api` 必须保持停止**（codex S1-R2-F4；上一版我写了「校验通过 → `start api`」，与 §8「两片之间不得启回 api」**自相矛盾**）：此刻库存已是第 2 代，而 App 仍拒 `.db` 与 `user_version = 2`。启回 api ⇒ 若持久化的 tailscale serve 配置没被成功清掉，**不兼容的客户端会立刻恢复访问、预占库存、然后在确认前失败**，把库存烧成 `reserved`。

⇒ **`api` 与对外入口一律等到切片二部署完、且共用 fixture 的端到端测试通过之后才启回。**

⚠️ **数据库清单校验要做两次**（暂存前、提交前各一次）：确认 `training_sets` 仍是那 3 行、id 未变 —— 防止「静默期开始后仍有人插了行」这种情况被静默带过。

⭐ 这比「修好 `expose.sh` 再迁移」更强：停容器**同时**掐断 tailnet 与本机两条路径，且**不依赖任何待修缺陷**。`expose.sh` 的锁缺陷仍是独立残留（§6.4），但**不再是本片的前置阻塞**。

⛔ **收口闸**：**9 个目标全部收敛到同一代之前，不得启回 `api`、更不得开对外入口**。写成脚本里的显式检查，不是嘱咐。

### 4.1 ⭐ 跨端接缝的**生产者半边**（本片必须交付；codex S1-R1-F2）

§1.4 把「没有任何测试把生成器真实产物喂给 App 读取器」认定为两个缺陷共同的藏身之处。母 spec 归档后，**若本片只做后端变异 + 产物自洽校验，两侧的静态 fixture 仍会各自漂移，同一类回归照样静默。**

**本片交付**：

1. 用**生产顶层装配函数** `assemble_from_windows(...)` 从一组合成 bar 数据产出一个**小训练组**，提交进仓库作为**跨端共用 fixture**；
   ⚠️ **不得**自己串调 `assign_global_indices` → `build_training_set_sqlite` → `zip_and_hash`：真正决定 zip 成员名的是 `assemble_from_windows:403`（`f"{fname}.db"`），绕过它的测试对该行**零敏感**。
2. 该 fixture 的形态必须**同时覆盖本片三类特征**：① 至少一个非 m3 周期有 ≥2 根落在 `end_global_index = 0`（轴前历史）；② 含跨**午休**与跨**日**的日内边界；③ 含一处**被删的跨界周**（起点设为周中）。
3. 断言：**压缩包清单**（恰好 1 个成员、后缀 ∈ {`.sqlite`,`.db`}、无 sidecar）+ **逐周期索引向量**与**独立人工推算**的期望值逐根相等。
   ⚠️ **期望值必须手写**，不得由「跑一遍生成器」得出 —— 否则生产者与校验者可以**一起用错公式而全绿**，那正是缺陷藏住的机制。

**移交切片二**：必须用**这一个 fixture**（不是自己另造一份）跑通真实的解压 → 打开 → 读取链路。⇒ 两侧钉在同一件产物上，无法各自漂移。

**正向对照（必配，防「全是拒了」的套件掩盖恒抛守卫）**：健康输入必须被放行 —— ① `daily`/`monthly`/`3m` 逐根不变；② 迁移后的 3 个包内容自洽（`user_version = 2`、索引逐根等于 §2.2 反算值）；③ 迁移脚本对**已迁移**的包重跑一次为**幂等空操作**；④ 上述 fixture 通过全部断言。

⚠️ **B1 与 B3 必须互不掩盖**：另配一次 **B1+B3 组合变异**，确认组合下仍有测试红并记录是哪一条。

## 5. 兼容性

| 维度 | 结论 |
|---|---|
| 训练组 SQLite **表结构** | **不变**（无新列 / 无类型变化 / 无约束变化） |
| `PRAGMA user_version` / `TRAINING_SET_SCHEMA_VERSION` | **`1` → `2`**（§2.3：判据是「能否互读」） |
| 顶层 `CONTRACT_VERSION` | **`"1.13"` → `"1.14"`** |
| 既有 3 个产物 | **需就地迁移**（§3.4）；`content_hash` 会变 |
| 现有 App（未改） | 迁移后拿到 v2 包会报 `.versionMismatch` —— **不是回归**：它本来就消费不了任何真实训练组（zip 内是 `.db` 而它只认 `.sqlite`，属切片二） |
| QMT pilot 库 | 顶层 bump 后带 `"1.13"` 的既有库被闸 1 拒，需 `--reset`（4b 未投产，风险低） |

## 6. 明确不做（YAGNI / 归切片二）

1. **App 侧一切逻辑**：读取判据、缓存回收、进行中合成、面板联动 —— 归切片二；
2. **运行期能力协商 / 双格式过渡版 App**：未上架、单用户单机、次序可控，`user_version` 已足以给出可恢复信号。⚠️ **一旦上架必须重新评估**；
3. **`.db` / `.sqlite` 扩展名之争**：属切片二（改 App 接受 `.db`，user 已拍板）；
4. **`expose.sh` 看门狗继承 flock 导致窗口期内关不掉**：真缺陷，独立小 PR；
5. **App 后端地址不可配（PR-3 从未实施）**：`KlineTrainerApp.swift:18` 仍硬编码，独立 PR。

## 7. 验收判据

1. §4 全部 16 组变异 + 1 组组合逐条跑过，**每组写明红的是哪一条测试**；
2. 正向对照三条全部放行；
3. 后端 CI 全绿（Linux，**零 skip**）；iOS 侧因第 6/7/8 项常量改动而受影响的测试全绿；
4. 迁移完成后：9 个目标指纹一致、全仓 grep 旧指纹命中 0、来源闸通过、脚本重跑为幂等空操作；
5. `daily`/`monthly`/`3m` 逐根不变；`weekly` 实测变 **0 / 1 / 1** 根；`15m`/`60m` 按 §1.2 分布变化。

6. §4.1 的跨端 fixture 通过全部断言（清单形态 + 逐周期索引向量对**手写**期望值）；
7. 迁移期间**所有写入方**确实停着：`api` 停、scheduler/CLI 无进程、`B2_GENERATION_LOCK_KEY` 全程持有、`training_sets` 行数与 id 在暂存前与提交前**两次校验**一致；
8. **切片一交付时 `api` 仍处于停止状态**，对外入口未开（⛔ 启回归切片二，且须在其端到端测试通过之后）；
9. 故障注入：在每个替换点（含 PG 提交前/后）各中断一次，断言「全量还原后 9 目标全回旧代」且「重做一次后全到新代」。

⚠️ **本片交付后可以说**：「日内周期与周线的形成时刻已订正；既有 3 个产物已迁移至第 2 代」。
⛔ **不得说**：「手机能用了」「真实数据链路打通」—— App 侧一行未改，它仍消费不了任何训练组。

## 8. 与切片二的交接

**切片二（App 侧）必须承接的既定事实**（不得再自行推演）：

1. §2.1 的两套标注约定、§2.2 的索引定义 —— **契约已定**，切片二只负责**校验**产物是否符合；
2. `period_end` 必须**复用**本片的定义（§3.1），不得另写一份；
3. 产物代际 = `user_version 2`；App 侧 `TRAINING_SET_SCHEMA_VERSION` 与 `TrainingSessionCoordinator:1307` 那个**写死的字面量 `1`** 必须同步（⚠️ 该字面量的历史理由 residual E6a-R1 已过期）；
4. 迁移前的 v1 包会被版本闸拒为 `.versionMismatch`（**不是** `.dbCorrupted`）—— 切片二的「旧公式」测试必须用**合成档**（`user_version = 2` + 旧公式索引）才能走到索引校验那一层；
5. ⛔ **次序**：本片先落地并完成迁移，切片二才动；两片之间**不得启回 `api`、不得开对外入口**；
6. ⛔ **切片二必须把顶层 `CONTRACT_VERSION` 再 bump 到 `"1.15"`**（§3.3）：`1.14` 标识「产物已第 2 代、App 尚不支持」，`1.15` 标识「App 已支持」。两态共用一个版本号会让跨语言守卫在两种状态下都绿，标识失去意义；
7. **本片交付的跨端 fixture（§4.1）是切片二的必用输入** —— 切片二不得另造一份，否则两侧静态样本会各自漂移，缺陷 A/B 那类回归照旧静默。
