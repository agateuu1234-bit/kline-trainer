## 1. 问题（全部实测，非推演）

### 1.1 仓库里有两套 `datetime` 标注约定，从未对过账

| 周期 | `datetime` 标的是 | 证据 |
|---|---|---|
| `3m` / `15m` / `60m` | **收盘时刻** | 实测 60m = `10:30 / 11:30 / 14:00 / 15:00`；15m 首根 `09:45`；3m 首根 `09:33`（A 股 9:30 开盘）。重采样器函数签名即 `_bucket_label_minute(close_min, minutes)` —— **有意为之** |
| `daily` | 该交易日 `00:00` | `2026-04-30 00:00` |
| `weekly` | 该周**首个交易日** `00:00` | `2026-04-27` / `2026-02-24`（春节后首个交易日，非周一） |
| `monthly` | 该月**首个交易日** `00:00` | `2026-04-01 / 03-02 / 02-02` |

而 `assign_global_indices`（`backend/generate_training_sets.py:273-296`）的注释写着「覆盖区间 **`[开盘, 下一根开盘)`**」，对**所有**周期一律 `upper = 下一根 datetime − 1`。

⭐ **切分本身没错**：实测每天 `3m` 80 根 / `15m` 16 根 / `60m` 4 根，与 A 股 4 小时交易严丝合缝，午休已处理。**缺的只是这两套约定的对账。**

⭐ **日线及以上标 `00:00` 不是缺陷**：`00:00` 到当日首根 3m（`09:33`）之间无数据，故按「下一根开始 − 1」反算与「上一交易日 15:00 收盘」**逐点一致**。

### 1.2 后果一：日内周期的「形成时刻」晚一整个周期

实测 `000001.SZ_1756656000`，2026-04-20 四根 60m：

| 标 | 库里编号指向 3m 收于 | 它其实形成于 | 差 |
|---|---|---|---|
| 10:30 | 11:27 | **10:30** | 19 根 |
| 11:30 | 13:57 | **11:30** | 19 根 |
| 14:00 | 14:57 | **14:00** | 19 根 |
| 15:00 | **次日 10:27** | **15:00** | 19 根 |

逐根新旧对照（同一产物）：

| 周期 | 旧值 − 新值 分布 | 说明 |
|---|---|---|
| `15m` | **4**（2573 根）· 3（1 根）· 0（120 根） | 一根 15m 含 **5** 根 3m ⇒ 常规位移 **4** |
| `60m` | **19**（643 根）· 8（1 根）· 0（142 根） | 一根 60m 含 20 根 3m |
| `3m` | 全 0 | 两式同解 |

⚠️ **位移不是常量**：0 的那些是轴前 K 线（新旧都 clamp 到 0），`3`／`8` 落在轴边界，末根可能不动。**迁移与测试一律不得依赖位移常量，必须逐根重算。**

### 1.3 后果二：开盘侧用「下一根」当边界，而周线序列**允许有洞**

`select_period_window`（`:100-104`）**故意删掉**跨训练起点 / 跨 `after_end` 的那根周线（既有测试 `test_generate_training_sets.py:118-129` 起点设**周三**、明写 `assert "0629" not in got`）。被删那一周的 3m 数据**在轴上是存在的** ⇒ 洞之前那根周线会被判成「在洞里的某个时刻才完成」。

**实测**：三个真实产物里，「按下一根」与「按真实日历周期」不同的根数 ——

| 周期 | 000001.SZ_1756656000 | 600519.SH_1762099200 | 000001.SZ_1762099200 |
|---|---|---|---|
| `daily` | 0 | 0 | 0 |
| **`weekly`** | 0 | **1** | **1** |
| `monthly` | 0 | 0 | 0 |

⇒ **三个包里两个已经带着这个错误**（这 3 个包起点恰好都是周一，未触发「删跨界周」；错的是别处的周历边界）。

### 1.4 为什么藏到今天

仓库里**没有任何一条测试把「生成器真实产物」喂给「App 读取器」**。两侧各自的测试都绿，缝在中间无人负责。

## 2. 契约变更

### 2.1 每周期 `datetime` 语义（**本次新立**）

> `klines.datetime` 的语义**按周期区分**，任何依赖它的计算**必须**显式区分：
> - **`3m` / `15m` / `60m`**：该 K 线的**收盘（结束）时刻**；覆盖区间 `(上一根 datetime, 本根 datetime]`。
> - **`daily` / `weekly` / `monthly`**：该 K 线所属周期的**开始侧标识**；覆盖区间 = **该日历周期本身**。

### 2.2 `end_global_index` 的定义

> 含义 = 「这根 K 线在全局 3 分钟轴上**于第几刻形成（完成）**」。逐根精确等于：
>
> ```
> 收盘标注（3m / 15m / 60m）：  upper = 本根 datetime
> 开盘侧标注（daily/weekly/monthly）：
>     upper = period_end(本根 datetime, 周期)      ← 本根所属【日历周期】的结束时刻
>             daily   → 该交易日 23:59:59
>             weekly  → 该 ISO 周的周日 23:59:59
>             monthly → 该自然月最后一刻
>             （一律 Asia/Shanghai）
>
> derived = clamp( bisect_right(m3_datetimes, upper) − 1 , 0 , n3 − 1 )
> end_global_index == derived
> ```
>
> ⛔ **开盘侧不得用「下一根 − 1」**：该序列**允许有洞**（§1.3）。
>
> `.m3` 自身另有不变量（`global_index == end_global_index == 数组下标`，从 0 起严格递增无缺口），**本片不改**。

### 2.3 产物代际标识

> 迁移前后的产物**互不可读**（同一张表、同一组列，但 `end_global_index` 取值语义变了）⇒ 属**两代**，`PRAGMA user_version` **`1` → `2`**。
>
> 依据是冻结 schema 文件自己写的：`training_set_schema_v1.sql:3` ——「schema 变更时 bump `user_version`，旧 version reader 直接拒收」。
>
> ⚠️ **判断依据是「新旧产物能否互读」，不是「列有没有变」。**

⛔ **PG 侧必须先过一道「完整七元组双向比对」的身份闸**（codex S1-R5-F2）：

我上一版的 11 目标清单只用 `id + content_hash + schema_version` 认行。**这是对本仓既有保护的倒退** —— `…-p15-reset-training-sets.sql:15-17` 白纸黑字记着：期望集合必须写成**完整七元组**并与表内容做**双向 `EXCEPT ALL`**，理由正是「**指纹只有 8 位、表上没有唯一约束，单靠它认不出身份**」。母 spec 也记录过 P15 因此被打回重写过两次。

⇒ **本片照搬那套判据**：

```
【同一个连接、同一个事务，从头贯到尾】：
  0  取 B2_GENERATION_LOCK_KEY（advisory，挡住生成路径）
  1  BEGIN
  2  LOCK TABLE training_sets IN ACCESS EXCLUSIVE MODE
  3  身份闸：
  · 期望七元组（stock_code / stock_name / start_datetime / end_datetime /
    schema_version / file_path / content_hash）与表内容做【双向 EXCEPT ALL】
  · 另行断言 3 行的【生命周期状态】（status / lease 三列）符合预期
     · 任一不符 → ROLLBACK，一个字节都不动
  4  【在这个事务仍开着的期间】完成 8 个文件（6 zip + 部署 SQL 2）的持久替换
  5  只按【精确匹配出的那 3 个 id】UPDATE
  6  复核全部字段（不只是 hash 与 version）
  7  COMMIT
  持有该事务的连接必须【全程存活】：连接断 = 锁释放 = 保护消失
```

⚠️ **上一版只写了一句 `LOCK TABLE` 而没定义事务边界**（codex S1-R6-F3）：PostgreSQL 的表锁是**事务级**的 —— 不在显式事务里 `LOCK` 会直接报错；而若「身份闸」与「更新」分属两个事务，**换文件的那段时间就是无保护的**，一条人工或未覆盖到的 `INSERT` 就能让 11 目标集合失效，最终留下「包字节与元数据对不上」。

**必配测试**：文件替换阶段并发发起 `INSERT INTO training_sets` —— 断言它被锁**阻塞**（而非插入成功）。

⚠️ 若省掉这道闸：一行 `file_path` 已经漂掉的行，照样能通过「id + 指纹 + 版本」的检查、被盖上新指纹与新版本，**然后 API 返回错误元数据或 404**。

### ⭐ 一切以【epoch】为单位（codex S1-R13-F1 打回后确立）

本协议**每跑一轮**（首次迁移、回滚后重做、曝光后向前修）都是一个独立的 **epoch**，有自己的：

| 每 epoch 各一份 | 说明 |
|---|---|
| **epoch id** | 显式生成、写进清单与完成记录 |
| **阶段清单** | 记录本轮 11 个目标的「期望旧值 / 期望新值 / 状态」 |
| **备份命名空间** | `.bak.<epoch>` —— ⛔ 不同 epoch 的备份**互不覆盖、互不参与对方的判定** |
| **完成记录 / rollback 记录** | 均带 epoch id |
| **活跃 epoch 记录** | ⭐ **全局只有一份**，指认「当前未决的是哪一个 epoch」；见下 |

⚠️ **为什么必须 epoch 化**：曝光后的向前修是 **v2 → 修好的 v2**，它这一轮的「旧代」是**已曝光的 v2**；而本片又要求**原始的 v1 备份留到验收通过**。若两者共用一个备份命名空间，四态判定会拿 v1 备份去比「本轮的旧代（v2）」⇒ **判为「与旧代不符」→ 中止**；硬用它则会在半途把系统还原成**没人能消费的 v1**。⇒ **v1 备份属 epoch 1，只作重建与审计；epoch 2 备份的是当前已曝光的 v2。**

**必配故障注入**：在「**v1 备份集与 epoch 1 完成记录都还在**」的前提下跑 epoch 2 并中途中断，断言恢复只依据 **epoch 2** 的清单与备份，且 **epoch 1 的备份逐字节未被触碰**。

#### ⭐ 活跃 epoch 记录 —— epoch 化引入的新失效点（codex S1-R14-F2 打回后补）

⚠️ **上一版只说「每轮各有自己的一套」，却没说【重启后怎么知道自己在哪一轮】**。这不是措辞问题，而是 **epoch 化自己引入的一个新失效点**，且恰好落在最要命的边界上：

> epoch 1 **已完成**（v1 备份与完成记录都还在），epoch 2 跑到**一半被杀**。
> 重启的脚本看到的是一堆文件 —— 它**没有任何依据**判断「现在该认领 epoch 2」：
> · 若**新开 epoch 3**：它按规矩不许读 epoch 2 的备份，而 epoch 2 已经把一部分目标换成了新代 ⇒ **半截状态没有任何备份可依**；
> · 若**挑到 epoch 1**：epoch 1 的备份是 **v1**，而 epoch 2 的旧代是 **v2** ⇒ **还原成错误的一代**（正是 §「为什么必须 epoch 化」要避免的那件事）。

⇒ 「epoch 隔离」把「拿错备份」的风险从**内容层**推到了**选择层**；不定义选择规则，等于没解决。

**因此规定【活跃 epoch 记录】**：

```
· 全局【恰好一份】，与备份同一文件系统；原子创建（临时文件 → fsync → 改名 → fsync 父目录）
· 内容 = epoch id + 类型（正向迁移 / rollback-to-v1 / 向前修）+ 本轮清单路径 + 备份命名空间
· 【它必须在任何备份创建与任何目标改动之前就位】
    ⛔ 先动数据后写记录 = 留下「有半截改动、却没有任何记录指认它属于哪一轮」的状态
· 只在【完成记录写下】或【rollback 归档】那一刻被【归档并清除】（归档，不是删除）
· ⛔ 活跃记录存在期间【不得开始另一个 epoch】——
    正向、回滚、向前修一律先认领它；要换类型必须先把它走完或显式回滚归档
```

**必配崩溃测试**（三个，缺一不可）：
1. 在「**活跃记录已就位、备份尚未开始**」处杀掉 → 重启必须**认领同一个 epoch**，且不产生第二份活跃记录；
2. 在「**epoch 1 完成记录 + v1 备份都在**，epoch 2 替换到一半」处杀掉 → 重启必须认领 **epoch 2**、只用 epoch 2 的备份，且 **epoch 1 备份逐字节未动**；
3. 人为放进**两份未决**活跃记录 → 脚本必须**中止报警**，⛔ 不得自动挑一个（挑错 = 拿错备份还原错代）。

**执行协议 —— 全量备份 + 校验 + 失败重做（⚠️ 刻意**不**做「断点续做」）**：

```
0 静默：见下「静默期」——【所有写入方】停掉并持锁

0b 活跃 epoch 解析（⚠️ 必须在代际预检【之前】—— 「旧代 / 新代」的期望值本身来自本轮清单）：
    · 【恰好一份未决活跃记录】 → 本次运行**必须认领它**：沿用其 epoch id、清单、
      `.bak.<epoch>` 命名空间；⛔ 不得新开 epoch、⛔ 不得读写其它 epoch 的清单或备份
    · 【多于一份未决】       → ⛔ 中止并报警（不该出现的形态；自动挑 = 拿错备份还原错代）
    · 【不存在】             → 只有此时才允许开新 epoch：生成 epoch id → 写清单
      （本轮 11 目标的期望旧值 / 期望新值 / 状态）→ fsync 清单与父目录 →
      原子改名就位活跃记录 → fsync 父目录；**这一切都在任何备份与改动之前**

1 代际预检（⚠️ 必须在任何写入之前）：把 11 个目标各自判定为【旧代 / 新代】
    —— 期望值一律取自【本 epoch 清单】，⛔ 不得取自别的 epoch、也不得现场推断
    · 全部旧代 **且【没有有效的 rollback 记录】** → 继续第 2 步
    · 全部旧代 **但【存在有效 rollback 记录】** → ⛔【立即退出，不迁移】
        理由：回滚成功后的状态**正是**「全 v1」。正向脚本若只看代际，就会把
        「刚被人工回滚掉的状态」读成「该迁移了」，**把数据又推回 v2**——
        直接违反 B42。要再次迁移，必须由操作者【显式开新一轮 epoch】
        （归档旧的 rollback 记录并写入新 epoch 标识），不得靠重跑脚本达成
    · 全部新代 且【完成记录存在且可验】 → 【立即退出，不写任何东西】
    · 全部新代 但【完成记录缺失】 → 这正是「PG 已提交、记录未写」时崩溃的形态：
        重新对 11 个目标逐一算指纹复核 → 全对则 fsync 后【补写完成记录】
        并【归档清除活跃记录】再退出；
        任一不符 → 走【全量还原】回旧代（此时备份仍在），再从头重做
    · 混合     → 【先做还原】把已换的还原成旧代，再回到本步重判

2 备份（按【备份集状态】分支，⚠️ 不是简单的 no-clobber）：
    先判定备份集处于哪一态，再动作：
      · 【不存在】     → 全部创建
      · 【齐全且可验】 → 逐个校验其内容确为【旧代】；通过则【直接复用】，不重建
      · 【部分存在】   → 先校验已有的确为旧代，再【只补齐缺的那些】
      · 【存在但与旧代不符】→ 【中止并报警】，⛔ 不覆盖、不猜测
    · 备份内容 = 8 个文件的 .bak（6 个 zip + NAS `$DIR/sql/` 的 P11/P15 两份 SQL）
      + PG 3 行的 (id, 完整七元组, content_hash,
      schema_version, 生命周期状态) 预映像
    · ⚠️【每一份备份的创建本身也必须原子】：同文件系统临时文件 → fsync →
      与【仍是旧代的源】逐字节复验 → 互斥原子改名就位 → fsync 父目录。
      少了这步：拷到一半被杀/掉电会留下【半截 .bak】，而四态判定会把它
      当成「与旧代不符」→ 中止报警 ⇒ 明明旧目标还完好无损，却变成
      【无限期停机】，并逼操作者手工去动唯一的回滚副本
    · 对每个 .bak、预映像文件、【及其父目录】逐一 fsync —— 全部落盘后才许进第 3 步

3 执行：暂存目录产出【新包 6 份 + 新的部署 SQL 2 份】 → 逐个自校验
    · 两份部署 SQL 的新内容【由本 epoch 清单生成】，不得人工填指纹；
      生成后与仓库副本【逐字节比对】，不一致即中止（B51）
    · 对每个暂存文件 fsync
    · 同文件系统 rename 到目标位置
    · 对每个【目标父目录】fsync        ← 少了这步，rename 的目录项可能没落盘
    · 8 个文件全部就位后，PG 3 行在一个事务里更新并提交

4 校验：11 个目标逐一比对期望新指纹 + schema_version；全对才算成功
    · 写入并 fsync 一条【完成记录】，随后【归档并清除活跃 epoch 记录】
    · ⚠️ 未清除活跃记录 = 下次重跑会把【已完成的 epoch】当成未决去认领，
      「重跑应为幂等空操作」当场不成立

5 失败 / 中断 / 重启后：重跑本脚本 —— 第 0b 步先认领**同一个** epoch，
    再由第 1 步的代际预检把它导向
    「退出」「还原后重做」或「继续」；⛔ 在 11 目标复核一致之前，
    不得启回 api / scheduler
```

⚠️ **「全部新代」为什么要再分两态**（codex S1-R6-F2）：上一版只写「全新 → 立即退出」。可**PG 事务提交之后、完成记录写下之前**崩溃，得到的正是「9 个都新、记录没有」这个状态 —— 按上一版会**直接退出**：不补记录、不复核持久性、不还原，而服务还被我们**故意停着**，脚本对此**没有任何已定义的结局**。与 B25 及故障注入要求自相矛盾。

⚠️ **备份集为什么要分四态**（codex S1-R5-F1）：我上一版写的是「互斥创建，已存在则失败」。那条**让重启恢复变成不可能** —— ① 备份阶段崩溃 ⇒ 部分 `.bak` 已存在 ⇒ 重跑走到第 2 步直接失败；② 混合态还原之后备份集是齐全的 ⇒ 回到第 2 步同样失败。⇒ **我自己要求的故障注入用例根本过不了**，只能靠没写进文档的手工操作，而那恰恰会危及唯一的回滚副本。四态分支同时满足「不覆盖」与「可恢复」。

⚠️ **第 1 步（代际预检）是 codex S1-R4-F2 打回后新增的**：原文写「执行前无条件备份」，与另一条要求「重跑应是幂等空操作」**组合起来会毁掉唯一的回滚快照** —— 第二次跑时会拿 v2 状态覆盖 v1 备份，之后真机验收若失败就**没有任何一代可以回滚**。⇒ 预检 + no-clobber 两道一起，才能保证「第二次成功运行后，所有备份与预映像**逐字节不变**」（这条要写成测试）。

⚠️ **第 3 步的 fsync 是 codex S1-R4-F3 打回后新增的**：原文只对**备份**要求 fsync，没管**新写入**的那一侧。后果是 —— 校验时从页缓存读得到内容，但内容或 rename 的目录项**并未落盘**；掉电后可能出现「PG 已提交 v2 指纹、而包退回旧代或残缺」。**「校验即标记」这句话在重启后不成立**，所以第 4 步要落一条 fsync 过的完成记录，且第 5 步要求重启后必须重新复核 11 目标才允许启回服务。

⚠️ 还原路径同样适用上述 fsync 与原子 rename 规则（还原不是「随便拷回去」）。

### 迁移【已成功完成】之后的回滚模式（codex S1-R7-F4 新增）

⚠️ **上一版有个洞**：协议在「11 目标全新 + 完成记录有效」时**立即退出**；而本片又要求 `.bak` **留到切片二真机验收通过**才删 —— 这等于承认「验收失败时需要它们」，**却没有任何命令能从完成态把它们用起来**。⇒ 切片二若验收失败，`api` 必须继续停着，而操作者**没有一条已定义、已测试的路**把 8 个文件与 3 行还原回 v1。

**因此定义一个显式的回滚模式**（与正向迁移同样严格）：

```
rollback-to-v1（人工显式触发，绝不自动）：
  0  与正向同样的静默：api / scheduler / CLI 全停 + 取 advisory 锁
  1  BEGIN → LOCK TABLE training_sets IN ACCESS EXCLUSIVE MODE
  2  身份闸（v2 侧）：按【v2 的完整七元组 + 生命周期状态】双向比对，
     确认现状确实是我们迁上去的那一代；不符 → ROLLBACK 中止
  3  校验 8 个 .bak（6 zip + 部署 SQL 2）与 PG 预映像齐全且确为 v1
  4  原子还原 8 个文件（临时文件 → fsync → 改名 → fsync 父目录）
  5  按 id UPDATE 回预映像（幂等）
  6  复核 11 目标全部回到 v1
  7  COMMIT → 归档（不是删除）完成记录，写 rollback 记录，
     并【归档清除活跃 epoch 记录】
  ⛔ 回滚完成前不得启回任何服务
```

⚠️ **回滚自己也要有预检与恢复态**（codex S1-R8-F2）：上一版把 PG 还原 `COMMIT` 排在「归档完成记录」**之前**。崩溃若发生在两者之间，得到的是「**11 目标全 v1、而 v2 完成记录还在**」——
· 重跑 `rollback-to-v1`：第 2 步的 **v2 身份闸**要求现状是 v2 ⇒ **直接中止**；
· 改跑正向迁移：它看到「全旧代」⇒ **又把数据迁回 v2**。
⇒ 服务全程停着，操作者**没有已定义的出路**，只能手工去动记录 —— 而那正是最不该手工动的东西。

**因此回滚必须有自己的预检**（与正向对称）：

```
rollback 预检（每次启动先跑）：
  · 先按同一规则解析【活跃 epoch】：有未决的就认领它、多于一份则中止、
    没有则新开一个【类型 = rollback-to-v1】的 epoch 并在动手前就位
  · 11 目标全 v2 + 有 v2 完成记录        → 正常回滚（走上面 0–7 步）
  · 11 目标全 v1 + v2 完成记录仍在(未归档) → 只需【补做归档】并 fsync，然后退出
  · 11 目标全 v1 + 已有 rollback 记录     → 已完成，退出
  · 文件/PG 处于混合态                   → 按备份继续还原到全 v1，再回本步重判
  · 备份集不齐或与 v1 不符               → 中止报警，⛔ 不猜测
⚠️ 陈旧的【正向完成记录】必须由本预检确定性处置（归档），
   ⛔ 不得留给正向迁移脚本去解释 —— 它会把「全旧代」读成「该迁移了」
```

⚠️ **上面这套只适用于【曝光前】回滚**（codex S1-R9-F2）——「迁完了、但手机还没下载过任何东西」。

### 曝光后的恢复 ——【**不是**回滚到 v1，而是**就地修 v2 向前走**】（codex S1-R11-F1 整节重写）

⚠️ **上一版的前提被推翻了。** 我写的是「还原到 v1 → 库存可用 → 再下载一次」。**那个状态不存在**：

| 客户端 | 能不能消费 v1 包 |
|---|---|
| **改动前的 App**（现网这版） | **不能** —— 它只认 `.sqlite`，而真实产物里是 `.db`（本片 §6.3 自己写着）；旧索引它也照样拒 |
| **切片二的 App** | **不能** —— 它要求 `user_version = 2` 并按新公式逐根校验 |

⇒ **没有任何一代 App 能消费 v1 包。** 把库存还原成 v1 再用 P15 放出来，得到的不是「恢复」，而是**一场停机**：行是可下载的，但每个客户端都拒。

**因此本片明确规定**：

1. ⛔ **v1 备份不是服务恢复手段** —— 它的用途只有两个：**重建**（迁移搞砸时回到已知良好的起点，好重来一次）与**审计**；
2. **曝光后（手机已下载过）的恢复，一律是「向前修 v2」**：

```
recover-after-exposure（人工显式触发）：
  1 ⭐【就是再跑一次本节的迁移协议，只是输入换成「修好的 v2」】——
    ⛔ 不得另造一个「简易修复分支」。必须复用同一套：
      · 同一份【11 目标清单】（部署目录 3 + P7 来源 3 + NAS `$DIR/sql/` 2 + PG 3 行）
      · 同一套【写死值同步清单】（§3.4 那张表：P11/P15 两份 SQL、runbook 两处、
        deployment-design 五处、Mac 本地副本）
      · 同一套【备份四态 + 原子 + fsync + 单事务 + 完成记录】
    ⇒ 重打包必然改 content_hash，而**P15 的期望七元组是本片自己要维护的**，
      在同一个协议里被一并更新，出协议时它已与库里的行匹配
  2 跑 runbook 既有的 P15 复位生命周期
    —— 此刻行是【修好的 v2】，而 P15 期望已在第 1 步同步过 ⇒【正好匹配】
  3 复位【前】必须满足 runbook 既有纪律：对外入口关闭 +
    手机上【长按删除 App 再重装】（否则上一轮下载的数据还在，G2/G4 观察作废）
  4 ⛔ 全程不静默改生命周期列 —— 复位是 P15 显式做的
```

⚠️ **上一版把第 1 步写成了一个轻量分支**（codex S1-R12-F1）：那样「重打包 ⇒ 指纹变」之后，
P15 仍拿**旧的写死七元组**认身份 ⇒ **确定性中止、不复位** ⇒ G4 失败后**没有任何重试路径**。
根因是我把「向前修」当成了迁移之外的东西 —— 它其实**就是一次迁移**，只是输入不同。
⇒ 现在明令复用同一套协议与同一份同步清单，指纹与 P15 期望在**同一个协议内原子地一起更新**。

3. **`rollback-to-v1` 的用途也要说准**：它把产物退回**已知良好的起点**，**为的是重做一次迁移**，⛔ **不是**为了让 App 去用 v1 数据。文档里任何「回滚后库存可用」的说法都作废。

⚠️ 若哪天真的必须让 App 消费 v1，那需要一个**经过测试的过渡版 App**（同时接受 `.db`、`user_version = 1`、旧索引语义），并且要跑**完整的下载 → 解压 → 打开 → 读取**链路才算数（只跑 HTTP 下载**不算**）。**本片不做，也不承诺。**


**必配测试**：
① **曝光前**：从已成功完成的 v2 状态执行 `rollback-to-v1`，断言 11 目标全回 v1、完成记录被**归档**（非静默丢弃），且断言其目的被正确表述为「回到已知良好起点以便重做迁移」——⛔ **不得**出现「库存可用」之类的断言；
② **曝光后**：构造「P14 走到 G3 之后、3 行已 `sent`、G4 失败」的场景，断言**曝光前那套回滚会明确中止并给出指引**；
③ **曝光后端到端（必须故意改动全部指纹）**：跑 `recover-after-exposure`，让修复**改掉全部 3 个 `content_hash`** → 用**真实的 P15 脚本**（其期望值由该协议同步更新）复位 → 再下载一次**能成功**；并断言**没有任何一步静默改过生命周期列**（复位是 P15 显式做的）；
④ 故障注入下沉到**每一次还原改名之后**、**PG `COMMIT` 之后**、以及**归档前后**各一次，断言每一处中断都能由预检确定性收敛（不出现「两个脚本互相把数据推来推去」）。

⚠️ **本节曾有一段「为什么不写三段状态机」的论证，现已【整段作废】**（codex S1-R7-F1）：那段话主张「不存在需要标记消歧的状态」「不需要 PG 反向事务，`pg_dump` 还原即可」——**两句都已被后续轮次推翻**（S1-R3-F1 指出 `pg_dump` 重放会主键冲突；S1-R6-F2 指出「9 个都新、记录未写」正是真实崩溃态）。留着它会让实施者按**互斥的两套算法**行事，做出「不写完成记录」或「回滚撞主键冲突」的实现。

⇒ **上面那段编号流程（第 0–5 步）是本节【唯一】的规范来源**；下面的说明只解释「为什么这么定」，不再重复定义算法。

⇒ **用「可完整还原 + 可重复执行」换掉「可断点续做」**，状态空间从「每目标 × 各阶段」塌缩成「成功 / 未成功」两态。⛔ 实施时**不得**为了「省时间」加断点续做。

⚠️ **但「重做」有一个前提，我上一版漏了**（codex S1-R3-F1）：**重做能成立，前提是备份本身已经持久化**。原文那句「不需要 fsync」**是错的** —— 它只对「续做用的阶段状态」成立；**掉电时，只经过页缓存的 `.bak` 可能根本没落盘，而原件已被替换 ⇒ 仅此一份的原始产物永久丢失**。

**第 1 步（备份）必须做到**：

```
对 8 个文件的 .bak（6 个 zip + 部署 SQL 2）、PG 预映像文件、以及【它们各自的父目录】逐一 fsync；
全部 fsync 完成并复验可读之后，才允许进入第 2 步（替换）。
（父目录也要 fsync —— rename 的原子性不等于目录项已持久）
```

⚠️ **PG 的还原方式也要改**（同条）：原文写「从 `pg_dump` 恢复」**不可执行** —— 那 3 行的 id 还在，重放 dump 会**主键冲突**，而不是把两列改回去。
**改为**：备份阶段存下 3 行的 **(id, content_hash, schema_version) 预映像**；回滚 = 一条**按 id `UPDATE` 回预映像**的**幂等**事务。

**故障注入必须覆盖两类边界**：进程被杀 **与** 掉电（后者用「不 fsync 就断电」的等价手段模拟），断言两类下都能还原到旧代。

**必配故障注入**：在第 2 步的**每个替换点之后**各中断一次（含 PG 事务提交前/后），断言：还原后 11 个目标**全部回到旧代**，且重做一次后**全部到达新代**。
⚠️ **替换点必须逐一枚举到 11 个**（含**两份部署 SQL 各自的替换点**），⛔ 不得只覆盖 6 个 zip 与 PG。

⚠️ **验收必须真跑那两份【部署副本】**（codex S1-R14-F1）：迁移后要**实际执行** NAS 上的 `sql/…-p11-insert-training-sets.sql` 与 `sql/…-p15-reset-training-sets.sql`（不是仓库副本、不是重写一份等价 SQL），断言它们的七元组身份闸**通过**。只比对文件指纹不算 —— 本片要保的正是「**runbook 真正会执行的那两份**能对上库里的行」。

**其它硬要求**：

| 要求 | 做法 | 不做会怎样 |
|---|---|---|
| **静默期（改法见下）** | **停掉 `api` 容器**，而不是只关 tailscale 入口 | 并发下载读到「旧元数据 + 新字节」，撞完整性校验；已被接受的请求与 **NAS 本机直连**的流量，关 serve 根本挡不住 |
| 确定性压缩 | 固定 `ZipInfo.date_time` 与压缩参数，使同一输入恒产出同一字节 | `zipfile` 默认嵌 mtime ⇒ **重跑一次 CRC 就变** ⇒ 迁移不幂等 |
| 回滚副本 | 原包留 `.bak`，**直到切片二真机验收通过**才删 | 原始数据只此一份，出错无退路 |

**静默期的正确做法**（codex S1-R1-F1 打回后订正）：

⚠️ **原文写「先 P16 关入口」是不成立的**，两个理由：
1. 本仓已实测三次：`expose.sh` 的看门狗**继承了 flock**，窗口期内 `close` 恒 `LOCK_TIMEOUT`、**关不掉**（母 spec 已记录，我却同时把它列为「范围外」又依赖它）；
2. 就算关成功了，**关 tailscale 入口挡不住两类流量** —— 已被接受的在途请求，以及 **NAS 本机直连 `127.0.0.1:8010`** 的访问。

**改为**：

⚠️ **只停 `api` 还不够**（codex S1-R2-F1）：本仓还有**独立于 API 的写入方** —— `backend/app/scheduler_main.py`（`build_generate_batch`）与生成器 CLI，**都能在 API 不在的情况下产出 zip 并往 `training_sets` 插行**。它们若在迁移中途跑起来，11 目标清单当场过期，还会产出**旧代契约**的新包。

```
迁移前：① docker compose stop api
        ② 停掉 / 确认没有 scheduler 与生成器 CLI 在跑
        ③ 【整个迁移期间持有 B2_GENERATION_LOCK_KEY】（生成器自己就用这把锁，
           持住 = 任何生成路径都进不来，且这是【可证明】的互斥而非口头约束）
        验证 ⓐ`docker compose ps` 无 api  ⓑ宿主机 8010 无监听
             ⓒ本机 curl 连不上  ⓓ锁已持有  ⓔ`training_sets` 恰好 3 行且 id 与清单一致
迁移后：11 目标收敛校验通过 → 释放锁
        ⛔ 【不启回 api】，⛔ 【也不启回 scheduler / 生成器 CLI】—— 见下
```

⛔ **切片一结束时 `api` 必须保持停止**（codex S1-R2-F4；上一版我写了「校验通过 → `start api`」，与 §8「两片之间不得启回 api」**自相矛盾**）：此刻库存已是第 2 代，而 App 仍拒 `.db` 与 `user_version = 2`。启回 api ⇒ 若持久化的 tailscale serve 配置没被成功清掉，**不兼容的客户端会立刻恢复访问、预占库存、然后在确认前失败**，把库存烧成 `reserved`。

⇒ **`api` 与对外入口一律等到切片二部署完、且共用 fixture 的端到端测试通过之后才启回。**

⛔ **`scheduler` 与生成器 CLI 同样要停到切片二之后**（codex S1-R5-F3；上一版我只把「停 scheduler」写成迁移期间的临时措施，迁移后就释放了）：

- `backend/app/scheduler.py:5` 写明其职责是「`unsent<=40` 就调 `generate_batch` **补到 100**」⇒ 一启动就会**批量补货**；
- 而 `backend/docker-compose.yml:96-103` **已经白纸黑字记着**：生成器在**宿主机**上跑、把**宿主机绝对路径**写进 `file_path`，「**产出的行在容器内会全部 404**」。

⇒ 启回 scheduler = 往库里塞进**几十行 schema-v2 但下载必 404** 的记录，**且它们全在那 9 个被校验的目标之外**。

⚠️ 这条与「`file_path` 宿主/容器语义未统一」这个既有残留是同一个根（PR-2 已明写、本次不修）。**在那个残留解决之前，任何自动补货都必须保持关闭**，并把「scheduler 与 CLI 仍处于停止」写进本片的最终验收。

⚠️ **数据库清单校验要做两次**（暂存前、提交前各一次）：确认 `training_sets` 仍是那 3 行、id 未变 —— 防止「静默期开始后仍有人插了行」这种情况被静默带过。

⭐ 这比「修好 `expose.sh` 再迁移」更强：停容器**同时**掐断 tailnet 与本机两条路径，且**不依赖任何待修缺陷**。`expose.sh` 的锁缺陷仍是独立残留（§6.4），但**不再是本片的前置阻塞**。

⛔ **收口闸**：**11 个目标全部收敛到同一代之前，不得启回 `api`、更不得开对外入口**。写成脚本里的显式检查，不是嘱咐。

| B36 | 备份创建不走「临时文件 + 原子改名」 | 「拷贝 .bak 中途被杀」故障注入用例变红（会留半截 .bak 并把下次运行推进中止分支） |
| B37 | 不提供完成态回滚模式 | 「从已完成的 v2 回滚到 v1」用例变红 |
| B38 | 回滚跳过 v2 侧身份闸 | 「现状并非我们迁上去的那一代时必须中止」用例变红 |
| B39 | 只改 R03、不改冻结契约其余三处版本引用 | 3c 的收敛守卫变红（三处版本号未同时为 2） |
| B31 | 迁移后启回 scheduler | 「切片一交付时 scheduler / CLI 仍停止」用例变红 |
| B26 | CI 不比对「当前生成器输出 vs 已提交 fixture」 | 「生成器改了序列化 / user_version 而 fixture 未更新」用例变红（两侧本会双绿） |

### 4.1 ⭐ 跨端接缝的**生产者半边**（本片必须交付；codex S1-R1-F2）

§1.4 把「没有任何测试把生成器真实产物喂给 App 读取器」认定为两个缺陷共同的藏身之处。母 spec 归档后，**若本片只做后端变异 + 产物自洽校验，两侧的静态 fixture 仍会各自漂移，同一类回归照样静默。**

**本片交付**：

1. 用**生产顶层装配函数** `assemble_from_windows(...)` 从一组合成 bar 数据产出一个**小训练组**，提交进仓库作为**跨端共用 fixture**；
   ⚠️ **不得**自己串调 `assign_global_indices` → `build_training_set_sqlite` → `zip_and_hash`：真正决定 zip 成员名的是 `assemble_from_windows:403`（`f"{fname}.db"`），绕过它的测试对该行**零敏感**。
2. 该 fixture 的形态必须**同时覆盖本片三类特征**：① 至少一个非 m3 周期有 ≥2 根落在 `end_global_index = 0`（轴前历史）；② 含跨**午休**与跨**日**的日内边界；③ 含一处**被删的跨界周**（起点设为周中）。
3. 断言：**压缩包清单**（恰好 1 个成员、后缀 ∈ {`.sqlite`,`.db`}、无 sidecar）+ **逐周期索引向量**与**独立人工推算**的期望值逐根相等。
   ⚠️ **期望值必须手写**，不得由「跑一遍生成器」得出 —— 否则生产者与校验者可以**一起用错公式而全绿**，那正是缺陷藏住的机制。

4. ⭐ **CI 每次都要把「当前生成器的输出」与「已提交的 fixture」对齐**（codex S1-R4-F1）：

   ```
   每次 CI：重新调 assemble_from_windows(...) 产出一份 → 与仓库里那份 fixture 比对
            比【逻辑内容】：压缩包成员清单 + user_version + 每张表的全部行
            ⛔ 不比 zip 原始字节（zipfile 嵌 mtime，跨机跨时不可复现，比字节必然假红）
   ```

   ⚠️ **缺了这条，§1.4 那道缝会原样复活**：生成器日后改了序列化 / DDL / 版本，**生产者侧的测试对着新鲜输出照样绿**，而 App 侧对着**陈旧的已提交 fixture** 也照样绿 —— 两边都绿，缺陷照旧静默。

**移交切片二**：必须用**这一个 fixture**（不是自己另造一份）跑通真实的解压 → 打开 → 读取链路。⇒ 三方（当前生成器输出 / 已提交 fixture / App 读取链路）钉在同一件产物上，任何一方漂移都会红。

**正向对照（必配，防「全是拒了」的套件掩盖恒抛守卫）**：健康输入必须被放行 —— ① `daily`/`monthly`/`3m` 逐根不变；② 迁移后的 3 个包内容自洽（`user_version = 2`、索引逐根等于 §2.2 反算值）；③ 迁移脚本对**已迁移**的包重跑一次为**幂等空操作**；④ 上述 fixture 通过全部断言。

⚠️ **B1 与 B3 必须互不掩盖**：另配一次 **B1+B3 组合变异**，确认组合下仍有测试红并记录是哪一条。

## 5. 兼容性

| 维度 | 结论 |
|---|---|
| 训练组 SQLite **表结构** | **不变**（无新列 / 无类型变化 / 无约束变化） |
| `PRAGMA user_version` / `TRAINING_SET_SCHEMA_VERSION` | **`1` → `2`**（§2.3：判据是「能否互读」） |
| 顶层 `CONTRACT_VERSION` | **`"1.13"` → `"1.14"`** |
| 既有 3 个产物 | **需就地迁移**（§3.4）；`content_hash` 会变 |
| 现有 App（未改） | 迁移后拿到 v2 包会报 `.versionMismatch` —— **不是回归**：它本来就消费不了任何真实训练组（zip 内是 `.db` 而它只认 `.sqlite`，属切片二） |
| QMT pilot 库 | 顶层 bump 后带 `"1.13"` 的既有库被闸 1 拒，需 `--reset`（4b 未投产，风险低） |

## 6. 明确不做（YAGNI / 归切片二）

1. **App 侧一切逻辑**：读取判据、缓存回收、进行中合成、面板联动 —— 归切片二；
2. **运行期能力协商 / 双格式过渡版 App**：未上架、单用户单机、次序可控，`user_version` 已足以给出可恢复信号。⚠️ **一旦上架必须重新评估**；
3. **`.db` / `.sqlite` 扩展名之争**：属切片二（改 App 接受 `.db`，user 已拍板）；
4. **`expose.sh` 看门狗继承 flock 导致窗口期内关不掉**：真缺陷，独立小 PR；
5. **App 后端地址不可配（PR-3 从未实施）**：`KlineTrainerApp.swift:18` 仍硬编码，独立 PR。

1. §4 **全部 58 组变异（B1–B58）+ 1 组组合（B1+B3）**逐条跑过，**每组写明红的是哪一条测试**；
   ⚠️ **本条第七次踩同一个坑**（codex S1-R3-F3）：上一轮加了 B17–B21，验收门却还写着「16 组」—— 与既有教训「改了表没改门」完全同型。
   ⇒ **配一条机械校验**：断言「§4 变异表行数」==「本条列举的编号个数」，对不上就红。比「记得同步」可靠。
2. 正向对照三条全部放行；
3. 后端 CI 全绿（Linux，**零 skip**）；iOS 侧因第 6/7/8 项常量改动而受影响的测试全绿；
4. 迁移完成后：11 个目标指纹一致、全仓 grep 旧指纹命中 0、来源闸通过、脚本重跑为幂等空操作；

7. 迁移期间**所有写入方**确实停着：`api` 停、scheduler/CLI 无进程、`B2_GENERATION_LOCK_KEY` 全程持有、`training_sets` 行数与 id 在暂存前与提交前**两次校验**一致；
8. **切片一交付时 `api`、`scheduler`、生成器 CLI 三者均处于停止状态**，对外入口未开（⛔ 启回归切片二，且 scheduler 还需等 `file_path` 宿主/容器语义残留解决）；
9. 故障注入：在**全部 11 个替换点**（含两份部署 SQL 各自的替换点、含 PG 提交前/后）各中断一次，断言「全量还原后 11 目标全回旧代」且「重做一次后全到新代」；
10. **活跃 epoch 三条崩溃测试**全过：①活跃记录已就位/备份未开始被杀 → 认领同一 epoch；②epoch1 完成 + epoch2 半途被杀 → 认领 epoch2 且 epoch1 备份逐字节未动；③两份未决记录 → 中止报警；

⚠️ **本片交付后可以说**：「日内周期与周线的形成时刻已订正；既有 3 个产物已迁移至第 2 代」。
⛔ **不得说**：「手机能用了」「真实数据链路打通」—— App 侧一行未改，它仍消费不了任何训练组。

## 8. 与切片二的交接

**切片二（App 侧）必须承接的既定事实**（不得再自行推演）：

1. §2.1 的两套标注约定、§2.2 的索引定义 —— **契约已定**，切片二只负责**校验**产物是否符合；
2. `period_end` 必须**复用**本片的定义（§3.1），不得另写一份；
3. 产物代际 = `user_version 2`；App 侧 `TRAINING_SET_SCHEMA_VERSION` 与 `TrainingSessionCoordinator:1307` 那个**写死的字面量 `1`** 必须同步（⚠️ 该字面量的历史理由 residual E6a-R1 已过期）；
4. 迁移前的 v1 包会被版本闸拒为 `.versionMismatch`（**不是** `.dbCorrupted`）—— 切片二的「旧公式」测试必须用**合成档**（`user_version = 2` + 旧公式索引）才能走到索引校验那一层；
5. ⛔ **次序**：本片先落地并完成迁移，切片二才动；两片之间**不得启回 `api`、不得开对外入口**；
6. ⛔ **切片二必须把顶层 `CONTRACT_VERSION` 再 bump 到 `"1.15"`**（§3.3）：`1.14` 标识「产物已第 2 代、App 尚不支持」，`1.15` 标识「App 已支持」。两态共用一个版本号会让跨语言守卫在两种状态下都绿，标识失去意义；
7. **本片交付的跨端 fixture（§4.1）是切片二的必用输入** —— 切片二不得另造一份，否则两侧静态样本会各自漂移，缺陷 A/B 那类回归照旧静默。
