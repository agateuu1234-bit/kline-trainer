## 0. 一句话

崩溃恢复删掉某只股的 `files` 记录时**不退还**它们的字节，于是重拉同一只股被转移守卫算成
「新增」，`committed_bytes` 必须再涨一整份。**同一只股每崩一次重拉就多烧一份预算**，
最终以**虚假的 `--max-bytes` 触顶**结束运行 —— 一次基础设施故障被记成一次正常结束。

修法（user 2026-10-01 拍板）：**恢复时同步退还**，并给「累计量不许调小」那条守卫开一个
**精确到字节**的口子。

## 1. 现状与证据

### 1.1 机制（逐处回源码核实）

- 账本条目的键是 `(stock_code, period, relative_path)`（`qmt_manifest.py:1406 _by_id`）。
- 崩溃恢复第③档删掉该股的两条 `files` 记录 ⇒ 这两个键从 `prev_files` 消失。
- 转移守卫（`:1566-1583`）据此把重拉的同两个文件算成 `added`，要求
  `committed_bytes ≥ 旧值 + added`。
- **不是固有检查的问题**：固有检查只给**下界** `nb ≥ sum(files) + staged_export_log`，
  而**两种语义都满足这个下界** ⇒ 它分不出这两种语义（契约 §3 已订正过一次归因错误，
  本次复核无误）。
  ⚠️ 本节不刻画「两种语义差多少」—— 本文上一版在这里写过「累计语义必然更大」
  （过强）、改版又写过「从没移除过任何记录时两者相等」（**错的**：记录逐字相同的
  **重拷**会让累计量上涨而 `files` 集合一个字不动，实测差 140 字节，见 U14）。
  连错两次之后的处理是**删掉这个刻画**，而不是再换一个说法 —— 本节的论证只需要
  「两种语义都过得了下界」这一条，差额多少与结论无关。

### 1.2 实测 · 现状（`probe_r1_fix.py`，用真实守卫 + 真实夹具）

```
盘上真实占用量 = 2399920 字节（其中该股两条记录共 366）
首次提交后 committed_bytes = 2399920

第 1 次崩溃恢复：放行，committed_bytes 不动（2399920）
  重拉时最小可接受的 committed_bytes = 2400286   （盘上仍是 2399920）   ← +366
第 2 次崩溃恢复：放行
  重拉时最小可接受的 committed_bytes = 2400652   （盘上仍是 2399920）   ← 再 +366
```

⇒ **每崩一次多烧一份**，而盘上占用量一字未增。与契约 §3 记录的 366 → 706 → 1046
**结构完全一致**（绝对数字不同只因本探针的 `export_log` 夹具更大）。

### 1.3 实测 · 修法会撞上哪条守卫（同一探针的对照组）

```
第 1 次崩溃恢复（退还 366）：⛔被拒
  「committed_bytes 从 2399920 变成 2399554 —— 它是累计量，
    调小、删掉或换成别的类型都等于绕开 --max-bytes 这条硬上限。」
```

⇒ 「累计量不许调小」那条（`:1548-1555`）**对崩溃恢复一样生效，没有任何豁免**
（我在写修法前先核实过这一点，它决定了修法的形状）。

### 1.4 改动面有多大：恢复第③档**目前零实现**

```
$ /usr/bin/grep -rn "RecoveryScope\|recovering_from_crash" backend/*.py | grep -v qmt_manifest.py
backend/qmt_fetch.py:1259:  # qmt_manifest 的转移守卫（不得修改）没有 RecoveryScope 就不允许「同一
backend/qmt_fetch.py:1261:  # RecoveryScope 是 S4b 崩溃恢复的职责，不是单股事务该做的事——一律拒绝，
```

⇒ `qmt_fetch` 的单股事务**显式拒绝** `RecoveryScope`，恢复第③档要到 S4b 才实现。
**本 PR 只动守卫与测试，没有调用方需要迁移**，这正是交接单说的「必须在 S4b 之前修」：
S4b 的停机判断会直接建在这个计数上。

### 1.5 为什么不能改成「当前占用量」语义

契约 §3/D7 的 E11 已经记录并实测过：那会**死锁** —— 恢复后重拉时转移守卫要求
`≥ 旧值 + 新增字节`，而当前占用量没涨，提交被拒，文案指向「换新 staging 重拉」，
于是每次重跑都死在同一处、约 2 GiB 的 staging 永久报废。
**本 PR 不推翻这条**；退还修法恰好绕开它（见 §2.3 的算术）。

## 2. 设计

### 2.1 恢复时退还：唯一改动点

崩溃恢复第③档删掉该股的 `files` 记录时，`committed_bytes` **同步减去这些记录的
`bytes` 之和**。`files` 之外的任何东西都不动。

### 2.2 守卫的新判据（R1 / R2 / R4 / R5；R3 已删，见下）

`_require_no_progress_rollback` 里「累计量不许调小」那一段，**仅在已声明的崩溃恢复
且该股被完整移除时**换成一条更严的等式判据。

现有代码已经算出了 `scoped_removed`（`:1365-1383`），它为真当且仅当：
声明了 `RecoveryScope`、锚点与冻结名单对得上、且该股的 `files` 与池条目**一起**消失。
**口子挂在它上面，不另造旁路。**

| # | 判据 | 不通过时 |
|---|---|---|
| **R1** | `scoped_removed` 为假时，维持现状：`nb ≥ ob`，且 `nb ≥ ob + added` | 原文案不变 |
| **R2** | `scoped_removed` 为真时，`nb` 必须**恰好等于** `ob - removed_bytes`，其中 `removed_bytes` = `prev_files` 中消失的那些记录的 `bytes` 之和 | `block`：说明「恢复必须恰好退还被移除记录的字节数，多退少退都会让 `--max-bytes` 失真」 |
| **R4** | `scoped_removed` 为真时，`new_files` **不得包含任何 `prev_files` 里没有的键**（即 `added` 必须为 0） | `block`：说明「恢复提交只许移除，不许同时新增；新增请另起一次提交，好让它的字节被正常计账」 |
| **R5** | `scoped_removed` 为真而上一份**根本没有 `committed_bytes`** 时：拒绝这次恢复提交（R4 先判，它不需要基准） | `block`：说明「它是 `--max-bytes` 的累计基准，缺了基准「恰好退还」无从核对；读侧仍允许旧账本缺这个字段，**非恢复提交照旧放行**」 |

**原先还有一条 R3「`nb` 必须 ≥ 0」，已删除 —— 它不可达**（codex 在评审实施计划时
实测发现，`probe_plan_bugs.py` 复现）：

```
U12 夹具（ob = 183，退还 366 后 nb = -183）
  → 拒绝：「账本里有 0 条 files 记录 + staged export_log 2399554 字节，
           而 committed_bytes 是 -183（须为非负整数且不小于两者之和）」
  ⇒ 拦住它的是**固有检查**，不是退款分支
```

`_require_no_progress_rollback` 开头就调 `_require_intrinsic_payload_ok(payload, …)`，
它要求 `nb ≥ sum(files) + staged_export_log`，而两者都非负 ⇒ **`nb` 恒 ≥ 0**，
退款分支里再查一次永远执行不到。按 CLAUDE.md §2「不为不可能的场景写错误处理」删掉。
U12 改为**表征用例**：断言拦住它的确实是固有检查（而不是假装 R3 在起作用）。

**为什么是「恰好等于」而不是「≤」或「≥」**：

- 用 `≥` 等于没改（现状就是 `≥ ob`，退还会被拒）。
- 用 `≤` 会放任把累计量退成任意小 —— 那正是现有文案警告的「绕开 `--max-bytes`」。
- **等式是可机械检验的**：`removed_bytes` 完全由 `prev_files` 与 `new_files` 的差集算出，
  不依赖调用方自报。⇒ 这个口子**不是**一个可被滥用的旁路。

### 2.2b R4 的由来：「两格互斥」原本没有代码保证

我起初在这里写「`scoped_removed` 为真时没有任何文件被写入，所以两格互斥」。
**这句话是错的**（codex 第 1 轮 [medium]，实测坐实）：`scoped_removed` 只检查
**目标股**完整消失，`files` 守卫不禁止新增别的键，`pool_order` 也允许追加。

**实测**（`probe_r1_leak.py`，特意把累计值抬高 1000 万，排除「固有下界检查代为拦截」）：

```
起点：files = A 的两条（366 字节），committed_bytes = 12399920（比下界高 1000 万）
这次提交：删掉 A（366），同时新增 B（366），声明对 A 的 RecoveryScope

  ① nb = ob + 366（按现状规则）   ✅放行   ← 这种形状现有守卫**是允许的**
  ② nb = ob                        ⛔拒绝
  ③ nb = ob - 366（我设计的 R2）   ⛔拒绝（被「不许调小」拦住，即今天的现状）
```

① 放行 ⇒ 我的 R2 一旦生效，B 的 366 字节会**完全不计账**，而余量足够大、
固有下界也拦不住。**这就是一条记账旁路。**

⇒ 补 **R4**：退款分支里 `added` 必须为 0。有了它，「两格互斥」才**由判据保证**，
而不是由我的断言保证。

**与 D7「`≥` 不可收紧」不矛盾**：D7 那条讲的是**重拷成功**那一格
（记录逐字相同 ⇒ `added = 0`，而本次真写盘 140 字节 ⇒ 必须允许 `nb > ob`）。
那一格 `scoped_removed` 为假，走 R1，`≥` 原样保留；R2/R4 只管恢复移除那一格。
U14 专门钉这一点。

### 2.2c R5 的由来：R2/R4 被一个与它们无关的开关挡在外面

实现把 R2 与 R4 整段嵌在 `if ob is not None:` 里，而**读侧允许旧账本没有
`committed_bytes`**（§8 的 R-B2 明文保留这条兼容性）⇒ **`ob is None` 时两条判据
双双不执行**。

**实测**（codex 对抗性评审第 1 轮的唯一一条 finding，判决 `needs-attention`；
两份账本都先过真正的 `validate_manifest`，证明是合法账本、不是畸形输入）：

```
对照组：旧账本**带** committed_bytes → ✅拦住（R4 报「只许移除」，并列出新增的键）
实验组：旧账本**缺** committed_bytes → ⛔放行 —— 恢复时夹带 2 条新记录（2469134 字节）
```

⇒ R4 这条 binding 契约被整条绕开，夹带进来的字节**完全不计账** ——
正是 §2.2b 那条记账旁路，只是换了个入口。

**修法 = 塌掉那一层、去掉那个开关**（不在旁边再补一条检查）：

- **R4 改为无条件执行** —— 它只看键的差集，压根用不到 `ob`。§2.2 表里「`scoped_removed`
  为真时」本来就是**无条件的措辞**，所以这一步是让**实现对上 spec**，不是改 spec。
- **R2 确实要基准，缺基准就 fail closed** —— 这才是新增的 R5。体例对齐实现里既有的
  「`committed_bytes` 坏型时直接拒」：**坏型与缺席，对恢复提交是同一种处境**。

**R5 不违反 R-B2**：没有把 `committed_bytes` 变成**读侧**必需键
（`validate_manifest` 一字未动）、**不** bump `manifest_version`、既有 staging
不作废；旧账本缺这个字段的**正常提交一个字节都没变**。被收紧的只有**恢复提交**
这一条路径 —— 而那条路径要求有基准可核对，否则 R2 的等式没有左值。

⚠️ **同一类里还剩一半，本 PR 明确不收**：`ob is None` 且 `scoped_removed` 为假时，
R1 的单调判据（`nb ≥ ob`）**依旧整条不执行** —— 旧账本缺基准时，一次正常提交可以把
累计量写成任何过得了固有下界的数字。这不是本次引入的，它是 R-B2 这条兼容性的**直接
后果**：没有基准，单调性本来就无从比较。

⚠️ **本节不预先裁定「将来怎么收这半边」。**

本文已经在这里连错两版：上一版写「只有两条路、两条都要 bump `manifest_version`、
让既有 staging 作废」（codex 第 2 轮：**并非技术必然**）；改版换成一张「三条路」对照表，
又被 codex 第 3 轮指出第 ③ 条的代价描述不全、第 ② 条的框定方式也不对
（补零会与非空账本的固有下界冲突，而那不是 bump 版本号能解决的）。

**连错两版之后的处理是把这些断言删掉，不是再换一版措辞。** 理由：本 PR **没有实现、
也没有测试过任何一种收法**，而这是一份 binding 的规范 —— 在这里替 S5 评估方案，
写出来的是未经核实的话，还会把后人的选项提前关掉。

⇒ **交接 S5**：那时要一并回答三个问题 ——「历史累计量能不能恢复、恢复不了算不算、
怎么算」「收这半边要不要动读侧必需键与 `manifest_version`」「与 R-B2 的兼容性承诺怎么并存」。
**本 PR 对这三问一律不表态。**

本 PR 只把**恢复提交**这一格收紧，是因为 R2/R4
是本 PR 自己新立的 binding 契约，立了就不许有缺省放行的入口。

### 2.3 算术：为什么这样就不再重复计账，也不死锁

记盘上该股占 `S`，恢复前累计值 `ob`。**R4 保证这一步没有任何新增**，所以下面的算术成立。

```
恢复：      nb = ob - S                      （R2）
重拉：      added = S（两条记录重新出现）
            转移守卫要求 nb' ≥ (ob - S) + S = ob
            ⇒ 最小可接受值回到 ob            ← 与恢复前相同，不再累加
```

再崩一次重复同一算术，**累计值永远回到 `ob`**，与「崩了几次」无关。
而 E11 的死锁来自「不退还 + 占用量语义」，本修法退还了，`ob - S + S = ob` 恒成立 ⇒ 不死锁。

**固有检查仍然成立**：恢复后 `sum(files)` 也减少了 `S`，
原不等式 `ob ≥ sum_old + log` 两边同减 `S` 后仍成立 ⇒ 不需要动它。

### 2.4 明确不做

- **不动** `--max-bytes` 的语义定义、不动 D7 的「回滚退还」条款、不动固有检查。
- **不新增**任何持久化字段（故**不** bump `manifest_version`，现有 staging 不作废）。
  本仓教训：新增一层持久化状态自带三个新失效点。
- **不动** `qmt_fetch.py`（它显式拒绝 `RecoveryScope`，与本 PR 无关）。
- **不实现**恢复第③档本身（那是 S4b）。本 PR 只保证**契约正确**，使 S4b 能建在对的地基上。

### 2.5 必须同时迁移的既有测试（**穷尽枚举，实测得出**）

R2 一上，「移除记录但不退还」就成了违规，而**现有测试里有三条正是这么写的**。
它们不是误报，是 R1 缺陷在测试里的既有表征。

**枚举方法**（不靠读代码）：临时给守卫打上 R2 补丁、跑后端全套、让它自己报，
跑完把源码逐字还原并用 `sha256` 核对（`enum_affected.py`）。结果：

```
3 failed, 1617 passed

tests/test_qmt_fetch.py::test_recovery_removing_a_stock_leaves_committed_bytes_unchanged_and_is_accepted
tests/test_qmt_manifest.py::test_recovery_removal_keeps_everyone_elses_order
tests/test_qmt_manifest.py::test_recovery_removes_exactly_the_inflight_stock
```

⚠️ codex 只点到后两条；**第三条在另一个文件里**，是实测枚举补上的。
它的**名字本身**就写着「committed_bytes 保持不变是被接受的」—— 那正是本 PR 要推翻的行为，
故必须连名字一起改。

**迁移方式**（三条共同）：

- 在构造「恢复后的那一份」时，把 `committed_bytes` **减去被移除记录的字节之和**；
- **原有的不变量断言一条不删**（它们测的是 files/pool/cursor 的形状，与本 PR 无关）；
- 额外断言**落盘后的累计值**确实等于退还后的数（证明退还真的持久化了，不只是通过了守卫）。

## 3. 测试（每条都必须能红）

新增于 `backend/tests/test_qmt_manifest.py`。全部用真实夹具构造，账本形状与
`ledger`/`commit_stock` 的真实产物一致。

用例若只删条目不退游标，会先被既有的耦合检查拦下，**测不到本 PR 的判据**

| U12 | 构造 `ob < S`（账本已损坏），退还会变负 | 拦，**且拦它的是固有检查** | 表征用例：证明 `nb` 不可能为负，这就是 R3 被删掉的依据 |
| U13 | 正常的非恢复提交（新增一只股） | **放行** | R1 正向 —— 证明没把主流程拦死 |
| U14 | 重拷成功那一格（记录逐字相同、`added = 0`、`nb > ob`） | **放行** | 证明没有误伤 D7 的 `≥`（S2-F38 那条悬案） |
| U15 | 恢复提交里**完整移除 A 的同时新增 B**，`nb = ob - S_A` | 拦 | **R4**（codex 第 1 轮实测的记账旁路） |
| U16 | 同 U15，但 `nb = ob - S_A + S_B`（把 B 的字节补上） | 拦 | R4 —— **补上字节也不行**：恢复提交一律不许新增，否则 R2 的等式就不再可机械检验 |
| U21 | 旧账本**缺** `committed_bytes`，恢复时完整移除 A 的同时新增 B（不付账） | 拦 | **§2.2c 那条绕法本身**：R4 必须无条件执行 |
| U22 | 旧账本**缺** `committed_bytes`，**正常**（非恢复）提交新增一只股 | **放行** | R-B2 没被误伤 —— 收紧的只有恢复提交那一条路径 |
| U23 | 旧账本**缺** `committed_bytes`，恢复时**不**夹带（夹具顺手退得恰好对，但那不是条件 —— R5 排在 R2 之前） | 拦 | **R5** —— 这三条里只有它走得到 R5（U21 夹带新增，先撞排在前面的 R4） |

U1/U2、U3/U4、U8/U9、U13/U14、U21+U23/U22 成对存在：只有拦截用例时，「判据正确」与
「判据恒拒」无法区分（记忆 `feedback_judgment_power_two_failure_modes`）。

⚠️ **U21/U23 与 U22 的变异方向必须对上**（控制者在本片早先已经把方向用反过一次、
得出「这条用例没判别力」的假结论；本轮三发由实施者实测，记在变异记录 M10~M12）：**放宽**方向（把 R2/R4 改回原来的嵌套）只杀 U21/U23；**收紧**
方向（把 R5 从「只拦恢复提交」提到顶层变成「一律拦」）只杀 U22。
另外，把 R5 整段删掉时 U23 红的形态是 `None - int` 抛**裸 `TypeError`**（不是
`ManifestInvalidError`）—— 这正是 R5 非写不可的理由：没有它，一个合法旧账本上的
恢复提交会把守卫自己弄崩。

U10 是 R1 缺陷的**直接回归钉**：它在修复前必须红、修复后必须绿。

⚠️ **U15/U16 的夹具必须把 `committed_bytes` 抬到远高于下界**（探针里用的是 +1000 万）。
否则拦住它的可能是**固有下界检查**而不是 R4 —— 那样这条用例就测不到它要测的判据
（codex 第 1 轮明确点了这一条）。实施时必须在用例里注释写明这个余量的用途。

- 按**判据**枚举，不按语法枚举：4 条判据不是「4 个 `if`」。若某条在实现里写成别的形式

- 每次变异前后清 `__pycache__`，并带 `PYTHONDONTWRITEBYTECODE=1`。
- 把同文件的邻居用例 `deselect` 掉单独跑目标用例，证明红的是它。

**A2 的基线纪律**：先在 `origin/main` 上跑一次并记下确切数字，改完再跑，**逐条比对**，

## 9. 与本仓既有教训的对应

- 「新增一层持久化状态＝自带三个新失效点」→ §2.4 明确**不新增字段**，口子挂在既有的
  `scoped_removed` 上，不另造旁路、不 bump 版本号。
- 「写『必须 X』前先核实机制兑现得了吗」→ §1.3：写修法之前先核实「累计量不许调小」
  对恢复有没有豁免（答：没有），这一条直接决定了修法的形状。
- 「报 0 违反必须先证明它能报非 0」→ §4 A3 的逐条变异 + §3 的四对正反用例。
- 「读侧判据双向各问一次」→ U1/U2、U3/U4、U8/U9、U13/U14 成对。
- 「收紧判据会让别处理由失效」→ §2.2 末尾：R2 把这一格收成等式，必须同时证明
  **D7 的 `≥` 没被误伤**（U14）。
- 「『这两格互斥』必须由判据保证，不能由作者断言」→ §2.2b：我写「`scoped_removed`
  为真时没有任何文件被写入」，实测发现守卫根本不禁止同时新增别的股 ⇒ 那句话是
  一条**没有代码支撑的前提**，而我的等式判据正建立在它之上。补 R4 把它变成判据。
- 「反例的夹具要排除『被别的判据代为拦截』」→ U3/U11/U12/U15/U16 全部栽在这上面：
  codex 实测跑了我的夹具，发现 U3/U11/U12 都先被**固有下界**拦掉、根本到不了退款分支。
  ⇒ U3 加余量、U11 换零字节日志夹具、U12 改为表征用例。
- 「穷尽性必须按字面量枚举后逐条定性」→ §2.5：codex 点了 2 条受影响的既有测试，
  我没照着改，而是**临时给守卫打补丁跑全套让它自己报**，枚举出 **3 条**——
  第三条在另一个文件里。**靠读代码找影响面必漏。**
- 「不为不可能的场景写错误处理」→ R3 被删：固有检查保证 `nb ≥ 0`，那条判据永远
  执行不到。**是 codex 跑夹具跑出来的，不是读代码读出来的。**
- 「同一类缺陷反复出现＝方案选错，解法是塌层 + 去开关」→ §2.2c：R4 被挂在一个它压根
  用不到的 `ob` 开关后面，修法不是在旁边补一条检查，而是把那一层塌掉。
- 「『它挡得住 X』必须实测」→ §2.2b 写下 R4 时，我默认它「只要 `scoped_removed` 为真
  就会执行」，没去跑「上一份缺 `committed_bytes`」这一档；codex 第 1 轮跑了，
  R4 在那一档**根本不执行**（有基准时它确实在拦，U15/U16/U19 为证）。
  **R4 这条判据本身是 codex 挖的，它失效的那一档又是 codex 挖的。**
- 「先用探针把问题跑出答案」→ §1.2/§1.3 两组数字都是探针跑出来的，不是读代码推断的；
  探针还当场纠正了我一个构造错误（忘了退游标）。
