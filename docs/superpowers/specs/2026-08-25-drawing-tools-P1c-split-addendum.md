## 0. 本文件是什么

拆分补充 §8 逐字要求：

> **P1c 不是一个已授权的 PR 边界（codex R12/R13-high）**：~1400 行 / 五个风险面（多锚泛化 · 节点模型 · 节点拖动手势 · 四个工具几何 · 折线临时 4 键），**明确超出「≤3 子项 / ≤500 行」**。本 spec **不拆它** —— 它尚未设计，切一个不存在的 PR 是空想。
> **硬性要求**：进入 P1c 的 spec / plan 阶段前，**必须先按同样方法把它拆成若干各自可 ship、各带负向测试与验收清单的顺序 PR**。……**任何实现者都不得把 P1c 当作一个 PR 来做。**

本文件就是那份拆分。它**不是**任何一片的实施 spec —— 六片各自还要走 `superpowers:brainstorming` → 自己的 spec → `superpowers:writing-plans` → `codex:adversarial-review` → 实施 → whole-branch 评审 → PR。

本文件**只做四件事**：① 定切分线与顺序；② 把上游留给 P1c 的未决问题拍板（D104–D111）；③ 把上游三处不准确的事实陈述订正掉；④ 列出各片 spec 必须回答的遗留问题。

## 0.1 为什么必须拆（体量实测，非估算）

拆分补充 §8 给的估算是 **~1400 行**。实测标定说明这个数字明显偏低：

| 标定物 | 实测 |
|---|---|
| 最简单的工具（水平线，**1 锚 / 无填充 / 无节点**）本体 | `Drawing/HorizontalLineTool.swift` = **105 行** |
| 同一工具的测试 | `Drawing/HorizontalLineToolTests.swift` = **351 行** |
| 已合并划线 PR 的真实体量（`git show --stat`） | #153 `f3f67da` = 408 行；#154 `f21cca1` = 1473 行；#156 `46fba04` = 1056 行；#159 `baca047` = 1899 行；#163 `371b870` = 110 行 |

一个工具（含测试）落在 **400–600 行**，而 P1c 有 **四个**工具、且其中三个比水平线复杂（趋势线 3 种线型子类几何、通道线 3 锚 + 平行线 + 填充带、折线不定锚数）。加上节点模型、拖节点手势、跨版本兼容地基与三组举证测试，本 spec 估 **5000–7000 行**。

**这个数字是拆成六片而不是四片的直接依据**，也是 1b-i 的复现（原估 400 行，最后切成四个 PR 才把 codex 评审收住）。

## 1. 拆分结论（决策表 D104–D111）

### D104　跨版本兼容策略 = ③受保护的未支持数据 + ①记账（bump 只是账本）

拆分补充 §8「P1c 的契约地位（未决）」给了三选一。**user 2026-08-25 拍板选 ③，并叠加 ① 作为记账。**

**选 ① 单独不成立的实测依据（本 spec 订正上游）**：`CONTRACT_VERSION` 在本仓**没有任何运行期效力**。

- 定义在 `ios/Contracts/Sources/KlineTrainerContracts/Models/Models.swift:7`，当前值 `"1.13"`。
- 全仓 `grep -rn "CONTRACT_VERSION\|contractVersion" ios --include='*.swift'` 的**全部**命中点只有三类：常量定义本身、**测试**里的等值断言（`ModelsTests.swift:8`、`RenderStateBuilderTests.swift:1260`）、以及治理文档矩阵同步守卫（`M01MatrixSyncGuardTests.swift`）。**没有任何一条加载 / 解码 / 迁移路径读它并据此拒绝或告警。**
- 数据库侧的 `PRAGMA user_version`（app.sqlite 当前 = **8**，`AppDBMigrations.swift:253`）同样不构成版本门：迁移是**单向前进**的（`if version < N` 逐级执行），一个只认识到 7 的旧构建打开 `user_version == 8` 的库时，只是**一条迁移都不跑**，既不拒绝也不告警。

⇒ **bump `CONTRACT_VERSION` 是给人看的账本，不是运行期的门。** 拆分补充 §8 的选项 ① 若单独采用，老构建的行为一字不变。本 spec 因此把 ① 降格为「记账义务」，真正的机制全在 ③。

**⛔ 任何后续实现者不得援引本条把 bump 省掉** —— 记账义务仍是义务（m01 契约 §Bump 策略 + CODEOWNERS 门），只是不得**冒充**为兼容机制。

### D105　「本版本不支持的画线」是**一个统一概念**，覆盖两类，四条不变量 + 一道显式 UI 门

**两类**（**必须同一套机制处理，不得各写一份判据**）：

| 类别 | 成因 | 今天的表现 |
|---|---|---|
| **(a) 可解码、本构建无渲染器** | `toolType` 是**已声明**的枚举 case，但 `KLineView.drawingTools` 注册表里没有它。P1b 时代的构建看 P1c 写的 `.trend` 就是这一类。 | `KLineView+Drawing.swift:25` 的 `guard let tool = tools[drawing.toolType] else { continue }` **静默跳过**；`DrawingHitTester.firstHit`（`DrawingHitTester.swift:26`）对同一条件**返回 false**。用户什么都看不到、也选不中。 |
| **(b) 不可解码** | `toolType` 是本构建**根本不认识**的字符串（未来加的第 12 个工具），或结构损坏。进 `LossyDrawingArray` 的 `.unknownRaw` 分支。 | 连 `engine.drawings`（已知投影）都进不去 —— 用户既看不到、也**无法删除**。 |

**四条不变量（对两类同时成立）**：

1. **不渲染**（已有行为，保持）。
2. **不可命中**（已有行为，保持）—— 画不出的就选不中，与渲染 dispatch 逐字同判据（1b-i spec §8 #2）。
3. **不被普通保存覆盖**（已有行为，保持）—— `LossyDrawingArray.reconciled(currentKnown:)` 对未编辑的 `.known` 条原样回写 `raw`（`LossyDrawingArray.swift:347-348`），对 `.unknownRaw` 原位保留（`:354-355`）。
4. **⭐不阻止归档**（**新增，本片要做**）—— 见 D105b。

**一道显式 UI 门（新增，本片要做）**：画线模式内一处可见提示「本局有 N 条画线本版本不支持」+ **整条删除通道**。删除通道必须同时够得着 (a) 与 (b)；(b) 的条目**不在 `engine.drawings` 里**，故删除入口**不能**建在 `deleteDrawing(id:)` 上（那条路按 id 在 `drawings` 里找，对 (b) 恒 no-op）。

**⛔ 本条推翻「今天的静默 `continue` 就够了」这一默认**（拆分补充 §8 逐字：「**不得**是今天的『静默 `continue`、用户无感』」）。

### D105b　`finalize` 那道门的**精确**形状（本 spec 订正 1b-ii §4 残留②的表述）

**门在哪**：`TrainingEngine/TrainingSessionCoordinator.swift:741-745`

```swift
if !effectiveLossy.unknownRaw.isEmpty
    || effectiveLossy.hasKnownFutureFields(liveIds: liveIds)
    || effectiveLossy.hasKnownFutureEnumValues(liveIds: liveIds) {
    throw AppError.persistence(.dbCorrupted)     // 拒绝归档，且不清 pending
}
```

1b-ii spec §4 残留② 写的是「……`finalize` 门则会因未来数据 `throw`」。**逐条核实后，这句话对 P1c 的场景不成立**：

- 一条 `.trend` 线**不是** `unknownRaw` —— `.trend` 在 `Models.swift:39` 已声明，能正常解码成 `.known`。
- `hasKnownFutureFields` 只探测 `knownDiskKeys` **之外**的额外顶层字段（`LossyDrawingArray.swift:191-216`）。P1c 不新增字段 ⇒ 不命中。
- `hasKnownFutureEnumValues` 查的是一张写死的表 `enumKeyValidValues`（`LossyDrawingArray.swift:261-269`），表内是 `period / lineSubType / lineStyle / colorToken / labelMode / textForm / textColorToken` —— **`toolType` 不在这张表里**。⇒ `.trend` 这个值永远不会被当成「未来枚举值」。

⇒ **一条纯 `.trend` 线（不带未来字段、不带未来枚举值）在今天的构建里归档是能过的。** 残留②里成立的那一半是前半句：**选不中 ⇒ 解不开锁、删不掉**。后半句只在「那条线**同时**还带着未来字段 / 未来枚举值」时才成立，**不是**「非水平线」本身导致的。

**⛔ 各片 spec 不得照抄 1b-ii §4 那句原话**，一律引本条。

**顺带挖出的更深的洞（user 2026-08-25 拍板由第 1 片一并堵上）**：那道门的**第一个**条件 `!effectiveLossy.unknownRaw.isEmpty` 是**无条件**的 —— 另外两个条件都经 `liveIds` 过滤（用户删掉那条线即放行，`hasKnownFutureFields(liveIds:)`/`hasKnownFutureEnumValues(liveIds:)` 的 `liveIds.contains($0.id)`），唯独它没有。而 `.unknownRaw` 条目：

- 不在 `engine.drawings` 里 ⇒ 用户选不中、删不掉；
- `reconciled` 对它**无条件原位保留**（`:354-355`）⇒ 保存路径也抹不掉。

⇒ **一条 (b) 类画线一旦躺进存档，这一局永久归不了档，且用户没有任何可达出口。** 代码注释自己承认的出口是「用户须用**支持这些工具的更新版本 app** 打开本条 pending 才能真正 finalize」（`TrainingSessionCoordinator.swift:701-702`）—— 即**降级安装的用户被永久卡死**。

这个洞**不是 P1c 造出来的**（P1c 只写已声明的枚举值，产不出 `.unknownRaw`），今天也不可达（App 未上架、不存在更新版本）。但它与 D105 是同一件事的两半，分两次做会导致第 1 片的 UI 日后被推倒重来。**故并入第 1 片。**

### D106　画制中间态 = 只显示**已落的锚点** + **已落锚点之间的连线**；**无跟随手指的预览段**

user 2026-08-25 逐字定义（原话）：

> 折线画的时候是点第一个点，然后在点第二个点之前的话，就只显示第一个点。然后点第二个点落成之后，那它之间就把那个线自动的补上去。就是落那个第二个点的时候，同时那个线就画出来了。然后再点第三个点，第三个点落之前的话，第二个点跟第三个点之间是没有任何东西的，那点到第三个点的时候，这个线也随之生成。以此类推

**规则**：屏幕上**永远只有「已经确定下来的锚点 + 已经确定下来的线段」**。手指当前位置**不参与任何渲染**。

**本条推翻可视化稿**：`2026-07-03-drawing-tools-expansion.html:2147-2178`「折线画到一半（临时底栏）」那张图里，除三个已落锚点的实线折线外，还从最后一个锚点拉出一条 `.lineAux`（灰色虚线）到第四个位置，caption 原文：「**虚线段是当前正跟随手指的预览段**」。

**推翻理由（两条，第二条是硬约束）**：

1. 触屏没有「悬停」。手指不在屏幕上时不存在「当前位置」；要真做出跟随，落锚就必须从**单击**改成**按住拖动**。
2. **改成拖动会与 1a-iv 的 D32 正面冲突** —— `GestureClassifiers.swift:92-94` 的头注逐字写着「本函数与画线状态完全无关 —— 画线模式下单指横滑照常平移、竖直甩动照常出 `periodSwipe`。旧的 `drawingTakesOver` 截获参数已连同 `DrawingModePanPolicy` / `panPolicyInDrawingMode` **原子删除**，使『画线吞掉平移』这一状态**不可表达**（结构守卫 `DrawingGestureSourceGuardTests` 钉死）」。让画制期的单指拖再次有语义，等于把那条刚被结构性消灭的状态请回来。

可视化稿那张图属于**画稿阶段带进来的鼠标习惯**，非产品意图。

**⛔ 各片 spec 与实施者不得援引 `2026-07-03` 那张图要求实现橡皮筋预览。**

### D108　选中态视觉 = **取消「线变蓝」**，选中 ⇔ 显示节点 + 底栏 🗑/🔒 由灰变亮

**本条推翻拆分补充 D27 的前半句。** D27 原文（`2026-07-10-drawing-tools-P1b-split-addendum.md:47`）：

> **D27 选中态视觉（1b-i）**：选中态 = **线渲染为选中蓝** + 底栏 🗑/🔒 由灰变亮，**不显节点圆**。**P1c 补上两端 / 各转折点的实心圆节点。**

D27 的原意是「P1c 在变蓝的基础上**加**节点」（可视化稿 `:2100` 那条线显式带 `style="stroke:var(--blue)"`，caption 亦写「线变蓝，两端显示带蓝色外圈的实心圆节点」）。user 2026-08-25 改为「**取消变蓝、只靠节点**」。

**理由（user 提出，本 spec 认可）**：线变蓝会**盖掉用户自己给这条线设的颜色**。用户特意把一条设成红色、另一条设成绿色，一旦选中全变蓝 —— 而**样式面板此刻正显示着「红色」让他改**，屏幕上却是蓝的。有了节点之后「哪条被选中」已有明确视觉信号，变蓝成了冗余且有害的一层。

**保留不变**：D27 的后半句（底栏 🗑/🔒 由灰变亮）**照旧**。选中反馈 = 节点 + 底栏键活化。

**落点**：与「显示节点」**必须同片**（第 2 片）。分开做会产生一段「变蓝已拿掉、节点还没有 ⇒ 选中一条线屏幕上完全无反馈」的中间形态。

**⚠️ 本条会改动已合并的 1b-i 行为**（`DrawingColorResolver.selectionRGBA` 那条路 + `HorizontalLineTool.render` 的 `isSelected` 分支 + 相关测试与验收条目）。第 2 片是 P1c 里**唯一**一片「改已有行为」而非「纯新增」的，其 spec 必须逐条列出被推翻的 1b-i 测试与验收项。

**⚠️ 遗留问题（第 2 片 spec 必须回答，见 §10-Q1）**：水平线（含其 `.ray` 子类）是**唯一**一个「几何范围远大于锚点范围」的工具 —— 线横贯全图（或自落点直到右缘），锚点却只有 **1 个**、钉在落点那一个 x 上。

**画完的那一刻锚点必然在屏幕上**（它就是用户手指点的位置，user 2026-08-25 指正了本条初稿的含糊表述）。**问题出在事后**，而「事后」在本 App 里是常态而非边缘情况：

- **训练推进（主因，已实测）**：`RenderStateBuilder.geometryCore` 的视口起点是 `baseStartIndex = currentIdx - (visibleCount - 1)`（`RenderStateBuilder.swift:131`）。`currentIdx` 每推进一根 +1、`visibleCount` 不变（默认 **80**，`RenderStateBuilder.swift:13`）⇒ **每推进一根 K 线，固定的 `candleIndex` 在屏幕上就左移一格**。
  ⇒ **画完一条水平线后再推进 80 根，锚点即彻底出屏**（默认缩放）。一局训练动辄推几百根 —— 故**每一条早期画的水平线最终都会进入这个状态**，用户什么都没做。
- **平移**：1a-iv 已放开画线模式内的单指横滑平移，画完接着滑图是自然动作。
- **`.ray` 子类同样中招**：`HorizontalLineTool.lineXRange` 对射线返回 `(max(frame.minX, anchorX), frame.maxX)`（`HorizontalLineTool.swift:59`）—— 锚点滚出左缘后线被夹到左边框，**线照样横贯整屏、锚点却不在**。

于是产生这个状态：**线清清楚楚在屏幕上、点它也确实选中了，但屏幕上没有任何变化** —— 唯一的选中标志在看不见的地方，只有底栏 🗑/🔒 亮着（而用户的视线正在线上）。

**其余四个工具没有这个问题**：它们的几何就在锚点附近，锚点出界时线也一起出界，不会出现「线在、标志不在」的错位。

### D109b　本 spec 对拆分补充 §8 建议缝的**三处修正**（逐条给理由）

拆分补充 §8 的建议缝是：「①多锚泛化 + 趋势线 ②通道线 + 箱体 ③折线 + 画制中临时 4 键 ④节点模型 + 拖节点 + §14 节点拖动分支」。

**修正 A：节点模型与拖节点整体前移到工具之前（④ → 2、3）。**

1. **节点不是每工具一张表，而是一条通用规则**（见 D111）：节点 ≡ 该线的 `anchors` 投影到屏幕坐标。母 spec §5.11「两锚为节点」、§5.3 三锚三节点、§5.4「每个转折点」三处一致。⇒ 节点模型**不需要**等工具齐了才能做。
2. **D108（取消变蓝）与「显示节点」必须同片**，而变蓝是**今天就在跑的行为** —— 越晚做，中间形态存在得越久。
3. **最高风险的手势面应在几何最简单时吃掉**。第 3 片落地时只有水平线、**1 个节点**，且拖它是真实有用的功能（今天已画好的线**改不了价位**，只能删了重画）。后续每个工具片只需追加「拖它的第 N 个节点」的测试，不必回头改手势。按原顺序，④ 要**一次性**面对四种工具的节点语义 —— 那正是 1b-i 栽过的形状。

**修正 B：折线必须排在节点之后（③ 与 ④ 对调）。**
折线的「选中时每个转折点显示可拖的实心圆节点」（可视化稿 `:1636` caption）与「删单节点」（母 spec §7 删除分支）**都依赖节点模型**。拆分补充建议的 ③ 在 ④ 之前，在依赖上是**反的**。

**修正 C：新增第 1 片「跨版本兼容地基」。**
拆分补充数的是五个风险面，未把**样式矩阵**单列。实测：`Drawing/DrawingStyleAvailability.swift` 整份**只有水平线一行** —— `toolsWithStyleMatrix: Set<DrawingToolType> = [.horizontal]`（`:30`），且该常量的头注逐字警告：

> ⚠️ P1c 给新工具接线时：加进 `DrawingToolType.implemented` 之后它就能画了，但**样式仍改不动**，直到你为它写出子类型/标注矩阵并加进本集合 —— 这个方向的漂移是 **fail-closed**……

这块加上 D104/D105 构成独立的第六面，且它必须在**第一条非水平线存盘之前**生效 ⇒ 只能排第一。

### D110　交付方式 = **逐片合入 `main`**，不叠罗汉

**实测依据**：`.github/workflows/hardening_6_gate.yml:8-10`

```yaml
on:
  pull_request:
    branches: [main]
```

该工作流的 `acceptance` 任务是分支保护的**必需检查**，而它**只在 base 为 `main` 时触发**。叠罗汉 PR（base 指向前一片的分支）会让该检查**永不上报状态** ⇒ PR 永久 BLOCKED，只能靠 `gh pr close <n> && gh pr reopen <n>` 手动补触发（P1b 后三片的实况）。

**顺带收益**：每片的 codex 评审 base 恒为 `origin/main`，不再出现「以 main 为基准评审会把前一片的改动当成本片删的」那类整批假 finding。

**代价**：**串行**。第 N 片合进 `main` 之前，第 N+1 片不开工。

**⛔ 六片一律 `--scope branch-diff --head <本片分支> --base origin/main`，不得传任何窄化参数（含 `--help`）。**

### D111　节点 ≡ `anchors` 的屏幕投影（通用规则，非每工具一张表）

母 spec §6 把工具分成「有节点」与「无节点」两类：

- **有节点**：水平线、趋势线、通道线、折线、黄金率、波浪尺、时间尺、箱体、标注（节点 = 气泡尾巴尖）
- **无节点**：周期线、斐波那契（靠拖线本身交互）

**除标注外**，「有节点」类的节点位置**全部**等于 `drawing.anchors` 逐个经 `CoordinateMapper`（`indexToX` + `priceToY`）投影到屏幕。标注是唯一例外（节点 = `tailAnchor`，母 spec §5.10/D11），**属 P3，不在 P1c 范围**。

⇒ 第 2 片建立的是**一个工具无关的纯函数** + **一张「哪些工具有节点」的登记表**，而不是每工具一份几何。P1c 范围内该表只需登记水平线 + 四个新工具；周期线 / 斐波那契 / 时间尺 / 黄金率 / 波浪尺 / 标注属 P2/P3，**第 2 片不得替它们做决定**（同 `isRenderableSubType` 的 over-reject 教训：把只对某类型成立的规则套到所有类型）。

## 4. 第 3 片：拖节点 + §14 手势分支

**一句话**：让节点真的能拖，把母 spec §14 剩下的那一条分支补完。

### 4.1 做

1. **§14 的节点拖动分支**：单指起手若**落在选中线的某个节点上** → 进入节点拖动；否则**一字不变**地走 D32 建立的方向分流（横滑平移 / 竖甩切周期 / 双指缩放）。
2. **拖动实时跟随**：拖动过程中该线几何实时更新。
3. **引擎第 5 个 `drawings` 写入 API**（改某条线的某个锚点）。
4. **进撤销栈**：一次完整的拖动（起手到抬手）= **一条** `.replaced` 记录，不是每帧一条。

### 4.2 不做

局部放大镜与吸附（母 spec §9，属 P4）；折线删单节点（第 6 片）；四个新工具；节点选中态。

### 4.3 必须存在的负向测试

- **P1c-3-N1「D32 不得回退」**：画线模式下、**没有**选中任何线时，单指横滑仍平移、竖甩仍切周期、双指仍缩放。⚠️ 这是 1a-iv 的核心成果，本片是**唯一**有能力打破它的一片。
- **P1c-3-N2「选中了但没落在节点上」**：有选中线，起手落在**离节点很远**的地方 → 走方向分流，**不是**节点拖动。
- **P1c-3-N3「落在未选中线的节点位置上」**：另一条**未选中**的线恰好在起手点有个节点 → **不进入节点拖动**（节点只在选中态存在，母 spec §6）。
- **P1c-3-N4「一次拖动 = 一条撤销记录」**：拖动经过 N 帧 → 撤销栈里只有 **1** 条；点 ↩ 一次，线**整个回到拖动前**。⚠️ 必须断言栈深度**和**回滚后的坐标，只断言深度会撞「空栈」假绿。
- **P1c-3-N5「引擎写入点穷尽性守卫同步」**：新增写入 API 后，`DrawingUndoSourceGuardTests` 的两处判据（L12b 总数、U-G4 逐函数表，现按 **10** 钉死，见 `DrawingUndoSourceGuardTests.swift:291-301`）**必须同步**，且新 API 在 U-G4 的表里**有自己的一行**。
- **P1c-3-N6「锁定的线拖不动」**：`locked == true` 的线选中后，节点**拖不动**（与 D60 的写入门同族）。
- **P1c-3-N7「拖出可见范围」**：把节点拖到主图之外 → 行为必须**确定**（拒绝 / 夹回边界，由本片 spec 定），且**不得**产生 `visibleGeometry == nil` 的幽灵线（同 1a-i 的 fail-closed 纪律）。
- **P1c-3-N8「拖动中切周期 / 转屏」**：拖到一半发生视口变化 → 不得写出混周期锚点（复用 `DrawingSession.commitPending` 的同周期守卫，`DrawingSession.swift:254-258`）。

## 7. 第 6 片：折线 + 画制中临时 4 键 + 删单节点

**一句话**：P1c 最复杂的一片 —— 唯一不定锚数的工具、唯一的第二套撤销、唯一会换掉底栏的形态。

### 7.1 做

2. **不定锚数提交**：`requiredAnchors` 对折线是**开区间**语义，靠「完成划线」显式收尾。

5. **节点选中态**：「当前选中了哪一个节点」—— 删单节点需要它。第 2 片只做了「命中哪一个」的纯函数，本片把它变成一个**状态**。
6. **折线删除的三选一**：选中了某个节点时，🗑 弹 `[删除选中节点] [删除整条划线] [取消]`（母 spec §7）；删节点后折线**自动重连**。

## 11. 契约 / 闸门 / 交付方式

### 11.1 契约

| 片 | `CONTRACT_VERSION` | `user_version` | 迁移 |
|---|---|---|---|
| **1** | **bump**（D104 的记账义务；同步 m01 矩阵与 bump 记录） | 不变（**8**） | 无 |
| **2–6** | 不变 | 不变（**8**） | 无 |

**依据（逐条给出，不用「只写入 X」这种笼统说法）**：

- 第 2–6 片**不新增任何 `DrawingObject` 字段**：四个工具用的 `toolType` 全部**已在 1.11 声明**（`Models.swift:39` 的 11 个 case），`anchors` 是既有数组列，样式字段自 P1a 迁移 0009 起就在 `style_json` 里往返。
- 第 2–6 片**不扩展任何枚举值域**。
- **为什么 bump 落在第 1 片、而不是首次写出 `.trend` 的第 4 片**（本条 load-bearing，D8「避免多次 bump」的直接后果）：
  - 第 1 片**确实改变了既有语义** —— `finalize` 那道门的行为变了 + 多了一条能删「用户够不着的数据」的通道。这本身就命中 m01 §Bump 策略的 **A 类「改既有语义」**（先例：E2 的 1.4→1.5「reader 侧收紧语义、无 DDL 变更」）。
  - 第 4 片写出第一条 `.trend` **不构成契约变更**：`.trend` 自 **1.11 起就是已声明的 case**（`Models.swift:39`），不扩展值域、不新增字段、不改既有 key 的含义。按 1b-ii §3 建立的同一套逐条论证，这一条**不该**单独触发 bump。
  - 故**一次 bump 覆盖两个理由**：m01 的 bump 记录里必须**同时载明**「①`finalize` 未支持数据处置语义变更（A 类）；②自本版本起，本 App 具备『受保护的未支持数据』机制，且 P1c 后续切片将开始写入 `.trend / .channel / .rect / .polyline`」。第二句就是 D104 里 ① 那份记账义务的**落点** —— 它记的是「机制从哪个版本开始存在」，比记「哪个版本开始写新工具」更有用。
- **⛔ 本表任何一行都不得被援引为「P1c 不用 bump」的依据** —— 第 1 片必须 bump，且必须写全上面两句记录。

### 11.2 三绿门（每片作者亲核，clean build）

沿拆分补充 §10 的既有规则，**强度按该片是否含 `#if canImport(UIKit)` 测试而定**：

- 含 UIKit-guarded 测试 → Catalyst 必须 **`xcodebuild test`（真执行）**。host `swift test` 在 macOS 上 `canImport(UIKit) == false` 会整份跳过，`build-for-testing` 只编译不跑，二者都验不了 UIKit 渲染路径。
- 纯 host 测试 → Catalyst `build-for-testing` 即可。
- **凡渲染路径断言，其决策逻辑仍必须另有 host 可测纯函数覆盖**（不把 UIKit gate 当唯一防线）。

**P1c 的实际情况**：第 2、3、6 片**必然**含 UIKit-guarded 测试（节点渲染 / 手势 / 底栏换栏），第 4、5 片的几何主体可做成 host 可测纯函数、只有 render 薄层进 UIKit。

**⚠️ 新增 UIKit-gated 测试必须同步四处 Catalyst 基线**，取数用 CI 同款 `-only-testing:KlineTrainerContractsTests`，且喂闸门的日志**必须冷构建**（用 `mktemp -d` 的专属 `-derivedDataPath`；⛔ 绝不删全局 DerivedData —— 本仓有 20 个 worktree）。

### 11.3 交付方式（D110）

- **逐片合入 `main`**，不叠罗汉。第 N 片合进 `main` 之前，第 N+1 片不开工。
- 每片：独立 worktree（`.dev/worktree/<名字>`）→ 自己的 spec → `superpowers:writing-plans` → `codex:adversarial-review` 收敛 → 实施 → 三绿 → `superpowers:requesting-code-review` + whole-branch codex → PR。

### 11.4 变异验证纪律（P1b 三片换来的，逐条适用于 P1c）
