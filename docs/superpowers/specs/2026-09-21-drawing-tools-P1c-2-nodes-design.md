### D121　节点绘制落在**一处工具无关的实现**，不是每工具一份

承上游 **D111**（「第 2 片建立的是一个工具无关的纯函数 + 一张登记表，而不是每工具一份几何」）。本条把它从「几何」推广到「绘制」，并给出落点约束。

**结论**：节点与代理标记的**决策与绘制**都集中在一处，由渲染 dispatch 在 `tool.render` 之后调用一次；⛔ 不得写进任何具体工具的 `render` 里。

**落点的硬约束（load-bearing，决定本片要不要动 Catalyst 基线）**：

| 若把这一处写在 | 后果 |
|---|---|
| `Render/KLineView+Drawing.swift`（`extension KLineView`，整文件在 `#if canImport(UIKit)` 内，`:7`） | 像素级测试**只能在 Catalyst 上跑**；host `swift test` 在 macOS 上 `canImport(UIKit) == false` 会整份跳过 ⇒ 每加一条断言都要同步四处 Catalyst 基线 |
| 一个**只依赖 CoreGraphics** 的新文件（`Drawing/` 下，与 `HorizontalLineTool.swift` 同族） | host `swift test` **真跑**像素断言 |

**实测依据（本条的前提，已核实）**：`ios/Contracts/Tests/KlineTrainerContractsTests/Drawing/HorizontalLineToolTests.swift` **全文件零 `#if canImport(UIKit)`**（`git grep -c 'canImport(UIKit)'` 对该文件返回 0），却含 `renderPixelsSelected`（`:290`）这样把 `CGContext` 画进 bitmap 再逐像素比对的断言 ⇒ **CoreGraphics 的像素级渲染测试在 host 上是跑得起来的**，UIKit 不是必要条件。

⇒ **本片新增的渲染断言绝大多数落在 host 层**；Catalyst 基线的改动被压到最小（见 §8.4 的精确清单）。

**⛔ 本条不规定新文件叫什么名字、函数怎么签名** —— 那是 plan 的事。本条只规定两件**结果**：① 决策与绘制集中在一处、工具无关；② 那一处不得只能在 UIKit 下编译。

### D122　「哪些工具有节点」登记表：本片**只登记水平线一行**

**上游 D111 原文**：「P1c 范围内该表**只需**登记水平线 + 四个新工具；周期线 / 斐波那契 / 时间尺 / 黄金率 / 波浪尺 / 标注属 P2/P3，**第 2 片不得替它们做决定**。」

**本 spec 的读法（明写出来供评审挑）**：「只需登记水平线 + 四个新工具」是**范围上界**（划定第 2–6 片合起来可以动的集合，禁止越界去替 P2/P3 决定），**不是**要求第 2 片当场把五个都写进表里。

**因此本片表里只有水平线一行。** 逐条理由：

1. **四个新工具今天画不出来。** `DrawingToolType.implemented`（`Models/Models.swift:50`，实测 `= [.horizontal]`）与生产渲染注册表都还没有它们 —— 第 1 片的 `KLineViewCompileTests.swift:39`（L8c）正是**钉死「生产注册表里确实没有 `.trend`」**的守卫。给一个渲染不出来的工具登记「它有节点」，是一张兑现不了的空头支票。
2. **第 1 片刚刚确立了同构的形状，本片照抄、不另立规矩。** `DrawingStyleAvailability.styleRules`（`DrawingStyleAvailability.swift:35-38`）表里今天也**只有水平线一行**，配一条漂移告警：新工具进了 `implemented` 却没在表里加行 ⇒ 断言当场红（该文件 `:31-34` / `:50-58` 头注逐字记载）。
3. **方向是 fail-closed 的。** 忘了加行 ⇒ 现象是「新工具选中了却不显示节点」，一眼可见、不污染任何持久化数据；反过来（预先登记、工具却没实现）是 fail-open，会让第 4/5/6 片的实现者误以为节点已经接好。

**⛔ 本条的漂移告警必须写成集合等式，不得写成存在性检查**（上一片评审挖出的那类缺陷）：

- ⛔ **禁止**：「断言水平线在这张表里」「断言这几个工具各自都在表里」—— 这类判据对「表里**多出来**第五个不该有的工具」**判别力为零**。
- ✅ **要求**：断言 `本表的键集合` 与 `另一张已建立的单一真相的键集合` **相等**（`==`，两个方向同时成立）。具体拿哪张表做对照由 plan 定，但**必须是集合相等**。

**⛔ 本条同时是给 plan 的约束**：这条弱化极易在 plan 阶段就被写进代码块然后被照抄（本仓已有记录的形状）。plan 里若出现节点登记表的断言代码块，**它必须已经是集合等式**；实施时若改了实现，plan 必须同步改。

### D123　Q1 的答案：锚点出屏时补画**代理标记**（user 2026-09-21 拍板）

**上游 §10-Q1 原文**给了三个候选：① 锚点出界时在可见段内补画代理标记；② 给选中态加一种不改变线色的强调；③ 接受现状只靠底栏键。**user 2026-09-21 选 ①。**

**落选理由（逐条记录，防止后续评审轮次重提）**：

| 候选 | 为什么没选 |
|---|---|
| ② 不改线色的强调（外晕 / 加粗） | 它要推翻 `selectionChangesColorOnly`（`HorizontalLineToolTests.swift:326`）钉死的「选中不得改变线宽 / dash / 几何」，而该测试**本片本来就要改**（§7），所以这不是决定性的；真正的理由是**语义成本**：D107/D108 刚把选中态收敛成「节点」**一种**信号，再加一层强调就变回两种；且「加粗」与用户自己设的 thickness（1–5 档，`HorizontalLineTool.swift:34`）语义直接打架 |
| ③ 接受现状 | 上游 D108 末段已自行论证它**不是边缘情况**：训练一局推几百根，`baseStartIndex = currentIdx - (visibleCount - 1)`（`RenderStateBuilder.swift:131`）、`defaultVisibleCount = 80`（`:13`）⇒ **每推进一根，固定的 `candleIndex` 在屏幕上就左移一格；推进 80 根后锚点必然出屏**。⇒ 每一条早期画的水平线最终都会进入「线在、记号不在」的状态，用户什么都没做 |

**候选 ① 的具体形状（user 2026-09-21 逐项拍板）**：

| 项 | 决定 |
|---|---|
| **形状** | **小三角，尖头指向屏幕外**（锚点在左侧屏外 → 尖头朝左；在右侧屏外 → 尖头朝右） |
| **为什么不是空心圆** | 与实心圆节点**形状同构**，在 7pt 量级上「实心 / 空心」的区分度太低，用户会伸手去拖它 —— 而第 3 片上了拖动之后，「拖不动」必须是一眼可见的，不能靠看填充 |
| **位置** | 贴在**线与主图边框的交点**上。左侧出屏 → 主图左边框；右侧出屏 → 主图右边框 |
| **颜色** | 与节点同族：日间纯黑、夜间纯白。⛔ **不跟线的颜色走** —— 它属于「选中记号」这一家，不是线的一部分 |
| **何时出现** | **仅在**「选中态」**且**「真节点画不出来」时。锚点一旦回到屏幕内，代理标记立刻消失、真节点接管 |
| **可不可拖** | **不可拖。** 本片不接任何手势；第 3 片接拖动时，代理标记处必须落到「平移图表」分支，**不得**被当成节点 |

**⛔ 本条继承上游 Q1 的硬约束，原样有效、不得削弱**：代理标记是一个**额外的视觉标记**，**绝不允许把真节点挪到可见处**。「锚点绑定的 K 线永不改变」是持久化不变量；节点是可拖的，画在一根不属于它的 K 线上会让拖动语义立刻失真。**真节点该在哪就在哪，出界就是不画。**

**水平线只有 1 个锚点 ⇒ 永远只会有一侧出现代理标记**，不会两端都有。多锚工具（第 4/5/6 片）可能两侧都有，**本片不替它们做决定**。

### D124　Q7 的答案：节点容差与线容差**各自一份**；节点视觉直径 7pt、命中半径 11pt

**上游 §10-Q7 原文**：「节点的命中容差与线本身的命中容差（水平线现为 8pt，`HorizontalLineTool.swift:24`）是同一个值还是各自一份？两者若相同，节点附近会出现『想拖节点却选中了线』的歧义。」

**答：各自一份。** 理由不是「想分开」，而是**两者的量纲不同**：

| | 线的容差 | 节点的容差 |
|---|---|---|
| 判据 | `abs(point.y - g.y) <= 8` **且** x 落在线段区间内（`HorizontalLineTool.swift:103`） | 点到节点中心的**欧氏距离** ≤ r |
| 维度 | **一维**（只看纵向偏差；横向是区间归属，不是容差） | **二维**（圆盘） |

用同一个数字同时表达一维带宽和二维半径，是巧合，不是设计。

**数值（user 2026-09-21 拍板）**：

| 量 | 值 | 依据 |
|---|---|---|
| 节点**视觉**直径 | **7pt** | 线宽档 1–5 = 1.5 / 2.0 / 2.5 / 3.0 / 3.5pt（`HorizontalLineTool.swift:34`）⇒ 7pt 是最粗线的 2 倍，满足 D107「与线连成一体」又看得出是个点 |
| 节点**命中**半径 | **11pt** | 见下面那条不变量 |
| 代理标记尺寸 | 外接尺寸与节点直径**同量级**（7pt 级）；精确形点由 plan 定 | 同族视觉，不另立尺度 |

**⚠️ 交互稿没有给出可用的节点尺寸（已核实，本条据此自行定值）**：`docs/superpowers/mockups/2026-07-03-drawing-tools-expansion.html` 里节点写的是 `r="1.1"`（`:1391` 等 38 处），但承载它的 `<svg>` 是 `viewBox="0 0 100 100"` **加 `preserveAspectRatio="none"`**（`:1389`）—— 横纵各自拉伸，圆实际会被画成椭圆。⇒ 那个 `1.1` 是稿内示意值，**换算不出真实 pt**。同上游 Q6「可视化稿只给了『淡色半透明』『极淡』，没给数值」的处境。

**⛔ 本片必须建立的不变量（这才是 Q7 真正要消解的东西）**：

> **以节点中心为圆心、半径 = 线容差（8pt）的圆盘内，凡是线命中的点，节点也必须命中。**

它由 `11 ≥ 8` 直接成立，且**必须写成一条真测试**（§8-T5）。它的作用是：让第 3 片「起手落在节点上 → 拖节点，否则 → 平移 / 选中」的分支**不存在「点在节点上、却只有线命中」的输入**。

**⛔ 本片不决定第 3 片的分支顺序。** 歧义的另一半（「想选线却拖了节点」）由**分支顺序**消解，不由容差大小消解，而分支顺序属第 3 片。本片只保证上面那条覆盖关系成立，并把它交接出去（§11-Q19）。

### D125　节点与代理标记**必须裁剪到主图框内**；⛔ 线**不得**加裁剪

**已核实的事实**：`KLineView.draw(_:)` 的绘制**没有 clip** —— `HorizontalLineTool.swift:70` 的头注逐字记载「`draw(rect:)` 无 clip，超范围的线会画到成交量/MACD 面板上去」，这也是 `visibleGeometry` 要把 y 夹在 `[frame.minY, frame.maxY]` 内的原因（`HorizontalLineTool.swift:78`）。

**节点带来的新风险**：线是**一维**的（只有线宽方向的厚度，最粗 3.5pt ⇒ 贴边时最多溢出 1.75pt）；节点是**二维**的（直径 7pt ⇒ 贴边时溢出 3.5pt，正好是半个点）。一条价位落在可见区间最边缘的线，其节点会有**一半画到下方的成交量面板上**。代理标记贴边框画，同理。

**结论**：
- ✅ 画节点与代理标记之前，把绘制**裁剪到主图框**。
- ⛔ **绝不给线本身加裁剪。** 线今天就是不裁剪的；给它加上会让贴边的线看起来变细 —— 那是一处**本片范围之外的行为改动**，且会让「零可见变化」的承诺失真。

⇒ 裁剪的作用域必须**恰好包住节点与代理标记的绘制**，`tool.render` 之前不得受影响。**这一条的守卫是 §8.2-T10**（⛔ 不是 T6 —— T6 走 `tool.render` 直调，碰不到 dispatch 层的裁剪，评审 R3 实证）。另配 §8.2-T6：同一条线在加与不加节点两种情况下，**线本身的像素逐点相同**。

**这对水平线做不到。** `HorizontalLineTool.lineXRange` 对 `.straight` 恒返回 `(frame.minX, frame.maxX)`（`HorizontalLineTool.swift:55`）—— **横向怎么平移，线都横贯整屏**。`.ray` 也一样被夹到左边框（`:59`）。横向平移真正会移出屏幕的**只有锚点**，而那恰恰就是 Q1 描述的那个洞。

**要让水平线整条消失，只能纵向**（价格滑出可见价格区间 ⇒ `visibleGeometry` 返 nil，`:78`）。

⇒ 本片 §9 的验收清单把这一条**拆成两条**：一条纵向（线与点一起消失）、一条横向（线还在、点变成代理三角）。⛔ 照上游原文写会让验收者照着一个做不到的动作打「不通过」。

### D131　节点的**命中集合 ≡ 渲染集合**（同一判据，⛔ 不得分叉）

**来源**：spec 对抗性评审 R1-medium 指出本 spec 上一稿的 **T5 与 T8 在一个具体输入上直接矛盾** —— **已逐步核实为真**。

**冲突的构造**（原样记录，供后续评审复核）：一条 `.straight` 水平线，锚点 x 落在主图**左缘外 1pt**，价位仍在可见区间内。取点 P =（`frame.minX`, 线的 y）：

| 判据 | 结果 | 依据 |
|---|---|---|
| 线命中 P？ | **是** | `abs(P.y - g.y) == 0 <= 8` 且 `P.x == g.minX`（`HorizontalLineTool.swift:103`；线恒横贯整屏，F3） |
| P 到真节点中心的距离 | **1pt** | 真节点在 `minX - 1` |
| 上一稿 **T5** 要求 | 1 < 8 且线命中 ⇒ **节点必须命中** | — |
| 上一稿 **T8** 要求 | P 正是代理标记所在处 ⇒ **必须无答案** | — |

⇒ 两条**不可能同时绿**。

**根因（比冲突本身更重要）**：上一稿**定义了「什么时候画真节点」（D123），却没定义「什么时候节点可命中」**，默认了两者一致却没写出来；而上一稿 §8.3 为了让 N7 可测，把命中函数设计成**只收一组节点坐标** —— 那样的函数**看不到主图框，无法知道某个节点是否出屏**，于是会对出屏节点照样返回命中。

**⚠️ 这正是本仓 1a-i 已经为「线」立过的规矩，上一稿没沿用到「节点」上**：`HorizontalLineTool.swift:68-71` 头注逐字 ——「render / hitTest / 标注三者**共用同一判据**（codex branch-R3：**避免分叉**）」。

**本条结论**：

> **节点的命中集合与节点的渲染集合是同一个集合。画得出的节点才命中得了；画不出的节点一律不可命中。**

逐条落实：

| 情形 | 画什么 | 节点可不可命中 |
|---|---|---|
| 线不可见（`visibleGeometry == nil`） | 什么都不画 | **不可命中**（没有节点） |
| 线可见 **且** 锚点 x 在主图横向范围**内** | 真节点 | **可命中** |
| 线可见 **但** 锚点 x 在范围**外** | 代理标记 | **不可命中**（代理标记不是节点） |

**不做这一条的后果（真实、且是静默的）**：第 3 片接上拖动后，用户按住代理标记想**平移图表**，实际会开始拖那个**看不见的锚点** —— 屏幕上没有任何东西跟着手指动，而持久化的锚点已经被改掉。这与 D123 硬约束要防的语义失真**同族**，只是换了个入口进来。

**⛔ 本条不规定在哪里加代码**，只规定两件结果：① 命中与渲染吃同一个可见性判据，⛔ 不得各写一份；② 命中函数必须**能够**表达可见性（上一稿那个只收坐标的形状做不到，见 §3.5 的两层结构）。

## 3. 本片做什么

**四项，与上游 §3.1 逐条对应。**

### 3.1 D111 的节点几何：工具无关的一处投影

给定一条线与一个 `CoordinateMapper`，算出它**每个锚点**的屏幕坐标（`indexToX(candleIndex)` × `priceToY(price)`）。

- **工具无关**：⛔ 不得按 `toolType` 分支算几何。
- 对水平线返回 1 个点（`requiredAnchors == 1...1`，`HorizontalLineTool.swift:13`）；对将来的多锚工具返回 N 个，**顺序与 `anchors` 数组一致**。
- **纯函数、host 可测。**

### 3.2 「哪些工具有节点」登记表（只登记水平线，D122）

配**集合等式**形式的漂移告警（D122 的硬约束）。

### 3.3 D107 的节点渲染 + D123 的代理标记

- 节点：**纯黑实心圆**（`AppColorScheme == .dark` 时纯白）、**无描边**、与线连成一体、**仅选中态显示**、直径 **7pt**（D124）。
- 代理标记：**小三角**，尖头朝屏幕外，贴主图边框，同色族，仅在「选中 **且** 真节点画不出来」时出现（D123）。
- 二者的绘制**裁剪到主图框**；线不裁剪（D125）。
- 落在**一处工具无关的实现**里，且不得只能在 UIKit 下编译（D121）。

**三种结果互斥且穷尽**（本片的核心判据，§8-T1 按它写测试）。**第三列由 D131 规定，与第二列同源、不得分叉**：

| 前提 | 画什么 | 节点可不可命中 |
|---|---|---|
| 线本身不可见（`visibleGeometry == nil`） | **什么都不画**（线、节点、代理标记全无） | **不可命中** |
| 线可见 **且** 锚点 x 落在主图横向范围**内** | 画**真节点** | **可命中** |
| 线可见 **且** 锚点 x 落在范围**外** | 画**代理标记**，朝向由在左侧还是右侧决定 | **不可命中** |

### 3.4 D108 取消线变蓝

`isSelected` 分支不再更换描边色；选中反馈 = **节点 + 底栏 🗑/🔒 由灰变亮**（后半句是 D27 保留下来的部分，**原样不动**）。

连带：删除 `selectionRGBA`（D127）、翻转 / 删除 5 条测试（§7.1）。

**⛔ `isSelected` 这个参数本身保留** —— 它现在的含义从「画成蓝色」变成「画出节点」。`DrawingTool.swift:18-22` 的头注需相应改写，但**协议签名不变**。

### 3.5 节点命中的纯函数（**不接任何手势**）

给一个屏幕点与一条线，回答「它落在**第几个锚点**上」（没落在任何节点上则无答案）。

**必须分成两层**（D131 的第 ② 条结果要求）：

| 层 | 收什么 | 做什么 |
|---|---|---|
| **外层** | 一条线 + `CoordinateMapper` | ① 用**与渲染共用的那个可见性判据**筛出**可见的真实节点**；② 把筛出的坐标**连同各自的原 `anchors` 下标**交给内层 |
| **内层**（纯函数） | 一组 `(坐标, 原下标)` + 一个屏幕点 | 只做最近距离选择，返回**原下标** |

- 命中半径 **11pt**（D124）。
- **⛔ 返回的必须是原 `anchors` 下标，不得是筛选后数组的下标**。否则第 3 片拖动时会**拖错锚点** —— 当一个锚点出屏、另一个在屏内时，筛后下标 0 对应的可能是原下标 1。⚠️ 这一条在本片**无法被测试证伪**（水平线只有 1 个锚点，构造不出混合输入），故交接为 **§11-Q24**。
- **多节点时必须有确定答案**：⛔ 不得依赖字典序或遍历顺序。判据是**距离最近者**；距离相等时取**原下标较小**者。
- **出屏的锚点不可命中、代理标记不可命中**（D131）。代理标记上的按压应落到「平移图表」分支（第 3 片行为）。
- 内层因为只收坐标，**可以直接喂两个靠得很近的点** ⇒ N7 可测，且不必伪造工具（§8.3）。
