## 2. 决定（每条只写一次；验收判据与它同处）

### D1 · 接口形状：`Slot` + 两条相对路径

`copy_stock` 接 `qmt_pool.Slot`（`code` / `market` / `universe_idx`，`Slot` **不能省**——
在途标记要写 `code` 与 `universe_idx`，其形状校验要求
`source_snapshot.universe[market][universe_idx] == code`）**外加两条相对路径**（1m、daily，次序钉死）。

**为什么必须额外接路径**：`{name}` 这一段上游拿不到——`Slot` 没有；
`freeze_universe(codes, *, seed)` 吃裸 code 列表（`qmt_pool.py:147`）；
`ExportLogEntry` 七字段无 name，`source=str(row[id_col])` 而 `id_col` 命中 `stock` 列
（`qmt_ingest.py:19/33/107`）。真实 `export_log.csv` 的 12 列里 `name` 与 `file_path` 都在
（`tests/test_qmt_ingest.py:233` 按 2026-08-23 挂载实测固化），是 `parse_export_log` 丢掉的。
⚠️ 但**两列都不是现成的相对路径**：`file_path` 固化值形如
`D:\qmt_export\x\{code}_{name}_{label}_前复权.csv`，是**导出机（Windows）上的绝对路径**。

**交接 S4b**：由 `Slot` 解析出这两条路径。**本片不选路线**，但解析方必须满足四条读侧硬约束，
否则每一次提交都被读侧拒掉：①整条路径过分量规则（拒绝绝对路径 / 空分量 / `.` / `..`）且落在 staging 之内；
②basename 过 `qmt_normalize._FILENAME_RE`；③解析出的 code 等于 `stock_code`；④period 等于该记录的 `period`。

**验收**：传入次序互换的 `(daily, 1m)`、以及 code 与文件名不符的组合，**都必须被拒**，
且**拒绝必须发生在写在途标记之前** —— 断言 `.inflight.json` 不存在、无 final 落地。
⚠️ 不加这后半句的话，一个**没有前置校验**的实现照样全绿：实测它会一路跑到 `commit_stock` 才被
`_validate_files` 的 `f_period == rec["period"]` 拒掉，而**那时两个 final 已落地、标记还在盘上**，
正是 D6 要消灭的状态 —— 契约自己立的原则，不能在自己的验收上落空。
⚠️ **判别力待实施阶段用变异坐实**：删掉前置校验，本档必须变红。

### D2 · staging 目标是 FIFO / 目录 / socket ⇒ 一律 `untracked_target_file`，不按有无记录分叉

判据是**调用方自己查 `stat.S_ISREG(st.st_mode)`**——`qmt_fsroot.open_regular_probe`
**只在 `open()` 失败时**才抛 `NotARegularFileError`，FIFO（带 `O_NONBLOCK`）与目录都**打开成功**
并返回 `(fd, st)`；其 docstring 明写「调用方拿到 `st` 后自行按 `S_ISREG` 拒掉」。

**为什么不能对有记录的那格重拷**（E6/E7）：目标是目录时 `os.replace` 抛 `IsADirectoryError`，
**而那时在途标记已写在盘上**，恢复流程要 `unlink` 那条 target 又撞 `EPERM`
⇒ 每次重跑都死在同一处。目标是 FIFO 时 `os.replace` 反而成功——同类篡改结局相反。
一律拒绝则两种都执行得了。

⚠️⚠️ **符号链接不在本条之列**：`open_under` 对**叶子**也施加 `O_NOFOLLOW`，
叶子是符号链接时撞 `ELOOP` ⇒ `PathEscapeError`（实测 errno 62），根本走不到 `S_ISREG`。
把它归进本条＝把一次信任边界破坏降级成普通池缩水。**本条里「非普通文件」不含符号链接。**

⚠️ **已登记的取舍（有记录那半边）**：这只股的 `files` / `pool_order` 记录**原样留着**，而失败收尾
沿用大 spec §4.5 步骤 1（记 failure、`attempts` 加一、推进 `cursor`、继续下一只）⇒ 它会**同时**出现在
`pool_order`+`files` 与 `failures` 里，实测 `commit_stock` **接受**这个组合。三条后果一并登记：
①`reason` 字面说谎（它是 tracked 的）；②大 spec §4.4 O2-F14 明写「`fetch_failures` 只统计未解决条目，
否则一只已在 `pool_order` 里的股会被一直算成『拷贝失败让池缩水』」—— 本条恰好造出那个读数；
③它让 D8 末段「只在恢复第③档退过 `cursor` 后才被重新走到」**不再穷尽**，因为补拉会先重试
`attempts < 2` 的条目，从而重访一个**有记录**的槽位。**本片不解决**（要动失败收尾的语义，超出单股事务范围）⇒ **交接 S4b**。

**验收**：**目录与 FIFO 各一档**（只测 FIFO 会全绿，因为 FIFO 的 `os.replace` 本来就成功）；
且必须构造「记录的 `bytes` 恰等于那个非普通对象的 `st_size`」，否则测试是碰巧过的。

### D3 · 源侧叶子不是普通文件 ⇒ `fetch_missing_file`

判据同为调用方自查 `S_ISREG`。落进本条的只有「打得开但 `S_ISREG` 为假」（FIFO / 目录）
与「打不开且 `lstat` 显示非普通」（socket → `NotARegularFileError`）。
**叶子是符号链接同样是整次致命**（`ELOOP` ⇒ `PathEscapeError`），不走本条。

**为什么源侧记候选失败、staging 侧记拒绝覆盖**：两者都是**候选级**处置，只是动作不同——
源侧那只股没有可用源文件（跳过它，继续下一只）；staging 侧那个对象来路不明（**不许覆盖它**，跳过该股）。
**判据不是「影响面多大」**（那把尺子是 R87-F1 给**路径分量**用的，分量被换掉影响同目录所有股 ⇒ 整次致命），
**而是「这只股能不能继续」**。

⚠️ **已登记的取舍**：复用 `fetch_missing_file` 会让一次篡改在 pilot 报告的
`fetch_failures.by_reason` 里显示成「文件不存在」，操作者可能去查「导出为什么没生成它」。
代价换的是**不新增 failure `reason`**（那份全集声明为闭合，加值要同步改 4c 报告 schema）。

**验收**：**源侧 FIFO 与源侧 socket 各一档**。
⚠️ 括号里那个风险（`except OSError` 把权限错误混成一族）**只有 socket 那条路触发** ——
FIFO 带 `O_NONBLOCK` 打开**成功**，走的是调用方 `S_ISREG` 那一支，根本到不了抛 `NotARegularFileError` 的分支；
而「断言不是 `PathEscapeError`」对 FIFO 是**恒真断言**（`PathEscapeError` 只在 `ELOOP`/`ENOTDIR` 时抛）。
故 socket 那档另须断言：`PermissionError`（`EACCES`，打桩造）**不**被归成 `fetch_missing_file`。
⚠️ **判别力待实施阶段用变异坐实**：把实现改成 `except OSError: raise StockCopyFailed("fetch_missing_file")`，这两档必须有一档变红；零红即说明判据仍无判别力，回头重构造。

### D4 · 幂等四象限，且**任何有记录的格**都要在落地前比对

四象限（manifest 有无记录 × 目标在不在）照大 spec §4.5 原表，另加两条：

1. **「相符」的判据含 `S_ISREG`**（见 D2）——非普通文件在任何一格都不算相符。
2. ⚠️ **比对不只挂在「重拷」那一格**：只要**账本里有这只股的记录**，
   新拷出来的 `bytes`/`sha256` 就必须与记录比对，**「有记录 × 目标不存在 → 正常拷贝」那一格同样要比**。
   理由：那一格同样可达（final 因写回丢失或被外部删除），
   且同样会在提交时撞 `qmt_manifest` 规则② 的「已提交的 files 记录只许新增、不许修改」——
   而那时两个 final 已落地、标记已写，正是 D6 要消灭的状态。

**验收**：「有记录 × 目标不存在 × 源已换代」单独一档，断言不写标记、无 final 落地。

### D5 · 比对不符 ⇒ 终止整次运行；比对必须早于两次 `os.replace` 与在途标记

不符的唯一可能成因是**源在本次运行期间变了**（判据只查本地文件与 manifest，不回读源文件）。
**定性：终止条件，不是这只股的失败**——删这只股的两个 `.part`、
**不记 failure / 不加 `attempts` / 不推进 `cursor`**、rc≠0。
与 R44-F2 / R66-F3 / R87-F1 同一判据的第四次应用：**「环境不对」不能记成「这个候选不行」**。

**为什么必须早于标记**（E5 与反事实对照）：排在提交时的话，撞规则② 那一刻两个 final 已落地、
`.inflight.json` 已写，盘上已是新代次而账本仍记旧 sha —— 一次静默的代次混合。

**manifest 一个字段都不写。** ⚠️ 曾考虑「写一个顶层诊断键」，**否决**：它没有消费者
（4c 步骤 ② 只按 `fetch_fatal_error` 存在性、其次按 `stopped_reason` 取值分支）、
没有解除时机，且**粘住删不掉**（`_carry_forward_persisted_keys` 会把省略的非必需键带回，
显式写 `None` 只会变成 `null`）。
**不新增 `stopped_reason` 取值**（旧读侧按闭合值域会把整份账本判非法）。

⚠️⚠️ **「什么都不写」的安全性挂在哪里，必须说准**：
接住这一档的**不是**收尾复校（它排在拷贝循环之后，本档终止时根本没跑），
而是**下一次运行启动期的补拉前置复校**（大 spec §4.4：补拉默认对所有先前已拷文件重算源 sha256，
任一不符即拒绝启动）与 **pilot 侧的三方相等源校验**。
⇒ **交接**：S5 若改动这两条机制，须知道它们是本档唯一的持久防线。

**验收**：断言 rc≠0、两个 `.part` 已删、`.inflight.json` 不存在、manifest 逐字节未变。

### D6 · 在途标记一经写下，只有两条出路

走到「提交成功 + 删标记」，或**终止整次运行**。**不存在「接住异常继续下一只股」这条路**：
下一只股的事务会**覆盖** `.inflight.json`，上一只的回滚凭据随之消失。

⚠️ 后果的准确说法：**一个孤儿 final 就够把这只股永久除名**，不需要两个 ——
大 spec §4.5 R37-F1 的原始论证正是「1m 拷成功、daily 失败 ⇒ 1m 的 final 已躺在 staging 里 ⇒
下次撞四象限「目标存在 × 无记录」⇒ `untracked_target_file` ⇒ 一次瞬时抖动被永久固化」。
故三个窗口里**只有第一个**（标记已写、第一次 `os.replace` 之前）是良性的；
**崩在两次 `replace` 之间、以及之后，都会留下至少一个孤儿 final。**

⚠️ 本纪律**编排层强制不了**（与 `begin_run` 那条 S2-F20 残留同源）。
**交接 S4b**：`copy_stock` 抛出的任何异常，只要发生在标记写下之后，一律终止本次运行。
**S4a 只负责抛，S4b 负责收**——S4a 不得代为终止，S4b 不得把它降级成候选失败。

⚠️ **标记自己的耐久等级：`full_sync=True`**（fix round 10 · codex R7 [high]）。
标记是本条**唯一的授权凭据**——它授权崩溃恢复去删那两条 final 与两条 `.part`。
此前它走 `qmt_fsroot.atomic_write_json` 的默认 `full_sync=False`（普通 `fsync`），于是
**凭据的耐久等级低于它要授权去删的那些东西**：本平台 `man 2 fsync` 明写 `fsync`
既不保证断电耐久、也不保证写序，故「先写标记、再两次 `.part → final`」这个**代码次序**
并不等于**落盘次序**。一次断电可以让某条 final 的目录项已经持久、而 `.inflight.json`
还不在盘上 ⇒ 恢复流程**手里没有凭据** ⇒ 那条孤儿 final 撞四象限「目标存在 × 无记录」
被判 `untracked_target_file` ⇒ **这只股被永久除名**，正是上一段「一个孤儿 final 就够」
那个后果。**授权在最需要它的那一刻可能根本不存在。**
**这与大 spec 自己的 O2-F1（[high]）是同一条推理的另一端**：O2-F1 要求「回滚删两条
final 必须先耐久，才允许删标记」，理由是**凭据必须比它授权的动作后消失**；本条是
**凭据必须比它授权的动作先出现**。大 spec 把这条推理用在了删除端，创建端漏了。
⚠️ **这是耐久性推理，不是一次真断电实测**（评审自陈如此，本仓也做不了断电实测）；
可被测试钉住的那一半是**次序**与**传下去的参数**，见下方验收。

**代价（登记，不是免责）**：`F_FULLFSYNC` 会 **drain 整个设备队列**，每只股因此**多一次**
——本片一只股原本只有 `commit_stock` 那一次，现在是**两次**。大 spec §4.5 O4-F11 原文
写的量级「每股 1~2 次」随之变成 **2~3 次**（那一句已进 §5 覆盖表）。
⚠️ **上面那个数是「落地点」口径**（与大 spec 原文同口径）。**真正被 drain 的是每一次调用**，
而 `full_sync=True` 的每个落地点各下**两道**屏障（内容一道、目录项一道）——实测打桩计数：
一只股的 `full_fsync` 调用数由 **2 次（只有 `commit_stock`）变成 4 次**。
两个口径都记在这里，是因为代价挂在**调用**上而大 spec 的预算挂在**落地点**上，
只写其中一个会让下一次算账的人拿错乘数。
⚠️ 这个代价**只落在创建那一侧**：删标记（`_remove_inflight_marker`）本片一个字没动，
仍是 `unlink` + 普通 `fsync(staging)`——定性与交接见 §4 第 17 条。

**验收**（两条，macOS 与 Linux 上都必须真跑，**不许 `skipif`**）：
1. **次序**：打桩记录调用序列，断言在**第一次** `.part → final` 的 `os.replace` 之前，
   标记那两道 `full_fsync`（**内容**一道、**目录项**一道，后者下在 staging 根上）
   **都已经发生**。⛔ 不得退化成「全程调过 `full_sync`」——`commit_stock` 自己那两道屏障
   就能满足后者，而它们排在两次 final 替换**之后**，对本条要防的那个窗口毫无作用。
2. **参数**：断言 `full_sync=True` 真的传到了 `qmt_fsroot.atomic_write_json` 的接口上
   （漏传与传 `False` 都必须红）。⛔ **判据不得放在「有没有调 `fcntl`」上**：
   `qmt_fsroot.full_fsync` 在没有 `F_FULLFSYNC` 的平台（CI 的 Linux）退回 `os.fsync`，
   按 `fcntl` 判会让这条判据在 CI 上恒假、在 Mac 上恒真，**两边各自失去判别力**。

### D7 · `committed_bytes` ＝ 累计**写下去**的字节；回滚退还

- **每次 per-stock 提交写 `旧值 + 本次真正写盘的字节`**；崩溃恢复第③档删掉某股记录时**原值不动**。
- ⚠️ **写成「当前占用量」（`sum(files[].bytes) + staged_export_log.bytes`）会死锁**（E11）：
  恢复第③档后重拉，转移守卫要求 `≥ 旧值 + 新增字节`（706），而当前占用量只有 366
  ⇒ 提交被拒、文案指向「换新 staging 重拉」⇒ **每次重跑都死在同一处、约 2 GiB 的 staging 永久报废**。
- **回滚退还**：逐块扣减的字节，在回滚删掉 `.part` 之后按实际写出的字节数退还。
  ⚠️ **退还的触发点是「已经扣过账」，不是「拷贝函数正常返回过」**：扣减逐块发生，
  故**拷到一半抛异常**（SMB 断线 `EIO`、磁盘满）同样已扣账。
  实施上必须**逐块累加「本次已写字节」并在回滚时退还它**，不得只在拷贝函数成功返回后才记录该值。
- **S2-F38 悬案「能否收紧成严格相等」：答否，维持 `≥`。**
  理由（E13）：重拷成功时记录逐字相同 ⇒ 转移守卫算出的 `added = 0`，
  而本次真写盘 140 字节 ⇒ 累计语义要 `506`，严格相等只收 `366`。
  **两者互斥，而累计语义是 D7 的前提** ⇒ 不能收紧。
  （S2-F38 登记的障碍「未定 `committed_bytes` 计不计失败 `.part` 的字节」由退还条款定死：**不计**。）
- **S2-F42 悬案「`committed_bytes` 进不进读侧必需键」：本片不做**，
  那是「新增必需字段」须 bump `manifest_version`（O2-F8），bump 会让既有 staging 全部作废。**交接 S5**。

**验收**：同一只股连续失败三次后预算剩余量与从未尝试过时相同；
且该测试必须覆盖**拷到一半抛异常**那条路（只测「后一个文件缺失」会漏掉它）。

### D8 · 续跑时「跳过已拉好的股」由四象限承担，不得在进入它之前用 `pool_order` 预过滤

`qmt_manifest._validate_files` 强制「每条 `files` 记录的股必在 `pool_order` 里」
且「池内每只股恰两条记录」⇒ **「有记录」与「在池里」等价**。
四象限对**已成功且两个文件都完好**的槽位给 `skip`（E4）；**文件坏了或丢了则给 `recopy` / `copy`**（E3）
—— 后者正是重拷那一格赖以可达的前提。
⚠️ **因此本条是对 S2-F8 的收窄，不是等价改写**：S2-F8 字面要求「以 `pool_order` 为准跳过已成功槽位」，
本条收成「池内**且两文件完好**才跳」。**收窄的理由**：按字面无条件跳过会让重拷那一格成为死代码。
**S2-F8 因此进覆盖表。**

⚠️ **但两者不可互换**：若在进入四象限**之前**按 `pool_order` 过滤掉，
则「有记录 × 目标存在 × 不符 → 重拷」这一格与大 spec §9-5 那条 R2-F3 回归钉**双双成为死代码**。

⚠️ **这一格在一次运行里怎么到达**：新槽位区间是 `[cursor, min(quota, len(universe)))`
（`qmt_pool.fresh_slots`），已成功且 `universe_idx < cursor` 的股**不会被访问**
⇒ 它**只在崩溃恢复第③档把 `cursor` 退到那些槽位之前时**被重新走到。
**重算哈希的量级因此是「被退回的那一段」，不是整批。**

## 3b. 已登记的对外可见取舍（T1–T3：硬链接修复 · codex R1 [high]；T4–T5：`qmt_fetch` 关闭判据收口 · codex R5 [medium]；T6–T7：`qmt_fsroot` 关闭判据收口 · codex R9 [medium]）

**背景**：codex 官方评审 R1 挖出 —— 在 `<rel>.part` 植入一个指向 **staging 树外**可写文件的**硬链接**，
`O_WRONLY|O_CREAT|O_TRUNC` 会在任何校验之前把那个树外文件截断，`copy_one` **零异常返回**。
本机复现：仓外 145 字节文件被顶成拷来的 110 字节。
⚠️ **它穿过了本片全部类型纪律**：硬链接**不是**符号链接（`O_NOFOLLOW` 不适用）、
**就是**普通文件（`S_ISREG` 为真）—— 此前 6 轮对抗性评审（含多轮专攻「非普通文件」）全部未发现。

**修法**：`O_CREAT|O_EXCL` 造新 inode 的私有临时文件 → 流式拷贝 + 落地复算 → `os.replace` 发布成 `<rel>.part`。
**绝不截断既有 inode**（与 `qmt_fsroot` 对它自己原子写的既有保护同一条纪律；此前这条新写路径绕过了它）。

由此产生三条取舍（**T1–T3**），**逐条登记而非沉默**；**T4–T5** 是另一次评审（codex R5 的 [medium]，本片内部修复轮 fix round 8）的修复副产物，与硬链接无关，同样登记在这张表里：

| # | 取舍 | 定性与理由 |
|---|---|---|
| T1 | `SIGKILL` / 断电落在「临时文件已建、尚未发布」之间，会留下一个 `<rel>.part.<pid>.<rand>.tmp`，而 S4b 的回滚「只删标记里明写的四条、不做模式匹配式清扫」**不会回收它** | **接受**。与 `qmt_fsroot` 为同一保护接受的代价逐字相同；改动前同一窗口留下的是半截 `.part`，同样非零残留。⇒ **交接 S4b**：启动清理若要回收它，需要一条**新的**清扫规则，而那条规则本身会重新打开「模式匹配式清扫」的口子，须单独论证 |
| T2 | 篡改探测与 `os.replace` 之间存在残留窗口：其间被植入 `<rel>.part` 的对象会被发布**连名字换掉** | **接受，且关不掉**。POSIX `rename` 恒覆盖，而「上一次中断留下的合法 `.part` 必须被盖掉」又**要求**覆盖。⚠️ **该窗口丢不了 staging 树外的数据**：FIFO / socket 无数据可丢，符号链接被 `replace` 换掉时**不跟随** |
| T3 | `<rel>.part` 底下是**读不了**的普通文件（如被植 `0o200`）时，现在逃出裸 `OSError`(EACCES)；改动前是打开成功并截断重写 | **接受**。本工具自己写的 `.part` 一律 `0o600`，故这种对象**只可能是外来的**；对它报错而不是覆盖，方向与 D2「拒绝覆盖来路不明的对象」一致。裸 `OSError` 的处置归属见 §4 第 10 条 |
| T4 | `copy_one` **从准备发布那一刻起**把 `<rel>.part` 也列进自己的回滚名单 ⇒ 这一档的失败会删掉那个名字底下的普通文件，**包括上一次运行崩在半路留下的合法残留 `.part`**（此前 `copy_one` 无条件不删它） | **接受**。成因：`_publish_part` 在 `os.replace` **成功之后**关目录描述符那一步同样可能失败，抛出来的只是一个裸 `OSError` ⇒ **`copy_one` 分辨不了发布到底发生没有**。不列它就等于「已发布的落地物漏清 + 这一趟的字节漏退」（codex R5 隔离故障注入实测：三个已扣字节留在账上）。代价极小：`copy_stock` 的主回滚在**同一条失败路径**上本来就会删这个名字，且非普通对象照旧由 `_cleanup_part` 原样留着不碰 |
| T5 | **异常展开途中** `os.close` 失败时，失败只挂成在途异常的一条 `add_note` 诊断，那个描述符**可能没被回收** | **接受**。另一侧的代价是**顶替掉一个终止信号**（实测的阻断级后果：`MaxBytesExhausted` / `PathEscapeError` 被换成裸 `OSError`，而 §4 第 10 条允许 S4b 把裸 `OSError` 当候选失败跳过 ⇒ 必须停机被降级成跳过这只股）。POSIX 对 `close()` 失败后描述符的归属不作保证；真要漏也只在同一棵树反复报错时才累积得起来，而那时整次运行本来就该停。**没有异常在途**时的关闭失败仍然原样上抛，不咽。⚠️ **同一类里还有一档未修、在此登记**：`_open_source_leaf` 与 `classify_target` 的**成功路径**上，父目录描述符关闭失败会把**已经打开的那个叶子描述符**的关闭一起吃掉（它还没交到任何 `with` 手里）⇒ 那个描述符漏掉。**这一档与本轮改动无关**（BASE 上 `finally: os.close(pfd)` 抛出时结局逐字相同），且后果同样只是「描述符没被回收」——盘面、账面、逃出的异常类型全不受影响；关它要在这两个函数里各嵌一层纯为「只读目录描述符关不上」服务的 `try/except`，判据收益不抵可读性代价。**S4b 若观察到 EMFILE 类症状，从这一条查起。** |
| T6 | `qmt_fsroot` 那 12 个落在异常展开路径上的关闭点，**展开途中** `os.close` 失败时只挂成在途异常的一条 `add_note` 诊断，那个描述符**可能没被回收** | **接受**。与 T5 **同一条判据、同一份理由**，只是换了一个模块：另一侧的代价是顶替掉 `PathEscapeError`（信任边界被绕过）/ `BoundaryError`（目录被调包）/ `LockDisciplineError`（脑裂）/ `MarkerInvalidError`（目录不属于本工具）这四类**必须停机**的信号，而 §4 第 10 条允许调用方把裸 `OSError` 当候选失败跳过 ⇒ **必须停机被降级成跳过一个候选**（评审对 `parent_fd_under` 做过隔离故障注入复现）。POSIX 对 `close()` 失败后描述符的归属不作保证。**没有异常在途**时的关闭失败仍然原样上抛，不咽 |
| T7 | `open_under` / `parent_fd_under` 在**没有异常在途**时撞上中间描述符关闭失败，那个**已经算出来、即将交给调用方**的返回值（叶子 fd / `os.dup(cur)`）会随异常一起被丢弃 ⇒ 漏掉一个描述符 | **接受，且本片没有改动它**（BASE 上 `finally` 抛出时结局逐字相同）。它**不是**本轮那条判据的成员：逃出去的仍是同一个裸 `OSError`，盘面、账面、异常类型全不受影响，后果只是少回收一个描述符。**S4b 若观察到 `EMFILE` 类症状，与 T5 末段那一条一起查。** ⚠️ 本轮**确实**改善了它的邻居：此前第一个中间描述符关闭失败会让**其余中间描述符一个都关不上**，现在逐个独立关、只上抛第一个失败（其余以 `add_note` 挂在它上面） |

**⚠️ 一条未采纳的加固及其理由（Ruling 14）**：发布那次 `os.replace` 之后**不补目录 `fsync`**。
依据是大 spec 耐久闭合清单**自身的入选判据**——「一个命名空间改动进本清单，当且仅当**它的丢失会改变后续运行的判断**」：
`.part` 不匹配导入侧 glob、不进四象限、崩溃恢复只按标记明写路径删且容忍不存在；
清单已按同一理由对「失败路径上 `.part` 的删除」**显式豁免**。
**更硬的一条：改动前 `O_CREAT` 直接造 `<rel>.part` 同样没有目录 `fsync`，本次未新增任何目录项。**
⇒ 不改大 spec 的闭合清单。

## 3c. 本片为什么**破例**动了 `qmt_fsroot`（fix round 11 · codex R9 [medium]）

`qmt_fsroot.py` 原本在本片的**禁改清单**里（与 `qmt_manifest` / `qmt_pool` / `qmt_ingest` /
`qmt_normalize` 并列）。**user 2026-09-21 明确拍板：这一条在本 PR 里一起修。**

**评审报的是什么**：`qmt_fetch._open_source_leaf` 那句 `parent_fd_under(src_fd, rel)` 之后
才开始有关闭保护，而 `parent_fd_under` **自己**在一个**没有保护的 `finally`** 里关中间目录
描述符 —— 一条嵌套路径的某个分量撞出 `PathEscapeError`（信任边界被绕过、必须停机）时，
若更早那个中间目录的关闭失败，裸 `OSError` 会**顶替**掉逃逸信号。评审对该函数做过**隔离
故障注入**复现。而 §4 第 10 条允许 S4b 把裸 `OSError` 当候选失败跳过 ⇒ **必须停机被降级成
「跳过这只股」，运行继续**。同一个 helper 也服务 staging 侧的全部命名空间动作。

**为什么这一条与 R1（已登记的阻断级残留）不同类、可以就地修**：
它**不改任何已写明的行为** —— 没有新增/删除/改名任何公开函数，没有改任何判据的判定结果，
没有改任何异常的类型或触发条件。它只是不再让**收尾动作**顶掉**在途异常**。
R1 那条要动的是 `qmt_manifest` 的转移守卫**语义**（会改变账本的接受集合），
按治理必须走它自己的 spec → plan → 评审；本条是**纯防御性**的，不在同一类。

**改法与范围**（按判据穷尽，不按点名修）：BASE 上 `qmt_fsroot.py` 有 **14 个 `os.close`**，
其中 **12 个**落在异常展开路径上 ⇒ 全部收口到**一个**关闭判据
`_close_or_note`（`_close_all_or_note` / `with _CloseFd(fd):` / `with _CloseFds() as opened:`
是它的三个外壳）；余下 **2 个**不在任何 `try` 的异常展开路径上，源码里各写了一行可核实的
理由，**保持裸 `os.close` 不动**（逐条定性见交付报告）。

⚠️ **两处实现并存、合并不了**：`qmt_fetch._close_or_note`（fix round 8 建的，那边是**登记处**）
与本次在 `qmt_fsroot` 里建的等价物**语义同规格**，但依赖方向是 `qmt_fetch` → `qmt_fsroot`
（地基不能反过来 import 它的使用者，会成环）。两边 docstring **互相指名**，
捕获宽度同为 `Exception`（**不是** `BaseException`：`KeyboardInterrupt` / `SystemExit`
不许被当成诊断咽掉），两边**各有测试钉着**这个宽度。

**代价**登记在 §3b **T6 / T7**；留给 S4b 的事实登记在 §4 **第 18 条**；
本次因此失效的两句大 spec 语句登记在 §5 表的最后两行。
